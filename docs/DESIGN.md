## 1. 全体構成

### 1.1 層の分け方

| 層 | 役割 | Obsidian API |
| --- | --- | --- |
| 純粋な処理 | 型、値の変換・検証、表の読み書き、健全性チェック、計算 | 使わない（単体テストする） |
| つなぎ | Vault・MetadataCache との読み書き、イベントの受け取り | 使う |
| 画面 | 設定画面、入力フォーム（モーダル）、ビュー、コマンド・メニュー | 使う |

判定・変換・文字列の組み立ては純粋な処理に置き、つなぎと画面は薄く保つ。

| フォルダ | 層 | 内容 |
| --- | --- | --- |

| `id/` | 純粋 | UUID v7 とノートID（10章） |
| `parse/` | 純粋 | 値の形式チェック、本文の表の読み取り（7章） |
| `config/` | 純粋＋つなぎ | 共有設定の読み書き（5章）、設定変更の影響（5.5）。`sharedConfig.ts` だけがつなぎ |
| `store/` | 純粋＋つなぎ | ノートの読み取りと索引（3章）。`vaultStore.ts` だけがつなぎ |

| `views/` | 画面 | カスタムビューとその部品（9.12）、ビュー・フォーム・ノートを開く処理（9章。`paneGroups.ts` だけは純粋） |

- 純粋の層は `ui/`・`views/` を読み込まない。画面とレポートで使う文字の組み立ては `calc/format.ts`
  - 純粋の層を画面の作りの変更から切り離し、単体でテストできるようにするため
- `calc/` は `forms/` を読み込まない。ビューとフォームの両方で使う処理は `calc/` に置く
- `ui/` が `views/` を読むのは、ビューを開く・描き直すとき（メニュー・設定画面）だけ
  - ビューとモーダルで使う部品は `ui/` に置き、`views/` から読む

`commands/` の中身：

- ノート作成、プロジェクトの複製、フォーム・表の編集画面を開く、作業ログ、再読み込み
- aliases の同期、共有設定の監視、HTMLレポートの書き出し、使い方を開く
- ノートの種類の判定（`isTaskFile`・`isMemberFile`）は `noteFiles.ts`
  - コマンドのファイルどうしが互いを読み込み合わないように、どれからも使う判定は別のファイルに置く

### 1.3 データの流れ

1. 起動完了後（`onLayoutReady`）に共有設定を読み、索引を作る（3.2）
2. ノートが変わると索引を差分更新し、`updated` イベントを出す（3.3）
3. ビューは `updated` を受けて描き直す。計算結果は保存せず、表示のたびに計算する（要件 3.7）
4. 書き込みは次のどれかを通す
   - frontmatter の書き方（4.1）
   - 本文の変えた行だけの書き換え：作業ログの行 4.3、表の編集画面 4.7、チェックリスト 4.10

## 2. 型（`model/`）

- 日付は `YYYY-MM-DD` の文字列（`IsoDate`）、月は `YYYY-MM`（`YearMonth`）。`Date` は使わない（4.1）
- `wbs`・`case_id` は文字列。数値にすると `1.10` が `1.1`、`0123` が `123` になる（4.1）
- 任意項目は「キーが無い」で表す（`undefined` を入れない）
- 本文の表の行は、ファイル先頭からの行番号（0始まり）を `line` に持つ
  - 警告一覧で「何行目」を示すため
- ステータスは名前の文字列のまま持ち、分類はその都度 `findStatus` で引く
  - 設定を変えても索引を作り直さずに済む

## 3. 読み込みと索引（`store/`）

### 3.1 対象のファイル

- ファイル名がノートIDの形式（`TASK-…` など。10章）のものだけを対象にする。フォルダは問わない
- アーカイブフォルダの中のノートも読み、`archived` で区別する
  - 一覧の既定では除くが、IDの重複確認や参照先の確認には含める

### 3.2 起動時の読み込み

- `onLayoutReady` の後に全ノートを読む。`onload` には含めない（起動を遅くしないため）
  - 4,000件で `onload` は約3ミリ秒、索引の作成は約0.1秒
- 200件ずつ処理し、区切りごとに処理を譲る（画面を固まらせないため）
- 本文を読むのはプロジェクト・メンバー・作業ログだけ（表があるため）
  - タスクのチェックリストは MetadataCache の `listItems` から数え、ファイルを読まない
- 作り直し中に再度呼ばれたら、同じ処理の完了を待つ
- 作り直しの間に変わった・消えた・名前が変わったファイルは覚えておき、最後に読み直す
  - 無くなっていれば索引から消す
  - 作り直しは途中で読んだ内容でまとめて置き換えるので、古い内容での上書きを防ぐため

### 3.3 差分更新

- frontmatter・本文の変更は MetadataCache の `changed`（解析後のキャッシュと本文を受け取れる）で受ける
- `changed` はリネームで呼ばれないので、vault の `rename` を別に受ける。削除は vault の `delete`
- ビューへの通知（`updated`）は300ミリ秒まとめて出す（入力中に何度も描き直さないため）
- タイトルが変わったら `title-changed` を出す（4.2）。最初の読み込み中は出さない
- 多くのノートをまとめて書くとき（WBS 番号の振り直し。9.7）は `writeMany` を使う
  - 書いたファイルがすべて `changed` で読み直されるまで、`updated` を止める。最後に1回だけ出す
  - 300ミリ秒のまとめは最初の変更から数えるので、書き込みが続くと何度も描き直して重くなるため
  - 知らせが届かないときのために上限を置く（書いている間10秒、書き終えてから2秒）
  - 書き込みは並行に行う。書く前に対象のファイルがすべてあるか確かめる

### 3.4 値の読み取り（`buildNote`, `Coercer`）

- 空の値（`null`・空文字・空配列）は未入力として扱い、問題にしない
- 型が違う値は無視し、理由を `problems` に記録する（健全性チェックで出す。8章）
- `wbs`・`case_id` が数値で読まれていたら、文字列に戻して警告する
  - 元の表記が失われている可能性があるため。直し方はフォームでの入れ直しを案内する（4.9）
- `.obsidian/types.json` でこの2つを「テキスト」型に固定することはしない
  - 値はフォームから文字列で書くので、数値になる経路はノートの直接編集だけ
  - types.json が効くのはプロパティ欄の入力だけで、ソースモードの手入力は防げない
  - Vault ごとに設定ファイルを配る手間に見合わない。警告で気づければ足りる
- プロジェクト・エピック・タスクは、必須の参照（`project`, `status`）が無いとモデルを作らない
  - ただし他の項目も最後まで調べ、誤りをまとめて報告する（直すときに一度で分かるように）
- メンバーの数値が無ければ既定値（8h・120%・在籍）を使う
- 作業ログのメンバーと月はファイル名を正とし、プロパティと違えば警告する
- frontmatter の `title` は、モデルを作れなかったノートでも `NoteRecord.title` に持つ
  - 警告一覧で人が見分けられるように

### 3.5 種類ごとの一覧（`VaultIndex`）

- `tasks()`・`members()` などは、種類ごとに分けた一覧を返す
  - 分けるのは索引が変わってから最初に呼ばれたときの1回だけ（`version` で判定）
  - 1回の描画で何度も呼ばれ、そのたびに全ノートを見ると重いため
- アーカイブ内を含む一覧と含まない一覧を別に持つ。順は索引に入れた順のまま
- 返す一覧は `readonly`。呼び出し側で並べ替えるときは写しを作る
  - 同じ配列を使い回すので、書き換えると次に呼んだ側の結果が変わるため

## 4. 書き込み

### 4.1 frontmatter（`write/frontmatter.ts`）

Obsidian 1.14.5 の `processFrontMatter` の実装を読み、`yaml` 2.9.1 で再現して確かめた結果に基づく。

- `processFrontMatter` は `yaml` ライブラリ v2（YAML 1.2）で読み書きし、frontmatter 部分だけを置き換える
  - 書き出しの設定：`{nullStr: "", lineWidth: 0, aliasDuplicateObjects: false}`。本文は変わらない
- キーはオブジェクトの順に書き出される
  - コールバックの中で全キーを消し、`FRONTMATTER_KEYS` の順に入れ直す
  - 決めていないキーは元の順で後ろに付ける
- 日付は文字列で渡す。`Date` を渡すと `2026-11-30T00:00:00.000Z` になるので、渡したらエラーにする
- リンクは `"[[ID]]"`（ダブルクォート付き）、配列はブロック形式で書かれる
- 手で編集したノートは、最初の書き込みで frontmatter 全体の書式が整う（2回目以降は差分が出ない）
  - frontmatter 内のコメントは消える
- YAML が壊れている（SVN のコンフリクトなど）と例外になるので、呼び出し側で通知する

### 4.2 aliases の同期（`write/aliases.ts`, `commands/aliasSync.ts`）

- aliases はタイトルと同じ値1つだけにする（要件 3.2）。手で足した値や以前のタイトルは残さない
- タイトルが変わったら1.5秒待ってから書く（ソースモードで入力中に何度も書かないため）
  - 待っている間にさらに変わったら数え直す
- 書くのは、この PC の前面のウィンドウで開いているノートだけ（`getActiveFile` と `hasFocus`）
  - ファイルサーバーでは全員の PC が変更に気づき、同じファイルに一斉に書きにいくため
  - タイトルを直接変えるのは、そのノートを開いて入力している人だけなので足りる
- 起動時・再読み込みでは書かない（SVN 更新などで多数のノートが一斉に書き換わるのを防ぐ）
  - ずれているノートは健全性チェックで知らせる
- すでに合っていれば書かないので、書き込み→変更検知→書き込み…の繰り返しにならない

### 4.3 作業ログの入力（`calc/worklogCells.ts`, `forms/worklogGrid.ts`, `ui/worklogGridModal.ts` ほか）

縦にタスク・横に1週間か1か月の日付のマス目に、予定か実績の時間を入れる。

- 作業ログのビュー（9.10）から開くときは、メンバーと日を渡す（`openWorklogModal` の `at`）
  - 期間はその日を含む期間にする（`defaultDate`）。メンバーを渡さなければ通常と同じ選び方
  - 日の欄から開くときは、その日のマスに入る（`focusDate`。無ければ今日、それも無ければ最初の日）
  - ビューが予定だけ・実績だけなら、フォームもその値で開く（`defaultMode`。初めは実績）
  - タスクを渡したときは、そのタスクの行に入る（最初の行へ移し直さない）

- マス目の値と書き換えは純粋関数に置く。画面（`ui/worklogGridModal.ts`）は描くことと呼ぶことだけ
  - `calc/worklogCells.ts`：期間、マスのキー、記録の集計、行の階層、合計。作業ログのビュー（9.10）と共有する
  - `forms/worklogGrid.ts`：変えたマス、検証、月ごとの分け方、作業ログの表への書き換え、保存後の知らせの文
  - `forms/worklogGridDraft.ts`（`WorklogGridDraft`）：保存前の値と、保存したが索引にまだ載っていない値
    - メンバーごとに持ち、期間・メンバーを替えても残す。保存していないマスの数もここで数える
- 見た目とキーでの移動は工数配分のマス目（4.7）と同じ（`forms/gridMove.ts`、CSS も共通）
- 描き直し（保存・絞り込み・開閉・切り替え）では、スクロール位置を保つ（`render()`）
  - 中身から外側の枠まで、すべての縦横の位置を戻す。どの枠がスクロールするかはテーマで変わるため
  - 列の幅が決まったあと（次の描画）にもう一度戻す。幅が足りずに途中で止まることがあるため
  - 予定・実績の切り替えでは、最後に入ったマスへ `preventScroll` で戻る。入るときの自動のスクロールを防ぐため

並べ方：

- 横は「1週間」（月曜〜日曜）か「1か月」（1日〜末日）を切り替える（`periodDates`）
  - 毎週付ける人と、月でまとめて付ける人の両方に合わせるため
  - 前後・今週（今月）と日付の選択で期間を替える（`shiftPeriod`・`periodStartOf`）
  - 切り替えたときは、今の期間の最初の日を含む期間にする
  - 1か月はマスを狭くし、横に流す。タスク名・見積・月の合計の列は左に固定する
  - 選んだ単位は個人の設定に覚える（6章）。初めは1週間
- 縦（`gridTaskIds`）：担当の未完了タスク、その期間に記録のあるタスク、画面で足したタスク
  - 未完了＝ステータスの分類が完了・停止でないもの
  - 「完了・停止した担当タスクも表示」で完了・停止も並べる（`assignedTaskIds`）。初めは出さない
  - 終わったタスクで行が増えすぎないため。選んだ値は個人の設定に覚える（6章）
- 行はプロジェクト → エピック → タスクの階層（`gridLines`）。並びと番号はガント（9.8）と同じ
  - プロジェクトは名前順、エピック・タスクは WBS 番号順。「（エピックなし）」は後ろ
  - 名前は `NO_EPIC_LABEL`（`calc/format.ts`）。その行かどうかは名前で比べず `noEpic` で見る
    - 同じ名前のエピックを作られても区別できるようにするため
  - 見つからないタスクは「（見つからないタスク）」にまとめ、エピックの行をはさまない
  - プロジェクト・エピックの行は ▶／▼ で開閉し、日ごと・月ごとの小計（入力している側）を出す
  - 初めはすべて開く（入力の画面なので、タスクのマスが見えている方がよいため）
  - 開閉は画面を開いている間だけ覚える。見出しの「すべて開く・すべてたたむ」で一度に変える
  - 足したタスクが、たたんだ行の中なら開く
  - 日の合計は、たたんだ行も含めた（絞り込み後の）全タスクの合計
  - ほかのタスクは表のいちばん下の「＋タスクを追加」で、名前で探して足す（`ui/chooseModal.ts`）
  - 担当のタスクを★付きで先に出す
- プロジェクト・エピック・ステータスで行を絞れる（`filterGridTasks`）。足す候補も同じく絞る
  - エピックはプロジェクトを選んだときだけ出す。プロジェクトを替えたらエピックは外す
  - ステータスは1つ選ぶ（プロジェクト・エピックの欄と同じ形にそろえるため）
  - ステータスは旧名も現在の名前にそろえて比べる（`currentStatusName`）
  - 絞っても、隠れた行の入力は残り、保存の対象になる
  - 日の合計は、絞り込みで残った行の合計。絞り込み中は見出しにそう書く
- 予定・実績は切り替えて片方を入れる。もう片方はマスの右下に小さく出す
  - 2列にすると横幅が倍になるため
- 見出しに今日（アクセント色）と休日（会社・個人・土日。灰色、理由はツールチップ）を出す
- 列はタスク名・見積(h)・月の合計・日付の順。下に日の合計（入力している側）
  - 見積はタスクの `estimate`（参考。灰色）。グループと合計の行は配下の合計（`sumEstimates`）
  - 見積と月の合計を名前のすぐ右に固定し、日付の列を流しても見比べられるようにする
  - 固定の位置は、左にある見出しのマスの幅の合計（`pinColumns`。列の幅が中身で変わるため）
  - 表の大きさが変わるたびに測り直す（`ResizeObserver`）。開く動きの拡大・縮小の分は戻して測る
  - `offsetLeft` は使わない。固定したマスでは表ではなく画面の枠からの位置になるため
  - 表の枠（`pm-worklog-grid-wrap`）は高さを `60vh` までにし、枠の中で縦にも流す
  - 日付の見出しを上、日の合計の行を下に固定する（`position: sticky`）
  - sticky は一番近いスクロールする枠に対して効くため。横に流す枠は縦の固定もその中になる
  - 合計は月ごと（工数は月で換算するため）。表示していない日の記録も含めた、その月全体の合計
  - 週が月をまたぐときは、両方の月の列を出す（`monthsOf`）
- 期限日・開始日は列にせず、日のマスの線で示す（列を増やさず、日付の位置で分かるため）
  - 期限日（`due`）の日のマスは右端に赤い線（`is-due`。ガントの期限日の線と同じ色）
  - 開始日（`start`）の日のマスは左端に青い線（`is-start`。ガントの開始日の線と同じ色）
- 1日の通常稼働は注意書きに出す
- タスクの作業範囲（`calc/taskRange.ts`）に入る日のマスに印を付ける。上に凡例を出す
  - 当初期間は薄い塗り（`is-plan`）、見込みの日程はマスの上の細い棒（`is-schedule`）
  - ガントの当初期間の帯・棒と同じ意味と色にし、入力しながら当初の計画と見比べられるようにするため
  - 日程は `rangesOf` で毎回引く。`commands/worklog.ts` の `ContextCache`（11章）で使い回す
  - 索引が変わったら値と一緒に描き直す（`drawCell`）。読み上げにも範囲の中かを足す
- 保存前に記録から変えたマスは、黄の薄い塗りと太字にする（`is-edited`。`cellEdited`）
  - 予定・実績は今入力している側だけを比べる。記録と同じ値に戻すと印は消える
  - 保存すると消える。読み上げにも「保存前の変更」を足す

マスの値：

- 記録は索引から読み、同じ日付・タスクの行は合計する（`gridHoursOf`。集計でも合算するため）
- 0 と空は同じに扱う（`normalizeHours`）。空欄は 0 とする決まり（要件 3.5）に合わせるため
- 入力はメンバーごとに覚え、期間・メンバーを替えても残す。「保存」で全部をまとめて書く
  - 記録と同じ値に戻したマスは書かない（`gridChanges`）
  - 保存していないマスがあるまま閉じるときは確認画面を出す
- 誤り（0.25刻みでない値）は保存時に一覧で知らせる（`validateGridChanges`）
- 保存した値は、索引に載るまで画面の上で重ねて出す（描き直しで古い値に戻って見えないように）
- 索引が変わったら、入力中のマス以外の値と合計を描き直す（ほかの人の SVN 更新など）
- メモはマス目で扱わない。「（月）の記録を一覧で編集」（4.7）で書く
  - 週が月をまたぐときは両方の月のボタンを出す

書き込み（`worklogGridEdits`、`commands/worklog.ts`）：

- 変えたマスを月ごとに分け、メンバー×月のファイルに書く
- 書く時点の本文から行を読み直し、日付・タスクで行を探す
  - 行番号ではなく中身で探すので、開いたあとにほかの行が変わっていてもよい
- 変えたマスは、その日付・タスクの1行目を書き換える
  - 同じ日付・タスクの行がほかにもあれば消して1行にまとめ、メモは「 / 」でつなげて残す
  - 1行にしないと、マスの値（合計）と書いた値がずれるため。まとめたら保存後に知らせる
- 予定・実績とも空にしたマスは、その日付・タスクの行をすべて消す。消したメモの数を知らせる
- 行の無いマスは日付順の位置に足す
- 表の書き換えは 4.7 の `applyTableEdits` を使う
  - 変えた行以外は1文字も変えない。改行コード（CRLF）も保つ（SVN の差分を最小にするため）
- 日付やタスクが読めない行はマス目に出さず、そのまま残す（健全性チェックと一覧の編集で直す）
- メモの `|` は `\|` に、改行は空白にする（表を壊さないため）
- 表が無ければ本文の末尾に作る（`appendTable`。本文が frontmatter だけなら空行をはさまない）
- ログファイル（メンバー×月）が無ければ作業ログのフォルダに作る。消すだけのときは作らない
- ログファイルは、まず索引から探し、無ければ作業ログのフォルダのパスで探す
  - アーカイブなど作業ログのフォルダの外にあっても、索引にあればそれを使う
  - 作ったばかりのファイルは Obsidian が読み終えるまで索引に載らない
  - 索引だけで探すと、同じファイルをもう一度作ろうとして失敗するため
- Obsidian で表を編集すると表全体の列幅がそろえ直され、差分が広がる。対策は 4.8

開く場所：

- コマンド「作業ログを入力」と、プロジェクト状況のタスクの行の「＋工数」（9.4）
- タスクの行から開くときは、そのタスクの行を足して開き、タイトルにタスク名を出す
  - 担当でなくても行が出るので、すぐに入れられる
- 最初に選ぶメンバー（`defaultWorklogMember`）
  - 前回選んだ人がそのタスクの担当者ならその人
  - そうでなく、在籍の担当者が1人ならその人。ほかは前回選んだ人
- 開いたら、最初の行の今日のマス（今日が期間に無ければ最初の日）に入る

### 4.4 ノートの作成（`commands/newNote.ts`）

- 入力を確かめ、作るノートのパス・frontmatter・本文を決める処理は純粋関数にする
- ステータスは一覧の先頭（新規作成時の初期値。要件 3.6）
- 本文に空の表を入れる（そのまま読み取れる形）
  - プロジェクトは「マイルストーン」「工数配分」、メンバーは「個人休日」
- ファイルを作ってから `processFrontMatter` で frontmatter を書く（4.1 のキー順を通すため）
  - フォルダが無ければ作る。作業ログのファイルと共通（`write/frontmatterFile.ts` の `createNoteFile`）
- 2回目の書き込み（frontmatter）が失敗しても、作成は終わりとする
  - 画面を閉じ、作りかけであることとパスを通知する
  - 画面を開いたままだと、もう一度押されて別のIDのノートができるため
  - 作業ログのファイルも同じ（行は書けているので保存は成功として通知する）
- 作ったノートは開かず、「「タイトル」を作成しました」と通知するだけ
  - 値はすべて画面から入れる方針（4.9）で、ノートを開いても使わないため。作ったものはビューにすぐ出る
- ID は索引で重複を確かめて採番する（アーカイブ内も含む）
- タスクの WBS 番号は、同じエピックのタスク（アーカイブ内も含む）の続きの連番にする（11.17）
- まだ入力していないプロパティも、`FRONTMATTER_KEYS` のキーをすべて空の枠として入れる
  - プロパティ欄にはじめから項目が並び、どこに何を書けばよいか分かるようにするため
  - 空の値（`model/frontmatter.ts` の `emptyValue`）：リストのキー（`LIST_KEYS`）は `[]`、ほかは `null`
  - `null` は 4.1 の設定で `start:` のように値なしで書かれる
  - 読み取り（3.4）は `null`・`[]` を「無い」と同じに扱うので、警告や計算は変わらない

### 4.5 入力補助フォーム（`forms/taskForm.ts`, `epicForm.ts`, `projectForm.ts`, `memberForm.ts`）

共通：

- frontmatter から読める値だけをフォームに入れる（必須項目が欠けたノートもフォームで直せるように）
- リンクの項目で読めない値（打ち間違い、種類の違うIDなど）は、消さずに元の文字列のまま持つ
  - フォームでは「（読めません）」と出し、外さなければ保存時に元のまま書き戻して通知する
  - 捨てると、開いて保存しただけで値が消えるため
  - 文字列・数値でない値（リストの中の `null` など）は読み飛ばす
- 選択肢に無い値（見つからないID、読めない値）も選択肢に足して選んだままにする（`missingLabel`）
- 入力の誤り（必須・刻み・日付・自分自身への依存）は保存しない
  - 期限日が開始日より前などは、保存したうえで知らせる
- 空欄の任意項目は、キーを消さずに空の値（4.4 の `emptyValue`）にする（`keepFrames`）
  - 作成時に用意した枠が、フォームで保存したときに消えないようにするため
- ステータスは旧名で書かれていても現在の名前で保存する（5.4）

タスクのフォームの担当者：

- 1人まで。プルダウンはエピックの担当者と同じ（`memberOptions`。在籍者と「なし」）
- `assignees` はリストのまま1件で書く（既存のノートを書き換えずに済み、SVN の差分を出さないため）
- 2人以上入ったノートは、開くときに1人目を残し、ほかは欄の下と保存時のお知らせで知らせる
  - 黙って外すと、担当者が減ったことに気づけないため
- `taskFormToUpdate` も2人以上を誤りにする（画面を通らない値の念のための確かめ）
- ビューは2人以上入ったノートも今までどおり読んで出す（直すまでの間も表示が崩れないように）

タスクのフォームの WBS 番号：

- 1以上の整数だけを受け付け、文字列で書く（4.1）
- プロジェクトかエピックを変えると、移った先の続きの番号に入れ替える（11.17。同じ番号が重ならないように）

エピックのフォーム：

- 項目：タイトル・プロジェクト・ステータス・担当者（`owner`、1人）・WBS番号
  - ほかに開始日・期限日・インプット・アウトプット
- 担当者のプルダウンは在籍者と「なし」。在籍していない人が入っていれば選択肢に残す
  - 開いて保存しただけで消えないように
- インプット・アウトプットは文字列のリスト。入力欄は複数行で1行に1つ。空の行は除く
- プロジェクトは、使われていれば変えられない（`epicFormToUpdate` の `fixedProject`）
  - 使われている：そのエピックのタスク（アーカイブ内も含む）か、マイルストーンの連動エピック
  - エピックだけ移すと、タスクの `project` と食い違って警告が出るため
  - タスクもまとめて書き換える案は、多くのファイルが変わり SVN でぶつかりやすいので採らない
  - 連動が無いエピックだけ、作り間違えの直しとして変えられる
  - プルダウンは押せなくして理由を添え、保存時にも確かめる

メンバーのフォーム：

- 項目：氏名・姓・名・1日の通常稼働時間・負荷許容率・在籍
- 氏名（`title`・`aliases`）・姓・名はそれぞれ入力し、どれも必須。作成画面も同じ（`nameErrors`）
  - 氏名は姓・名から作らない。表記（空白の有無など）を自由に決められるようにするため
  - 氏名の表示・リンク・並べ替えは今までどおり `title` を使う
- 姓・名の無い古いメンバーは自動で分けず、入力しなおしてもらう
  - 空白の無い名前や複数の空白で、分け方を誤らないため
  - 必須の項目にしたので、健全性チェックに出てフォームを開ける。入力するまでガントは氏名を出す
- 通常稼働時間は 0 より大きく 24 以下の 0.25 刻み。負荷許容率は 1 以上の整数
  - 100 未満は保存したうえで知らせる
- 空の項目は既定値（8・120・在籍）で開く。3.4 と同じ値なので、開いて保存しても計算は変わらない
- 数値は数値、在籍は true/false で書く。個人休日は 4.7 の編集画面で変える
- 開く場所：メンバー状況・ダッシュボードのメンバー名、メンバーのノートの右クリック、コマンド

プロジェクトのフォーム：

- 項目：簡易プロジェクト名・正式案件名・案件ID・ステータス（プロジェクト用）・開始日・期限日・責任者
- 簡易名・正式名・案件IDは必須（作成時と同じ）。案件IDは数字に見えても文字列で書く（4.1）
- 本文の表（マイルストーン・工数配分）は扱わず、表ごとの編集画面（4.7）で変える

部品：

- 値の読み取り・日付の確かめは `forms/formValues.ts`
- 入力欄の部品は `ui/formParts.ts`
  - 日付、時間（`hoursInput`。0.25刻み）、メンバー1人（`memberSetting`）、ステータス（`statusSetting`・`statusOptions`）
  - プロジェクト・エピックのプルダウン（`projectOptions`・`epicOptions`）、誤りの表示
  - タスク・エピックのフォームの並び（4.12）
- 保存して閉じる流れは `ui/formModal.ts` の `FormModal` にまとめる
  - 誤りの表示、二重送信の防止（4.6）、失敗・知らせることの通知、「キャンセル」「保存」のボタン
  - 継承するもの：4つのフォーム、表の編集画面（4.7）、チェックリストの編集画面（4.10）
  - 4つのフォームは `submitNote`、表・チェックリストの画面は `submit` で保存する（4.15）
  - 作業ログ入力（4.3）は「保存して続けて入力」があり流れが違うので継承しない
- 開く処理は `commands/editTask.ts` の `openTaskForm`・`openEpicForm`・`openProjectForm`・`openMemberForm`
  - ファイルかパスを受け取る。読み込み中・frontmatter が読めないときは通知して開かない
  - frontmatter は metadataCache でなくファイルから読む（4.15）
  - ノートの種類からフォームを選ぶ表（`FORMS`・`formOpenerOf`）は、コマンド・右クリック・警告一覧で共通

### 4.6 二重送信の防止

- 書き込む画面は、保存が終わるまで次の保存を受け付けない（`saving` の印）
  - 対象：作成・作業ログ・4つのフォーム・表の編集画面・チェックリストの編集画面
  - Enter の連打などで保存が2回走ると、ノートが2つできたり、ファイルの作成が失敗したりするため
- 入力の誤りで止まったとき・保存に失敗したときは印を戻し、直してもう一度押せるようにする

### 4.7 表の編集画面（`forms/projectTables.ts`, `holidayTable.ts`, `worklogTable.ts` ほか）

マイルストーン・工数配分・個人休日・作業ログの表を、画面で直す。

- 画面は `ui/tableEditModal.ts`、工数配分だけ `ui/allocationMatrixModal.ts`
- 書き出しは `write/markdownTable.ts`

開く場所：

- マイルストーン・工数配分：プロジェクト状況の見出しの横の「編集」（`commands/editProjectTables.ts`）
- 個人休日（`commands/editHolidays.ts`）
  - メンバー状況の「個人休日を編集」（メンバーを選ぶ）、メンバーのノートの右クリック
  - コマンド「個人休日を編集」（開いているのがメンバーのノートならその人、ほかは選ぶ）
- 作業ログ（`commands/editWorklog.ts`）：警告一覧の作業ログの表の警告、「作業ログを入力」の「（月）の記録を一覧で編集」

共通：

- 表の行を入力欄の一覧にし、変更・追加（「＋行を追加」）・削除してまとめて保存する
  - 1行ずつのフォームにしないのは、工数配分などは行が多く手間がかかるため
- 行はノートの本文から直接読む（索引ではなく）
  - 読めない行（日付の誤りなど）も一覧に出し、画面で直せるようにする
  - 中身の無い行は出さず、ノートにはそのまま残す
- 書き換えは 4.3 と同じく**変えた行だけ**。変えていない行は1文字も変えない
  - リンクにタイトルが無くても直さない
  - 消した行は除き、新しい行は日付（工数配分は月）の順の位置に入れる。CRLF を保つ
- 変えた行・新しい行のリンクは `[[ID\|タイトル]]`（要件 3.5）
  - 読めないリンクは消さずに元のまま書き戻して知らせる（4.5 と同じ）
- 列の順は表の見出し行に合わせ、決めていない列（自分で足した「メモ」など）の値は残す
- 開いたあとにノートの表が変わっていたら保存しない
  - ほかの人の SVN 更新などで行番号がずれ、別の行を書き換えるおそれがあるため
  - 開いたときの行（`readRows` が返す `snapshot`）と保存時の行を比べる（`applyTableEdits`）
  - 違えば「画面を開き直してください」と通知する
- 表が無ければ本文の末尾に作る。必要な列が足りない表は、開かずに知らせる
- 共通の処理：行を列名で読む（`readRows`）、リンクのセル（`linkCell`）、変えたか（`isChanged`）
  - `forms/tableRows.ts`。開く前の確かめ（`tableSource`・`usable`）は `commands/ready.ts`
  - セルの入力欄（`textCell`・`hoursCell`）とメンバーのプルダウン（`memberOptions`）は `ui/formParts.ts`
  - 書き出しの部品（`tableCell`・`tableLink`・`tableRow`・`emptyTable`）は 4.3・4.4 と共通

確かめ：

- マイルストーン：名前・日付が必須。連動エピックはこのプロジェクトのエピック（WBS順）から選ぶ
- 個人休日：日付が必須。同じ日付の行は最初の行だけが使われる（7章）ので、保存したうえで知らせる
- 中身の無い新しい行は捨てる

作業ログの表：

- 1ファイル（メンバー×月）の表を直す
  - 「作業ログを入力」のマス目ではメモを書けず、読めない行（日付の誤りなど）も直せないため
- タスクの欄は、押すとタスク名（とプロジェクト名）で探して選ぶ画面を開く（`ui/chooseModal.ts`）
  - `FuzzySuggestModal` を使う。個人休日のメンバーの選択と共通
  - 行ごとのプルダウンは、タスク数千件・行数十行で重く、画面も横に長くなるため
  - 選べるのはアーカイブ外のタスク。アーカイブ内のタスクの行はタイトルを出し、変えなければ残る
- 日付は対象月の中だけ（ファイルが月ごとのため。ほかの月は消して「作業ログを入力」で入れ直す）
- 予定・実績は空か0.25刻み。変えた行・新しい行は、予定か実績のどちらかが必須
  - 変えていない行は、両方空でも残す
- 同じ日付・タスクの行は集計で合算されるので、保存したうえで知らせる
- 時間は数値の形（`2.50` → `2.5`）で書く

工数配分のマス目（`forms/allocationMatrix.ts`）：

- 表の行の読み取り（`allocationRows`）は `forms/projectTables.ts`。マス目の値と変え方はすべて `allocationMatrix.ts`
  - マス目にする（`allocationMatrix`）・行の書き換えにする（`allocationMatrixEdits`）
  - 並べる月・メンバー（`allocationExtra`）、足せるメンバー（`memberCandidates`）
  - メンバー・月を足す・消す（`addMatrixMember`・`addMatrixMonth`・`removeMatrixMember`）
  - 消す前の確認の説明（`removedAllocationText`）、予定の超過（`overAllocated`）
- 画面（`ui/allocationMatrixModal.ts`）は描くことと、これらを呼ぶことだけをする

- 縦にメンバー・横に月。プロジェクト状況の配分表（11.8）と同じ向き
  - ノートの表の形は変えず、画面だけマス目にし、保存時に行の書き換えに直す
- 並べる月：表の行の月、プロジェクトの開始日〜期限日の月、作業ログに予定・実績のある月
- 並べるメンバー：表の行のメンバー、責任者、作業ログのある人（名前順）
- メンバー・月は表の中で足す（表の外に欄を置くより、足す場所が分かりやすいため）
  - メンバー：表のいちばん下の行のプルダウン（在籍者）。選んだらすぐ足す
  - 月：見出しの右端の月の欄。選んだらすぐ足す
  - 足したあとは、そのメンバー・月の最初の配分のマスに入る
- メンバーの行のごみ箱で、その人の配分をすべて消す
  - 消す前に確認画面（`ui/confirmModal.ts`）を出す。1回の押し間違いで数か月分の配分が消えるため
  - 確認には消す配分（月と時間）と、保存までノートは変わらないことを出す
- 書き換え
  - 変えていないマスの行は1文字も変えない。変えたマスは、その月・メンバーの1行目を書き換える
  - 新しいマスは行を足す（月の順の位置）。空にしたマスは行を消す。0 は「配分0」として残す
- 同じ月・メンバーの行が複数あれば、マスには合計を出す（`groupAllocationRows`。集計でも合計するため）
  - そのマスを変えたら1行にまとめ、保存したうえで知らせる
- 月かメンバーが読めない行はマス目の下に一覧で出し、消すことだけできる。消さなければ残る
- 見た目は表計算に寄せる（行・列をまたいで数字を入れやすくするため）
  - 月ごとに配分・予定・実績の3列。見出しは2段で、プロジェクト状況の配分表（9.4）と同じ形
  - 罫線で区切り、配分の入力欄は枠なしでマスいっぱいに置く。選んだマスはアクセント色の枠
- 配分の隣に、参考としてその月・メンバーの予定・実績を出す（配分を決めるときに見たいため）
  - このプロジェクトのタスクに付けた作業ログの合計。11.8 と同じ値。画面を開いた時点
  - どちらも0なら空。予定が配分を超えたら赤（入力のたびに描き直す）
- 合計の行・列は出さない（メンバーごとに単価が違い、時間の合計に意味がないため）
- キーでの移動（`forms/gridMove.ts`）
  - 矢印の上下・Enter（下）・Shift+Enter（上）で隣の配分のマスへ。端では止まる
  - 左右の矢印は、カーソルが文字の端にあるときだけ移る（マスの中の文字を直せるようにするため）
  - マスに入ると中身を選んだ状態にし、そのまま打てば上書きになる
  - 入力欄は `type=number` にしない（矢印キーで値が変わり、カーソル位置も読めないため）
  - 誤りは保存時の確かめで知らせる

### 4.8 表の自動整形と SVN の差分

- Obsidian のライブプレビューで表のセルを編集すると、表全体の列幅が空白でそろえ直される
  - 1行直すたびに表全体が差分になり、SVN のコンフリクトが起きやすい
- Obsidian にこの整形を止める設定は無い
  - 止めるには外部のプラグイン（Table Formatter など）を全員に入れる必要があり、使わない
- プラグインが同じ「列幅をそろえた形」で書く案も採らない
  - 長い値が1つ入るだけで、プラグインの書き込みでも表全体が変わるため
  - プラグインは詰めた形（`| a | b |`）で、変えた行だけを書き換える（4.3、4.7）
- **運用で避ける**：本文の表はプラグインの画面から変える（4.9）
- すでに整形された表も、編集画面は変えていない行を変えないので、そろえた空白はそのまま残る

### 4.9 ノートを直接編集させない

要件 4.2 の方針。

- 利用者が変える値（プロパティ・本文の表）は、すべてプラグインの画面で変えられるようにする
  - 画面なら値の確かめ（日付・0.25刻み・リンクの形）が効く
  - 書き込みは 4.1 のキー順・4.3 の「変えた行だけ」が守られ、書き方の誤りと SVN の差分を防げる
- プラグインの画面からはノートを開かない。クリックはフォームか表の編集画面を開く（9.1）
  - 開いたノートを直接書き換える入口を減らすため
- 開いてよいのは README と、警告一覧の直す画面の無い警告だけ（8章）
  - 壊れた frontmatter（SVN のコンフリクトの印など）はフォームで読めず、直す手段がほかに無いため
- Obsidian のファイル一覧・クイックスイッチャーからノートを開くことは止められない
  - Obsidian にノートを書き込み禁止にする仕組みが無いため
  - 使い方の README では直接編集を案内しない
- 画面
  - 入力補助フォーム（4.5）、表の編集画面（4.7）、作業ログ入力フォーム（4.3）
  - チェックリストの編集画面（4.10）、タスクの説明欄（4.11）、カンバンのカード移動
- まだ画面が無いもの
  - 作業ログのプロパティ（member・month。ファイル名が正なので計算には使わない）

### 4.10 チェックリストの編集画面（`forms/checklist.ts`, `ui/checklistModal.ts`, `commands/editChecklist.ts`）

- 編集は専用の画面にする（タスクのフォームには項目を表示するだけ。4.12）
  - フォームはプロパティ、この画面は本文と書き込む先が分かれ、どちらかだけ失敗することが無いため
  - フォームの「チェックリストを編集」は、フォームの入力を残したまま上に重ねて開く
- 開く場所：タスクのフォーム、タスクのノートの右クリック、コマンド「タスクのチェックリストを編集」
  - タスク一覧・WBS・プロジェクト状況の進捗の値からも開く（9.1）
- 出す項目は完了の割合で数えるものと同じ：`[ ]`・`[x]`・`[X]`
  - frontmatter とコードブロックの中、ほかの記号（`[-]` など）は出さず、そのまま残す
  - 入れ子の項目も出す（字下げは保つ）
- 書き換えは 4.7 と同じく**変えた行だけ**
  - チェックと内容だけを置き換え、行頭（字下げ・`-` や `1.`）は元のまま
  - `[X]` はチェックしたままなら `X` を保つ
  - 消した項目は行ごと除く（その下の入れ子の項目は残る）。CRLF を保つ
- 新しい項目は `- [ ] 内容` の形で、今の最後の項目の下（その下の字下げした行の後ろ）に足す
  - 最後の項目を消しても、その位置に足す
  - 項目が無ければ本文の末尾に、空行をはさんで足す（本文が frontmatter だけならはさまない）
  - 今ある項目の間には入れられないので、画面でも新しい項目は後ろにだけ並ぶ。並べ替えはできない
- 1項目は、チェックボックスと内容の入力欄を横に並べる（ノートのチェックリストと同じ形）
  - チェックボックスはノートと同じ見た目（`task-list-item-checkbox`）
  - 完了の項目は内容を薄く・取り消し線にする
- 入力欄で Enter を押すと、次の新しい項目を足してそこへ移る（続けて入れやすいように）
- 内容の無い新しい項目と、今ある項目の内容を空にしたものは誤りにして保存しない
  - 黙って捨てると、足したつもりの項目が消えて気づけないため。要らなければごみ箱で消す
- 開いたあとにチェックリストの行が変わっていたら保存しない（4.7 と同じ。行番号がずれるため）

### 4.11 タスクの説明（`forms/taskDescription.ts`, `ui/taskFormModal.ts`）

- 説明は、本文のうち frontmatter の次から最初のチェックリストの項目の前まで
  - チェックリストが無ければ本文全体。前後の空行と末尾の空白は除いて扱う
  - 項目の見分け方は 4.10 と同じ（コードブロックの中の項目は数えない）
- タスクの入力補助フォームの複数行の欄で読み書きする
  - フォームを開くときに本文を読む。チェックリストは今までどおり別の画面（4.10）
- 書き換えるのは説明の部分だけ。チェックリストとその後ろは1文字も変えない
  - 変えていなければ本文を書き換えない（SVN の差分を出さないため）
  - 説明とチェックリストの間は空行1つ。説明を空にすると、チェックリストを frontmatter のすぐ下にする
  - CRLF を保つ
- 説明に書けないもの（誤りにして保存しない）
  - チェックリストの行：書くと次からチェックリストになり、説明が途中で切れるため
  - 閉じていないコードブロック：後ろのチェックリストが数えられなくなるため
- 保存は本文を先に書き、次に frontmatter を書く
  - 開いたあとの変更の確かめは、プロパティと同じ仕組みで行う（4.15）

### 4.12 タスク・エピックのフォームの並び（`ui/taskFormModal.ts`, `ui/epicFormModal.ts` ほか）

- 見込みの日程の計算は `forms/taskSchedulePreview.ts`

- 見出しつきのまとまりに分け、まとまりごとに1〜3列で欄を並べる
  - 所属（3列）→ タイトル（見出しなし）→ 担当と状態（2列）→ 日程（2列）→ 説明・チェックリスト → 工数
  - まとまりは左右の列に分ける。縦にスクロールせずに全部の欄が見えるようにするため
    - 左：所属・タイトル・担当と状態・説明・チェックリスト。右：日程・工数（左右の高さをそろえる）
    - 窓の幅によらず、いつも2列にする（窓の幅で1列に戻すと、ふつうの画面でも1列になることがあったため）
  - 項目名は欄の上に置く。説明は欄の下に短く添える
  - 横に並べられるように、`Setting` の行ではなく自前の欄（`pm-form-field`）で組む
- 並べる部品は `ui/formParts.ts`（`formColumns`・`formSection`・`formField`・`dateInput`・`numberInput`）
- エピックのフォームも同じ形にする
  - 左：所属（プロジェクト・WBS番号）・タイトル・担当と状態。右：日程・インプット・アウトプット
  - プロジェクトを変えられないときは、理由を欄の下に出す（4.5）
- 日程の欄は、先行タスク（全幅）、開始日・期限日、当初開始日・当初終了日の順
  - 相対日数・所要日数の欄は出さない（要件 4.7）
  - 保存の変更内容に `lag_days`・`duration_days` を入れず、ファイルの値を残す
- 日程のまとまりの最後に、入力中の値での見込みの日程を出す（`previewTaskSchedule`）
  - 編集中のタスクをフォームの値で置き換え、`computeSchedules`（11.9）で計算する
  - 期限日を過ぎれば赤で知らせる。出せないときは「開始日か期限日を入れると計算します」と出す
  - 表示だけでファイルには書かない（要件 4.1「計算結果は保存しない」）
  - 当初終了日があれば、その下に当初との差を出す（11.18）。遅れていれば橙
- 期限日が休日（会社休日・土日）なら、欄の下に橙で注意を出す（`holidayDueNote`、`dateInput` の `calendar`）
  - タスク・エピック・プロジェクトのフォームで同じ。保存は止めない（休日の締め切りもあり得るため）
  - 個人休日は見ない。期限日はタスクの締め切りで、人の休みとは別のため
- 当初開始日・当初終了日は両方入れるか、両方空にする（片方だけ・逆順は誤り）
  - ガントの帯と当初との差が、いつも期間として扱えるようにするため
- チェックリストは、項目とチェックの状態を表示だけする（`renderChecklist`）
  - 編集は今までどおり別の画面（4.10）。フォームで編集すると、保存の流れが2つ混ざるため
  - 5件分の高さを超えたら、その欄の中だけスクロールする（フォームの高さを変えないため）
  - 編集画面で保存したら、書き換えた本文から項目を読み直して表示を出し直す（`ChecklistModal` の `onSaved`）
  - 日付・数の欄を変えるたびに、その表示だけを出し直す（描き直すと入力中の欄から外れるため）

### 4.13 失敗の知らせ方（`errors.ts`, `ui/notify.ts`）

- 書き込みなど Obsidian API の失敗は `try` / `catch` で受け、`notifyError(e, 文)` で知らせる
  - コンソールに `[project-manager]` 付きで記録し、Notice に文と誤りの内容を出す
  - 利用者が開発者ツールの赤い文を貼れば原因が分かり、画面でも何が起きたか分かるようにするため
- 文を渡さないときは誤りの内容だけを出す（誤りの文が利用者向けに書いてある処理。ノートの作成・共有設定）
- 誤りの文は `errorMessage` で取り出す。まとめた誤り（`AggregateError`）は中の文を重ねずに並べる
  - WBS の一括書き込み（9.7）で、どのファイルが失敗したかを出すため
- 例外：ビューの描画の失敗はビューの中に出す（`views/baseView.ts`）。ノート作成のプロパティの失敗は戻り値で返す

### 4.14 プロジェクトの複製（`commands/projectCopy.ts`, `commands/copyProject.ts`, `ui/copyProjectModal.ts`）

- ひな形は既存のプロジェクトにし、専用の保存形式は持たない
  - ひな形を直す画面を別に作らずに済み、今のフォームで直せるため
  - ひな形を集計から外す処理を、すべてのビューに入れずに済むため
- 作るノートの一式は純粋関数 `planProjectCopy` が決める。1件ずつは 4.4 の `planNewNote` を使う
  - 必須項目の確かめ・初期ステータス・空の枠を、ふつうの作成とそろえるため
- 一式の中で ID が重ならないよう、作った ID も「ある」として採番する
- 先行タスクをつなぎ直すため、タスクの ID を先に全部決めてから frontmatter を埋める
  - 元のプロジェクトの外の先行タスクは写さない
- `lag_days`・`duration_days` は写さない（日程の計算に使わないため。11.9）
- 日付をずらすのは稼働日で数える（`WorkCalendar`。11.2）
  - 土日をまたぐ間隔を保ち、ずらした日が休日にならないようにするため
  - 基準日より前の日付は、前日までの稼働日数だけ前にずらす
  - 休日の日付は、直前の稼働日と同じ位置になる
- 本文は frontmatter を除いて写し、チェックリストのチェックを外す（`copyBody`）
  - 判定は 4.10 の `checklistLines` と同じ。コードブロックの中は変えない
- プロジェクトの本文は、マイルストーンの表と空の工数配分の表
  - マイルストーンは日付が必須なので、日付を空にするときは写さない
- 作るのはプロジェクト → エピック → タスクの順。ファイルは1件ずつ作る（`createNoteFile`。4.4）
- 途中で失敗したら、画面を閉じて何件作ったかを知らせる（4.13）
  - 画面を開いたままだと、もう一度押されて同じものが二重にできるため
- 作ったノートは開かず、作った件数を通知する（4.4 と同じ）

### 4.15 開いたあとのノートの更新の確かめ（`forms/noteChanges.ts`, `write/noteFile.ts`, `ui/noteChangedModal.ts`）

- 対象は4つのフォーム（4.5）。プロパティとタスクの説明（4.11）を同じ仕組みで扱う
  - 共有フォルダや LiveSync では、フォームを開いている間にほかの人が同じノートを変えることがあるため
  - SVN 運用では効かない。ほかの人の変更は SVN 更新まで手元に届かないため
- 表・チェックリストの画面（4.7・4.10）は、今までどおり「変わっていたら止める」
  - 行ごとの差分の見せ方が要り、作りが大きくなるため
- カンバン・WBS の並べ替えは対象外。1項目だけを書き、ほかの項目を上書きしないため

項目と写し：

- ノートの値を「項目」の写し（`NoteItems`）で表す。プロパティはキーごと、説明は `description`
- 3つを比べる：開いたとき・今のノート（保存を押したときに読み直す）・フォームの値
- プロパティは metadataCache でなく、本文から読む（`getFrontMatterInfo` ＋ `parseYaml`）
  - metadataCache は書き込みより遅れることがあり、変わっていないのに更新ありと見えるため
  - 開くときも同じ読み方にする。読み方が違うと、値の形の違いで更新ありと見えるため
- 値の比べ方（`sameItemValue`）
  - 空（`undefined`・`null`・`''`・`[]`）どうしは同じ。キーの有無と空の枠（4.4）を区別しないため
  - 数値と数字の文字列は同じ。配列は順序つきで要素ごと
- フォームに無い項目（`lag_days` など）と、項目名の無い `type`・`aliases` は差分の表に出さない
  - `aliases` はタイトルと一緒に変わるため。書くときは対象にする

保存の流れ（`FormModal.submitNote`）：

1. 入力の誤りを確かめる
2. ノートを読み直し、差分を作る（`noteChanges`）
3. ノートで変わった項目が無ければ、フォームで変えた項目だけを書く（`editedItems`）
   - ノートで変わった項目がフォームと同じ値なら、変わっていないものとして扱う
4. あれば注意ダイアログを出す
5. 書く直前（`vault.process`・`processFrontMatter` の中）に、確かめた写しと同じかもう一度見る
   - 違えば書かずに 2 へ戻る（`NoteChangedError`）。3回続いたら止めて知らせる
6. 書く順序は説明 → プロパティ（4.11）

- 変えていない項目は書かない
  - ほかの人の変更を残すため。何も変えずに保存したときに差分を出さないため
- ノートに無いキーは、空の枠として足す（4.4 の `keepFrames` と同じ。`frameItems`）

注意ダイアログ：

- 見出しは「フォームを開いた時からノートに更新があります」
- 表の列：項目・開いたとき・今のノート・保存後（2つのボタンそれぞれ）
  - 「フォームの値」の列は置かない。保存しても書かれない値が、書かれるように見えるため
  - 今のノートから変わる値に印を付ける。両方で違う値に変えた項目には「両方で変更」の印
- ボタン
  - 変えた項目だけ上書き：フォームで変えた項目をフォームの値にし、ほかは今のノートの値を残す
  - フォームの内容ですべて保存：今のノートと違う項目をすべてフォームの値にする
  - 開き直す：フォームを閉じ、今のノートで開き直す（入力は捨てる）
  - フォームに戻る：ダイアログだけ閉じる（入力は残る）
- 値の文字は各フォームから渡す（`formatItemValue`）。リンクはタイトル、空は「なし」

## 5. 共有設定（`config/`）

### 5.1 ファイル

- `_pm/statuses.json`, `_pm/calendar.json`（フォルダはプラグイン設定で変えられる）。Vault API で読み書きする
- 書き出しはキー順・2スペースのインデント・末尾改行で固定する（SVN で余計な差分を出さないため）
- 休日は日付順に並べる

### 5.2 ファイルが無いとき

- 初期値（要件 3.6 のステータス、土日休み・休日なし）で動く
- ファイルは設定画面で保存したときに初めて作る
  - 起動時に作ると、SVN を更新していない人のファイルと、他の人のファイルがぶつかるため

### 5.3 ファイルが壊れているとき

- 使える部分だけ使い、壊れた部分は初期値で補う。ファイルは書き換えない
- 問題は `SharedConfig.problems` に入れ、警告一覧と設定画面の先頭に出す（保存すると上書きされるため）
- ファイルの作成・変更・削除・リネームを検知して読み直す（SVN 更新や他の人の保存に追従するため）
- 読み直したとき、ファイルの場所と中身が前回と同じなら何もしない（ビューも描き直さない）
  - 設定画面で保存すると、保存後の読み直しとファイルの監視で2回読み直すため
  - 自分の書き込みを印で見分ける方法は、印を消すタイミングが難しいので採らない
  - 保存後の読み直しは残す（保存の直後に設定画面を新しい値で描き直せるように）

### 5.4 ステータスの名前変更

- 旧名を `aliases` に残し、既存のノートは書き換えない（要件 3.6。SVN で大量のファイルが変わるのを避ける）
- 旧名のノートも新しい名前のステータスとして集計・表示する
  - ノートの値は、次にプラグインがそのノートを書くときに新しい名前になる
- 名前・旧名が他のステータスと重なる変更、空の名前、最後の1つの削除は受け付けない

### 5.5 設定変更の影響（`config/impact.ts`）

- 変更ごとに影響を「なし／通知／確認」に分ける（対応表は要件 4.12）
  - 確認は保存前に確認画面、通知は保存後に出す
- 影響するノートの件数は `UsageCounter` から得る
  - 索引ができる前は `NO_USAGE`（件数なし）を使い、説明だけを出す

### 5.6 保存の前の確かめ（`config/sharedConfig.ts`）

- 読むたびに、ファイルの中身をパスごとに覚える（`texts`。無ければ `null`）
- 書く直前（`vault.process` の中）に今の中身と比べ、違えば書かない
  - 読んだときにあったファイルが消えていたときも書かない
  - 画面の値は前回読んだ内容から作るので、そのまま書くとほかの人の変更を消すため
  - 共有フォルダではファイルの監視が遅れたり取りこぼしたりし、読み直しが間に合わないことがあるため
- 止めたら読み直して画面を描き直し、「もう一度変えてください」と知らせる
  - 差分のダイアログ（4.15）は出さない。設定画面は1回の操作ごとに保存し、やり直すのは1操作だけのため
- SVN 運用では効かない（ほかの人の変更は SVN 更新まで届かないため。4.15 と同じ）

## 6. プラグイン設定と個人の設定

設定の保存先は要件 4.12 の表のとおり。

全員共通の設定（`data.json`）：

- フォルダのパスと、種類（プロジェクト・エピック・タスク）ごとの色（`colors`）
  - `data.json` はプラグインフォルダごと SVN で配られるので、個人の好みは入れない
  - 色は全員で同じにしたい（HTMLレポートの色もそろう）ので共通にした
- 色は `#rrggbb`（小文字）だけを受け付け（`cleanColor`）、それ以外は初期の色にする
- 色を選んでいる間は何度も変わるので、`data.json` への保存は0.5秒待ってまとめる（`debounce`。`COLOR_SAVE_DELAY`）
- 画面には CSS 変数（`--pm-color-project` など。`ui/kindColors.ts`）として `body` に入れる
  - 別ウィンドウを開いたときにも入れ、プラグインを止めたら消す

全員共通の設定の保存と読み直し（`main.ts`、`settings.ts` の `mergeSettingsChanges`）：

- 前回 `data.json` から読んだ値（`savedSettings`）を持つ
- 保存の直前に読み直し、`savedSettings` から自分が変えた項目だけを今のファイルの値に重ねて書く
  - ファイルサーバーでは全員が同じ `data.json` を書くので、そのまま書くとほかの人の変更を消すため
  - 項目はフォルダ・種類の色はキーごと、ステータスの色は名前ごと。自分が消した名前は消す
  - 同じ項目を両方で変えたら自分の値にする
  - 共有設定（5.6）のように止めない。色を選ぶたびに保存するので、止めると操作がやり直しになるため
- ほかの人が変えたら `onExternalSettingsChange` で読み直し、同じ重ね方で今の設定に入れる
  - まだ保存していない自分の変更（色の保存待ち）は残す
- 入れたあと、色を当てはめ直してビューを描き直す
  - 共有設定のフォルダが変わったら読み直し、アーカイブのフォルダが変わったら索引を作り直す
  - 自分の変更による影響は、設定画面が先に反映している
- 設定画面は中の表を持っているので、入れ物はそのままで中身を入れ替える
- 読んでから書くまでの間にほかの人が書いた変更は消えうる。間が短いので受け入れる

ステータスの色（`statusColors`）：

- 全員共通の設定に、セット（タスク・エピック用／プロジェクト用）ごとに「名前 → 色」で持つ
  - `_pm/statuses.json` に持たせる案もあったが、種類の色と同じ `data.json` にした
- 選んでいないステータスは分類の色（`config/statusColor.ts` の `CATEGORY_COLORS`）
  - 未着手系＝灰、進行中系＝青、完了系＝緑、停止系＝橙
  - 何も選ばなくても見分けられ、分類を変えれば色もついてくる
- 名前で覚えるので、名前を変えたら色も付け替え（`renameStatusColor`）、削除したら消す
  - 旧名のノートは `findStatus` で今の名前にしてから色を探す
- 設定画面のステータスの行に、色を選ぶ欄と「分類の色に戻す」ボタン
- ステータス名は自由なので CSS 変数の名前にできない。描くときに要素へ `--pm-mark-color` を入れる
  - そのため色を変えたら開いているビューを描き直す（`redrawViews`。保存と一緒に0.5秒まとめる）

個人の設定：

- 項目：プロジェクトの表示名、プロジェクト状況の節の並び順と表示（9.4）、HTMLレポートの出力先
  - メンバーダッシュボードの部品の配置と、各部品の状態（`memberDashboard`。9.12）
  - 作業ログで前回選んだメンバー・表示の期間・完了・停止した担当タスクを出すか
  - 各ビューの状態（絞り込み・表示の切り替え。9.1）
- `app.saveLocalStorage` に保存する。この PC・この Vault だけに残り、ファイルサーバーや SVN で共有されない
  - 名前の前に Vault の ID（PC ごとに付く）が付く
  - 同じ Vault でも別のパス（ドライブ文字と `\\server\…`）で開くと別の Vault 扱いになり、初期値から始まる
- 以前 `data.json` に入れていた表示名は、個人の設定がまだ無いときに引き継ぐ
  - `data.json` は起動時には書き換えない（SVN 管理のファイルを全員の PC で書き換えないため）
  - 古い値は、誰かがフォルダや色の設定を保存したときに消える

その他：

- `minAppVersion` は 1.8.7
  - `getFileByPath`（1.5.7）、ビューの遅延読み込み（1.7.2）、`saveLocalStorage`（1.8.7）に合わせた
- フォルダのパスは `\` を `/` にそろえ、前後の `/` や空白を除く。空や `..` を含むパスは受け付けない

## 7. 本文の表の読み取り（`parse/`）

- 見出し（`##` など）の名前で表を探し、その見出しの直後の最初の表を読む
  - 次の同じか上位レベルの見出しまでに表が無ければ「表なし」
- 見出し名・列名は、全角括弧と空白の違いを無視して比べる。列は列名で見分け、並び順は問わない
- `\|` はセル区切りではなく文字の `|` として扱う（リンクの別名 `[[ID\|タイトル]]` のため）
- コードブロックの中の見出し・表は無視する
- 全セルが空の行は無視する。読めない行は読み飛ばし、行番号つきで problems に返す
- 必須の列が無い表は行を読まない
- リンクは `[[ID]]`・`[[ID|タイトル]]`・`[[フォルダ/ID]]`・ID そのものを受け付け、ID部分だけを使う
  - タイトルが古くても集計は変わらない
- 個人休日（`parsePersonalHolidays`）：列は日付・メモ。日付だけ必須
  - 同じ日付の2行目以降は読み飛ばす（印を出すだけなので、警告するほどではない）
  - 日付の形式違いは problems に入れ、健全性チェックに出す

## 8. 健全性チェック（`health/`）

警告一覧には次をまとめて出す。

| 出どころ | 内容 |
| --- | --- |
| 共有設定（5.3） | JSON として読めない、値の形式違い |
| ノートの読み取り（3.4） | frontmatter が読めない、type とファイル名の種類の違い、必須項目の欠落、値の形式違い、本文の表の問題 |
| 索引 | 同じIDのファイルが複数ある |
| `check.ts` | 存在しないノートへの参照、自分自身への依存、別プロジェクトのエピック、設定に無いステータス（旧名は問題にしない）、aliases がタイトル1つでない |
| `strayFiles.ts` | 管理フォルダの中の、ファイル名が ID の形でない Markdown ファイル |

- 参照先は、読めないノートでもファイルがあれば「ある」とみなす（そちらで別の警告が出るため）
- 警告一覧では、ノートを種類とタイトルで出す（`labels.ts`）
  - 作業ログは「メンバー名の作業ログ（月）」
  - 読めないノートは frontmatter の `title`、それも無ければファイル名

ID の形でないファイル（`strayFiles.ts`）：

- 対象は設定の「フォルダ」のうち共有設定（`_pm`）以外の6つと、その下のフォルダ
  - Vault の直下（`README.md` など）やほかのフォルダは見ない（利用者が自由にノートを置く場所のため）
- Markdown だけを見る（添付ファイルはノートと同じフォルダに置く設定のこともあるため）
- 索引には入れず、警告一覧を描くたびに Vault のファイルの一覧から探す（ファイル名を見るだけで速い）
- `VaultStore` は、管理フォルダでこの形のファイルが作られた・消えた・名前が変わったときも `updated` を出す

直す画面：

- 問題を作るところで、直せる画面を `NoteProblem.fix` に入れる
  - 値：`form`・`milestones`・`allocations`・`holidays`・`worklog`
  - メッセージの文字から後で推し量ると、文言を変えたときに壊れるため
- プロパティの問題は入力補助フォーム
  - 形式違い・必須項目の欠落・type の違い・存在しない参照・設定に無いステータス・aliases・循環
  - フォームは読めない値も消さずに持ち、保存で type・aliases も書き直すので、どれも直せる
- 本文の表の問題は、その表の編集画面（読めない行も元の文字のまま出すので、そこで直せる）
- 画面が無いもの
  - frontmatter が読めない（フォームも開けない）、同じ ID のファイル、ID の形でないファイル
  - 作業ログのプロパティ（member・month の食い違い）、作業ログの表が無い
  - 共有設定（設定画面で直す）
- 行は、`fix` があればその画面を開く
  - 無ければ最後の手段として、ノートを新しいタブで開く（問題の行があればその行。4.9）
- ファイルの見出しは、入力補助フォームのある種類ならフォームを開く。無ければ押せない

## 9. 画面

- **設定画面**：入力欄は `change` イベント（フォーカスが外れたとき・Enter）で確定する（1文字ごとに保存しない）
  - 保存後は描き直すが、スクロール位置を保存・復元する（`display()` は中身を作り直し先頭に戻るため）
- **確認画面**（`ui/confirmModal.ts`）：Promise で「実行／キャンセル」を返す。閉じたらキャンセル
- **入力フォーム**：入力の誤りはフォームの上に出し、フォームを閉じない
  - 選択肢が変わる操作（プロジェクトの選択など）の後は中身を描き直す
- **作業ログのフォーム**：追加か書き換えかを、タスクを選んだ時点で目立つ枠とボタンの文言で示す
  - 保存後は索引の更新を受けて「その日の記録」だけを描き直す（入力欄は触らない）
- **ビュー**：表示中に例外が起きたら、画面に内容を出す
  - メソッド名の注意は [OBSIDIAN_BEST_PRACTICES.md](OBSIDIAN_BEST_PRACTICES.md) 5章
  - ビューの種類の ID（`pm-gantt` など）は `views/viewTypes.ts` に集める
    - ほかのビューやメニューから開くときに、ビューのファイルどうしを読み込み合わないため
    - ID は保存された画面の配置が使うので、リリース後は変えない
- **リボン**：ボタンは2つ。↻ は再読み込み（要件 4.11）
  - かばんのボタンはメニューで主な操作を開く（ボタンを並べるとリボンが混むため）
  - メニューの並び（「／」は区切り線）
    - ノートの作成4種／作業ログの入力
    - ／ビュー・警告一覧
      - ビュー：ダッシュボード・タスク一覧・カンバン・WBS・ガントチャート・作業ログ
      - メンバー状況・メンバーダッシュボード・プロジェクト状況
    - ／HTMLレポートの書き出し・アーカイブ／使い方（README）・データの再読み込み

使い方のノート（`commands/readme.ts`）：

- 利用者向けの使い方は Vault の直下の `README.md` に置く
  - メニュー「使い方（README）」とコマンド「使い方を開く」で開く
- 正本はリポジトリの `docs/vault/README.md`（Vault はリポジトリと別管理のため）
- ファイル名が ID の形でないので、プラグインはノートとして読まない
- プラグインが作る（手でコピーすると Vault の README が古いまま残りやすいため）
  - ビルドの前に `scripts/readme-text.mjs` が正本を `src/generated/readmeText.ts`（文字列1つ）に変換する
  - main.js に入れる（esbuild の設定を変えずに済むため）
  - `npm run dev` の監視中は README を直しても変換し直さないので、dev を起動し直す
- 「使い方を開く」で、`README.md` が無ければ作り、中身がプラグインの版と違えば上書きしてから開く
  - 判定は `commands/readmeContent.ts`。改行コードの違いは見ない（SVN の取り出しで CRLF になっても書き直さない）
- 見出しの次に「プラグインが作るので直接書き換えない」注意書きを入れる（次に開くと元に戻るため）
- 古いプラグインの人が開くと古い中身に戻り、SVN の差分になる。全員のプラグインをそろえる運用が前提

設定画面：

- 並び：保存先で大きく2つに分け、その中を内容で分ける（誰に影響するかが一目で分かるように）
  - このパソコンだけの設定：表示（プロジェクトの表示名）／プロジェクト状況の節／HTMLレポート
  - 全員共通の設定：ステータス → 会社カレンダー → 種類ごとの色 → フォルダ
- グループ（`ui/settingGroups.ts`）：見出しを押すと開閉する枠（`<details>`）。中は左の線で入れ子を示す
  - 公式の `SettingGroup`（1.11〜）は入れ子と開閉ができず、対応バージョンも上げる必要があるため自作した
  - 初めは外側の2つだけ開く。描き直しても開閉は変わらない
  - 開閉は WBS と同じく「初期と逆にしたキー」で、ローカルストレージ（`project-manager:setting-groups`）に覚える
- ファイル：共有設定を変える欄（ステータス・会社カレンダー）は `ui/sharedConfigSettings.ts`
  - それ以外（個人の設定・色・フォルダ）は `ui/settingsTab.ts`（共有設定と個人設定で役割が違うため分けた）

### 9.1 ビューの土台（`views/baseView.ts` ほか）

描き直し：

- すべてのビューは `PmView` を継承し、`draw(el, ctx)` だけを書く
  - 索引・共有設定が変わったら描き直す。読み込み中・例外の表示・スクロール位置の保持は `PmView` が行う
  - タスク一覧・作業ログ・ガント・カンバン・WBS は、中身を部品（9.12）に置き、ビューは部品を1つ載せるだけ
- `ctx`（`calc/context.ts`）は作業ログの集計（11.1）・稼働日・プロジェクトの一覧・見込みの日程（11.9）
  - 開いているビューの数だけ作り直さないよう、変わるまで使い回す（11章の `ContextCache`）
- 見えていないビュー（裏のタブ・たたんだ横の欄）は、索引が変わっても描き直さず、見えたときに描く
  - 判定は `contentEl.isShown()`。`active-leaf-change`・`layout-change`・`onResize` で確かめる
  - 最初の1回は見えていなくても描く

絞り込み：

- 絞り込み（`calc/filter.ts`）はビューの状態（`getState`/`setState`）として Obsidian に保存する
  - 読むときは `field(state, 'キー')` で取り出し、各項目の読み取り関数（`parseFilter` など）で確かめる
  - 保存された値は古い版のものや壊れたものもあり得るため。読めない項目は初期値にする
  - タブを閉じるまで、再起動しても残る。保存先は `.obsidian/workspace.json`（svn:ignore の対象）

ビューの状態を各PCに覚える（`views/viewMemory.ts`）：

- ファイルサーバーでは `workspace.json` を全員で共有し、最後に保存した人の状態が全員に出るため
- 状態を変えたら `saveState()` で、`workspace.json` への保存と一緒にローカルストレージにも書く
  - 名前は `project-manager:view:ビューの種類`。ビューの種類ごとに1つ（同じ種類のタブは1つで足りるため）
  - `getState()` の結果をそのまま覚える
- `setState` は `PmView` だけが持ち、`resolveViewState` で当てはめる状態を決める
  - Obsidian が戻すとき（起動・別ウィンドウへの移動など）：このPCに覚えた状態があればそれを使う
  - プラグインが開いたとき（`openView` に state を渡す）：覚えた状態に渡した項目を重ね、覚え直す
    - 区別のため `openView` は状態に印（`OPENED_BY_PLUGIN`）を付ける。印は覚えない
  - 各ビューの項目は `readState` で読む
- まだ何も覚えていなければ、`workspace.json` の状態を使う
- 開いているタブの並びは Obsidian 本体が `workspace.json` に持つので、全員で共有のまま
- 判定は純粋関数（`filterTasks`, `filterProjects`）
  - クローズ済み＝ステータスが完了系のプロジェクト
  - 共通の絞り込みに期間は持たない。期間はビューごとに持つ（要件 4.1）
    - 保存された状態に期間があっても読まない。画面に出ないまま絞り込まないため
  - ステータスは旧名を現在の名前にそろえて比べる
- 部品（`views/filterBar.ts`）は、ビューごとに出す項目を選ぶ。複数選択は「×で外す・プルダウンで追加」

作成・編集の呼び出し（要件 4.2）：

- 各ビューのシェルの操作の欄に作成のボタン（`views/actions.ts`）を置く
- 1つに絞り込んでいるプロジェクト・エピックは、作成画面で最初から選んでおく（`NewNoteModal` の `initial`）
  - 選択肢に無いアーカイブ内のものは選ばない
- 編集は入力補助フォームなどの画面。ビューからはノートを開かない（4.9）
- 警告一覧は直すための画面なので、作成のボタンは置かない

| ビュー | 作成・入力 | 編集 |
| --- | --- | --- |
| タスク一覧 | 新しいタスク、作業ログを入力 | 行のクリック |
| メンバー状況 | 作業ログを入力、新しいメンバー | メンバー名のクリック |
| プロジェクト状況 | 新しいプロジェクト、「エピックとタスク」の見出しの横の新しいエピック・タスク（このプロジェクトを選んでおく）、エピックの行の「＋タスク」 | 「フォームで編集」（プロジェクト）、エピックのタイトル・タスクの行・マイルストーンの行・配分の数字のクリック |
| ダッシュボード | 作業ログを入力、新しいプロジェクト | メンバー名のクリック |
| カンバン | 新しいタスク（1つに決まっていれば選んでおく）、作業ログを入力 | カードのクリック |
| WBS | 新しいプロジェクト、プロジェクトの行の「＋エピック」、エピックの行の「＋タスク」 | エピックのタイトル・タスクの行のクリック |
| ガントチャート | プロジェクトの行の「＋エピック」、エピックの行の「＋タスク」（9.8） | エピック・タスクの表示名のクリック |
| メンバーダッシュボード | 作業ログを入力。部品の中は各ビューと同じ | 月の負荷のメンバー名、部品の中は各ビューと同じ |

シェル（`PmView.shell`）：

- どのビューも同じ並びの枠で描く。ビューは返された欄に中身を入れるだけで、置く場所を決めない
  - 見出し以外の欄は `shellParts`（`views/panel.ts`）で作る。部品を節として置くとき（9.12）も同じ
  - ビューごとにボタンの位置がばらつかないように。新しい機能も同じ場所に置ける
- 上に固定する欄（上から）
  1. 見出し：ビューの名前、一行の説明（`getDescription`）、右端に件数など（`summary`）
  2. 絞り込み（`filters`）：`renderFilterBar`、プロジェクト状況・アーカイブの操作とプロジェクトの選択
  3. 左に表示の設定（`settings`）、右に操作のボタン（`actions`）
     - 表示の設定：単位・グループ・すべて開く／閉じる・表示の切り替え
     - 操作のボタン：作成・入力・書き出し・ほかの画面へ
  4. 凡例・注意（`notes`）
- 中身の無い欄は出さない（CSS の `:empty`）。上の欄と本体の間に区切りの線を引く
- 「罫線を表示」は、表示の設定の後ろにある専用の欄に置く（並び順を CSS で入れ替えない）
  - `shell(el, { grid: true })` を渡したビューだけ。カンバン・警告一覧は表が無いので出さない
- 操作のボタン（`actionButtons`）は操作の欄にそのまま並べ、入れ物を重ねない
- 共通のクラス：節の見出しの行 `pm-section-head`、凡例 `pm-legend`、注意書き `pm-note`
- 節（`pm-section`）の中の見出しは、大きさを階層ごとに固定する（h3＞h4＞h5。値は UI_STYLE_GUIDE 12章）
  - Obsidian の見出しの大きさは親の文字の大きさに比例し、置き場所で同じ階層の大きさが変わったため
  - 見出しの行の中の h4 は余白を0にし、行の余白だけを使う（二重の余白とボタンとのずれを防ぐ）
- 入力欄の部品（プルダウン・期間・つまみ `rangeSlider`）は `views/filterBar.ts`、チェックは `ui/controls.ts`
- 表のビューは「上に固定する欄（シェル）」と「スクロールする欄（表）」に分ける
  - スクロールしても絞り込みと表の見出しが見えるように
  - 表の見出しはスクロールする欄の上端に、メンバー状況のメンバー名の列は左端に固定する
  - 描き直しでは、スクロールする欄の縦横の位置も保つ

数字と印（`calc/format.ts`：文字の組み立て。テストあり。`views/badges.ts`：画面の部品）：

- 時間は 3けた区切り、小数は2けたまで（`hoursText`。例：8,123.5）。表・説明・グラフ・HTMLレポートで使う
- 割合は `rateText`、タスク1件の進捗（完了／チェックリストの割合）は `subtaskText`
- タスク一覧・WBS・プロジェクト状況の進捗の値は、押すとチェックリストの編集画面（4.10）を開く
  - `subtaskCell`。動かすリンクで、行のクリックとは別に動く
- 進捗率は横棒と文字（`progressBar`。60px の棒の長さを `--pm-ratio` で渡す）
  - ダッシュボード・プロジェクト状況・WBS のプロジェクトとエピック・HTMLレポート
  - 表の中では、棒をセルの左端、文字を右端に置く。棒は縮めない（`flex: none`）
  - 文字の長さで棒の位置がずれ、狭い列で棒が縮んだため
  - 文字は％（`pm-progress-pct`。同じ幅の欄に右寄せ）と件数（`pm-progress-count`。左寄せ）に分ける
  - 行どうしで％と「（」の位置がそろう。HTMLレポートも同じ
- ステータスの枠（`statusBadge`。ビューからは `PmView.statusCell`）
  - 枠線と薄い背景はステータスの色（6章）、文字は通常の色
  - 付ける：タスク一覧・プロジェクト状況・WBS・ダッシュボード・HTMLレポート
  - 付けない：カンバンの列の見出し、文の中のステータス（マイルストーンの「エピックの状況」など）
  - 設定に無いステータスは枠を付けず、注意の色の文字
- 警告は種類ごとの小さな印（`warningBadges`）。名前と件数を必ず書く（色だけに頼らない）
  - 重いものから：期限超過＝赤、期限超過見込み・上位の期限超過見込み＝橙、工数超過＝黄、そのほか＝紫
  - タスクの行は件数なしの印（`taskWarningCell`）で、マウスを乗せると警告の文
- 種類の色の印（`kindMark`）：プロジェクト・エピック・タスクのタイトルの前に、設定の色の小さな丸
  - ダッシュボード・タスク一覧・カンバン・プロジェクト状況・WBS・ガント・アーカイブ・HTMLレポート
  - タイトルではない列（タスク一覧の「プロジェクト」列など）には付けない

休みの印（`holidayMark`・`dateCell`・`periodText`・`periodCells`）：

- 一覧の日付が休日なら、後ろに種類ごとの印を付け、マウスを乗せると理由を出す
  - 例：「会社休日：文化の日」「個人休日：佐藤（有給）」「土日休日：土曜」
  - 休日に置いた開始日は計算で次の稼働日にずれる（要件 4.7）ので、一覧で気づけるようにする
- 種類は社休＝橙・個休＝紫・土日＝灰。色だけに頼らず文字も変える。判定は `WorkCalendar.holidayMarks`（11.2）
- 個人休日はその行の人で見る（ID からメンバーを引くのは `calc/format.ts` の `membersOf`）
  - タスクは担当者（だれか1人でも休みなら付ける）、エピックは `owner`、プロジェクトは `manager`
  - マイルストーンの日付は人がいないので見ない
- 付ける場所：タスク一覧・プロジェクト状況・WBS・ダッシュボード・カンバンのカードの期限
  - 入力フォームの日付欄には付けない。メンバー状況にも付けない（9.3）
- 表の中の期間（ダッシュボード）は、開始日と「〜 期限日」を別のセルに分ける（`periodCells`）
  - 1つのセルだと、開始日の印の数で「〜」と期限日の位置が行ごとにずれるため
  - 見出しは2列ぶんの「期間」。間の罫線と余白は消して1つに見せる
  - 表でない場所（プロジェクト状況の概要）は `periodText` で1つの文字列にする

警告から直す場所への導線（`views/warningLink.ts`）：

- 警告の印をクリックすると、タスク一覧をそのプロジェクト（エピック）・警告ありのみで開く
  - 場所：ダッシュボードのプロジェクトの行、プロジェクト状況の概要とエピックの行、WBS のプロジェクト・エピックの行
  - クローズ済み・アーカイブ内のタスクも出す（警告の件数に入っているため）
  - タスク一覧のグループ・並べ替え・行のクリックの動きは残す
- 配分超過はタスクの警告ではないので、配分超過だけのときはプロジェクト状況へ動かす
  - プロジェクト状況の中では工数配分の表へ
- リンクは警告の印だけ（セルの余白を押しても動かない）。行のクリック（画面の移動）とは別に動く
- タスク一覧の件数はタスクの数なので、1つのタスクに警告が2つあると警告の件数より少なくなる

表の作り方：

- 見出しの行は `tableHeader`（`ui/table.ts`）で作る。数値の列は `numeric`、2列ぶんは `colspan`
  - 2段の見出し（プロジェクト状況の工数配分）だけは直接作る（`rowspan` を使うため）
- タスクの行は、列の定義（`TaskColumn`。`views/taskColumns.ts`）を並べた配列で描く
  - 1つの列が見出しとセルの作り方を持つ。見出しとセルの並びが食い違わないように
  - タスク一覧・WBS・プロジェクト状況で同じ列（`TASK_COLUMNS`）を使い、並びと見出しの文言だけ変える
  - 表ごとに違う列（タイトルの字下げ・WBS 番号・「＋工数」）は、その表で作る
  - 見込み開始日・終了日は、列ごとに `scheduleStartCell`・`scheduleEndCell`（`views/scheduleCells.ts`）
  - タスク一覧だけ、見積を超えた実績を赤にする（警告の列とは別に、数字で気づけるように）

表の見た目：

- 見出しはすべて中央にそろえる（`.pm-table th` と `th.is-numeric`）。HTMLレポートとガントの月の見出しも
  - はじめは一部の表だけ頼まれたが、同じ種類の表すべてに広がったので表全体の決まりにした
- 罫線：表の画面のマスの縦横に、うっすらした罫線を出す
  - 対象：タスク一覧・メンバー状況・プロジェクト状況・ダッシュボード・WBS・ガント・アーカイブ
  - 色は `--pm-grid-color`＝`rgba(var(--mono-rgb-100), 0.08)`（テーマの明暗に合わせて薄く見える）
  - 「罫線を表示」で消せる。ビューの状態（`gridLines`、初期は表示）で、「条件をクリア」でも変わらない
  - 消したときは行の区切りの線も出さない
  - ガントは行の横線と、期間の区切りの縦線。縦線は期間の数だけ行の後ろに置き、行ごとには作らない（数千行でも軽く）
  - プロジェクトの行の背景は、縦線が透けるよう半透明にする
- 開閉：WBS・ガント・プロジェクト状況の階層は、▶／▼ の印（`toggleMark`。`ui/controls.ts`）を押したときだけ開閉する
  - 行のほかの場所では開閉しない（タイトルや警告のリンクと押し間違えないように）
  - カンバンの列のたたみ（見出しのクリック）は階層ではないので別
- 色・余白・印・リンクの書き方は [UI_STYLE_GUIDE.md](UI_STYLE_GUIDE.md)。決めた理由：
  - 機能を足すたびに個別に決めてきたため、印が7通り、薄い背景の濃さが5通り、押せるものが5通り、赤が2種類に分かれていた
  - 押せるものは名前以外ふだん通常の色にした（表の数字やガントの表示名を青にすると画面が青くなりすぎる）
  - 点線の下線は見づらいので使わない
  - 赤は `--color-red` に1つ（`--text-error` はテーマで色味が違い、ガントの棒の赤と並ぶとずれて見える）

クリックで開く画面（`views/actions.ts` の `formClick`）：

- 行・タイトル・名前のクリックは、その項目の入力補助フォームか表の編集画面を開く（4.9）
  - タスク・エピック・メンバーはフォーム、マイルストーンの行・配分の数字は表の編集画面
  - 親の要素のクリックには伝えない（ダッシュボードの負荷率の行は、名前以外でメンバー状況を開くため）
- 横に「フォーム」ボタンは置かない（クリックと同じ動きになるため）
- アーカイブの画面の行は押せない（動かすファイルを確かめる画面のため）

ビューとノートを開く場所（`views/openView.ts`、`views/paneLeaf.ts`、`views/openNote.ts`）：

- 枠：中央のタブ（`iterateRootLeaves`）を並び順に見て、親（タブのまとまり）ごとにまとめたもの（`groupsInOrder`）
  - サイドバーと別ウィンドウは対象外
- ビュー（`openView`）：すでに開いていればその場所のまま表示する（動かした位置を尊重）。無ければ最初の枠に開く
  - 枠の中に空のタブがあればそれを使う
  - 無ければその枠で表示中のタブを（フォーカスを移さずに）アクティブにしてから `getLeaf('tab')` で作る
  - 特定のタブのまとまりにタブを足す公開 API が無いため
- ノート（`openNote`）：README と、警告一覧の直す画面の無い警告だけ。新しいタブで開く（作成は開かない。4.4）
  - 開く場所の設定は持たない（ビューから開かなくなり、選ぶほど使わないため）

### 9.2 タスク一覧（`views/taskListView.ts`, `views/taskListPanel.ts`）

- 計算は 11.6。ビューは表を描くだけ
- 見込みの日程のセル（`views/scheduleCells.ts`。プロジェクト状況・WBS でも使う）
  - 遅れでずれた開始日・終了日はそれぞれ橙（`startDelayed`・`endDelayed`。11.9）
  - 期限日より後の終了日は赤。両方に当たるときは赤にし、説明には両方の理由を出す
  - 完了系・停止系は期限日より後でも赤にしない（期限超過見込みと同じ）
  - 期限日のセル（`dueCell`）は期限超過なら赤にし、警告の文を説明に出す
- 絞り込みは共通の部品に、タスク一覧だけの項目（エピック・期限日の範囲・警告ありのみ）を足す
  - 共通：プロジェクト・担当者・ステータス・クローズ済み・アーカイブ
  - 「条件をクリア」は両方を消すが、グループ・並べ替えは残す
- タスク一覧だけの条件（`TaskListOptions`）も、ビューの状態として保存する
- 100行ずつ出し、「さらに表示」で100行ずつ増やす（要件 4.8）
  - 条件を変えたら100行に戻す。データの更新で描き直したときは、出している行数を保つ
  - 件数はタスクの数、残りは行の数（担当者でグループにすると1つのタスクが複数行になるため）
- 列の見出しをクリックすると並べ替え、もう一度で逆順
- 行のクリックで入力補助フォームを開く
- エピックの選択肢は、プロジェクトを絞り込んでいればその中だけ
  - プロジェクトが1つでなければ「プロジェクト名 / エピック名」と出す

### 9.3 メンバー状況（`views/memberStatusView.ts`, `ui/loadDetailModal.ts`）

- 計算は 11.7。行＝メンバー（名前順）、列＝期間
- 単位の初期値は週（初期の表示期間5か月で20列ほどになり、横に収まりやすいため）
- 「表示」で配分・予定・実績（初期は配分）、「数値」で負荷率(%)・工数(h)（初期は負荷率）を選ぶ
  - 配分を初期にするのは、負荷は工数配分を正として見るため（要件 4.5）
- セルは選んだ値を出し、段階で色を付ける（100%以下＝緑、注意＝橙、警告＝赤）
  - 工数(h)でも色は負荷率で付ける。時間で見ても負荷注意・負荷警告が分かるように
  - 基準工数が0の期間（休日だけの日）は「—」
  - 休日稼働があれば「休稼」の印（休日・個人休日の時間は負荷率に入れない。11.5）
  - その人の個人休日の日は基準工数0で「—」
  - 「休」だと一覧の休日の印（社休）と紛らわしいため「休稼」にした
  - 休稼の印は文字の行より低くする（`line-height`）。印の有無で行の高さを変えないため
  - 配分では休稼が出ないので、切り替えるたびに行の高さが変わっていた
- 休日の種類の印（9.1）は付けない。会社休日・土日は、日の単位なら列の見出しをグレーにする
- セルにマウスを乗せると配分・予定・実績と基準工数の時間（`loadHoursText`）を出す
- クリックするとプロジェクト別の配分・予定・実績の内訳を出す（`ui/loadDetailModal.ts`）
  - 配分と作業ログのどちらかがあるプロジェクトを、配分の多い順に並べる
- メンバー名のクリックでメンバーの入力補助フォーム（4.5）を開く（`formClick`）
  - ダッシュボードの負荷率のグラフのメンバー名も同じ
- 操作の欄に「個人休日を編集」（メンバーを選んで 4.7 の画面を開く。在籍者を先に並べる）
- 今日を含む期間の見出しは色を変える
- 横に長くなるので表は横にもスクロールでき、メンバー名の列は左に固定する（9.1）
- 表示期間・単位・表示（配分・予定・実績）・数値・在籍者のみも、ビューの状態として保存する
  - 「条件をクリア」は表示期間を初期値に戻し、プロジェクトの絞り込みを消し、在籍者のみを有効に戻す
  - 単位・表示・数値は残す

### 9.4 プロジェクト状況（`views/projectStatusView.ts`）

- 計算は 11.8。1つのプロジェクトを、上のプルダウンで選んで出す
  - 選んだプロジェクトはビューの状態として保存する。無ければ選択肢の先頭
- 一番上に概要。その下に4つの節：進捗グラフ（9.5）、マイルストーン、エピックとタスク、工数配分
  - 概要：表示名・簡易名・正式名称・案件ID・ステータス・期間・進捗率・工数・警告の種類ごとの件数
  - 4つの節の並び順と表示は個人の設定（`projectSections`。6章）。人によって見たい節が違うため
  - 設定画面の各行に ↑・↓ と表示のスイッチ、「初期の並びに戻す」。変えたら `redrawViews` で描き直す
  - 読むときは `cleanProjectSections` で整える。知らない節・重複は捨て、足りない節は末尾に表示ありで足す
  - 節が増えても、保存済みの並びのまま新しい節が出るようにするため
- 節の見出しの行（`pm-section-head`）に、その節だけのボタン・切り替えを置く
  - エピックとタスク：「新しいエピック」「新しいタスク」（どの節で作るかが分かるように）
- 操作の欄
  - 「フォームで編集」：表示中のプロジェクトのフォーム（4.5）。保存すると索引の更新で描き直す
  - 「タスク一覧で見る」：タスク一覧をこのプロジェクトで絞り込んで開く（クローズ済みも出す）
  - `openView` に状態を渡すと、開いているタスク一覧の絞り込みだけを書き換え、グループや並べ替えは残す
- マイルストーンの行をクリックすると、マイルストーンの編集画面（4.7）を開く
- マイルストーン・工数配分の見出しの横の「編集」は、その表の編集画面（4.7）を開く
  - 表が空でも出す（ここから最初の行を足すため）
- 概要の「見込みの期間」、エピックの行、開いたタスクの行に、見込み開始日・終了日を出す（9.2 と同じ印）

エピックの表：

- 担当者の列はエピックの担当者（`owner`）。件数は進捗の欄の「17%（2/12）」に出ている
- 「開始日」の列（`start`）を見込みの日程の後ろに置く
- 行の最後に「＋タスク」
- ▶／▼ を押すと、その下にタスクを WBS 番号順で開閉する（どれを開いているかは保存しない）
  - 並び（`wbsTaskRows`）・番号の列・行のドラッグは WBS と同じ（9.7）
  - 開閉は表全体を描き直さず、タスクの行だけを足す・消す（9.7 と同じ理由）
- エピックのタイトルとタスクの行のクリックで、入力補助フォームを開く
- タスクの行は担当者を出し、右端に「＋工数」（そのタスクを選んだ作業ログの入力。4.3）

工数配分の表：

- 「月ごとに配分・予定・実績の3列」。見出しが2段なので、この表だけ見出しを上に固定しない
- 配分の数字のクリックで、工数配分の編集画面（4.7）を開く

### 9.5 ダッシュボード（`views/dashboardView.ts`）

- 計算は 11.10。上から、プロジェクトの表、負荷率のグラフ、2週間以内のマイルストーン
- プロジェクトの行・マイルストーンの行は、プロジェクト状況をそのプロジェクトを選んで開く（`openView` に `project`）
- 絞り込みはプロジェクト・クローズ済み・アーカイブ。進捗率・割合・警告の件数の表示は `calc/format.ts`

メンバーの負荷率のグラフ（`views/loadChart.ts`。計算は 11.16）：

- 1行1人、在籍者全員。初期は名前順（いつも同じ位置に同じ人がいるように）
- 見出しの横のプルダウンで選ぶ（ビューの状態）
  - 並び順（`loadSort`）：名前順・負荷率の高い順・低い順
  - 期間（`loadPeriod`）：今週（初期）・来週・今月・来月。1人1本にして読みやすくし、先の忙しさも見られる

### 9.10 作業ログ（`views/worklogView.ts`, `views/worklogPanel.ts`）

作業ログ入力フォーム（4.3）の記録を、ガント（9.8）と同じ形で見るだけのビュー（要件 4.13）。

- 計算（行・列の幅）は 11.19。マス目の値・期間・行の階層はフォームと同じ `calc/worklogCells.ts`（4.3）
- 入力の処理は持たず、直すときはフォームを開く
  - 入力の処理を1か所にし、書き込みの経路（SVN の差分のもと）を増やさないため
- ガントの部品をそのまま使う：`div` の行、見出し（`ganttHeader`）、担当者の欄（`assigneeCell`）
  - 休日の帯・縦線・今日の線、`pm-gantt-*` の行のクラスと固定の欄も同じ
  - ガントと並べて見比べやすくするため
- 横軸は単位「日」の `ganttScale` に、1日の幅（`pxPerDay`）だけ差し替えて使う
- 担当者の右に「見積」と「合計」の欄（`pm-worklog-total`）を足し、左に固定する
  - `--pm-gantt-side` に見積と合計の幅を足し、縦線・帯・今日の線の位置を合わせる
- 日の中の値は横軸の上に `pm-worklog-cell` を置いて出す（位置と幅は `--pm-x`・`--pm-w`）
- 予定と実績の両方のときは見出しを3段（月・日・予／実）にする（`is-both`）
  - 予定は薄い文字にして実績と見分ける。合計の欄も中を2つに分ける
- 表示名の欄の幅は変えられない（初期 320px のまま。つまみはガントだけ）
- 担当者と合計の間に「見積(h)」の欄（`pm-worklog-estimate`）を足し、左に固定する
  - タスクの `estimate`（参考。薄い文字）。プロジェクト・エピック・日の合計の行は配下の合計
  - 人の行は空（見積はタスクごとのため）。幅は数字に合わせ、最小 56px
- タスク・人の行に、ガントと同じ当初期間の帯・見込みの日程の棒・開始日と期限日の線を描く
  - `planBand`・`ganttBar`・`startMark`・`dueMark` をそのまま使う。色・ツールチップもガントと同じ
  - 数字の後ろに置き、ガントの作業ログ表示と同じく薄くする（`opacity: 0.28`）
  - 数字（`pm-worklog-cell`）は指す対象にせず、後ろの棒のツールチップを出せるようにする

行：

- タスクの行は、記録した人が1人ならその人の値を出す。担当者の欄もその人
  - 担当者は1人まで（要件 3.5）なので、通常は1タスク1行で足りるため
- 2人以上なら、タスクの行は合計にし、下に人ごとの行（`pm-worklog-member`）を置いて開閉する
- プロジェクト・エピックの行と下の「日の合計」は配下の合計（薄い文字）
- 「日の合計」の行（`pm-worklog-sum`）は下に固定する。行が多くても日ごとの合計を見比べられるため
- タスク名・人の行を押すと、その人・そのタスク・表示中の期間で入力フォームを開く（4.3）
  - 2人以上のタスクの行は、人を決めずに開く
- タスク・人の行の日の欄を押すと、その日のマスに入ったフォームを開く（`dayLinks`）
  - 押した位置から日を求める（棒のツールチップを残すため、日ごとの部品は置かない）
  - 指した行は薄く塗る。プロジェクト・エピック・日の合計の行は押せない

表示の設定（ビューの状態）：

- 期間の単位（1週間・1か月）、表示する値、記録の無い担当タスクを出すか、たたんだ行
  - 記録の無い担当タスクに完了・停止も含めるか（`showFinished`。担当タスクを出すときだけ欄を出す）
- 絞り込みはほかのビューと同じバー。ステータスは複数選べる
- 表示中の期間は保存しない。開くたびに今日を含む期間にする（入力フォームと同じ）
- 呼び出し：リボンのメニュー、コマンド「作業ログを開く」

### 9.11 メンバーダッシュボード（`views/memberDashboardView.ts`, `views/memberPanels.ts`）

1人のメンバーの月の仕事を見るビュー（要件 4.14）。中身は部品（9.12）を並べるだけ。

- 表示の設定の欄に、メンバーの選択と月の移動（◀・月の選択・▶・今月）
  - 選んだメンバーと月はビューの状態（`memberDashboard`）。計算は 11.23
- 部品には「このメンバー・この月」（`PanelScope`）を渡す。どの部品もこれに固定して描く
- 部品（`memberPanels.ts` の `createMemberPanel`）
  - 月の負荷（`LoadPanel`）・アサインされている案件（`AssignedProjectsPanel`）：このビューだけの部品
  - タスク一覧（`MemberTaskListPanel`）：タスク一覧の部品に、出すタスク・月の予定と実績の列・注意書きを渡す
  - ガント・カンバン・WBS（`MonthTasksPanel`）：その月の担当タスクに固定して、各ビューの部品を包む
  - 作業ログ：作業ログの部品に、そのまま固定の条件を渡す
- 出すタスクは、タスク一覧・ガント・カンバン・WBS で同じ（`memberMonthTasks`。11.23）
  - 部品ごとに「その月」の意味が違うと、同じ画面の中で件数が食い違うため
- ガントは、初めて置いたときだけ単位を「日」にする（`initialMemberPanelState`）。1か月を見るため
- 「部品を選ぶ」（`ui/memberPanelsModal.ts`）：見せ方・並び順・表示を選ぶ。変えるたびに描き直す
  - 並び替えはプロジェクト状況の節と同じ `moveSection`
- 見せ方
  - 縦並び（`stack`。初期）：表示する部品を上から順に節として置く
  - タブ（`tabs`）：部品名のタブ（`pm-panel-tab`）を並べ、選んだ部品だけを描く。選んだタブも保存する
    - ガントのように横に長い部品は、縦に並べると見づらいため
- 呼び出し：リボンのメニュー、コマンド「メンバーダッシュボードを開く」

### 9.12 ビューの部品（`views/panel.ts`）

ビューの中身を、置き場所（タブかメンバーダッシュボード）から切り離したもの。

- 部品（`Panel`）が持つもの：絞り込み・表示の設定（状態）、`draw(shell, ctx, scope?)`、`getState`・`setState`
  - 状態の保存と描き直しは置き場所（`PanelHost`）に頼む
    - `changed`：保存して描き直す。`save`：保存だけ（開閉・幅のドラッグ）。`redraw`：描き直すだけ
    - `gridLines`：置き場所の「罫線を表示」
  - 同じ部品を、単独のビューにもメンバーダッシュボードにも載せられるようにするため
- 単独のビュー（`PmView`）は `panelHost()` を渡して部品を1つ作る
  - 部品の状態は、これまでと同じキー（`filter`・`taskList` など）でビューの状態に入れる
    - 保存された画面の配置を、そのまま読めるようにするため
- 固定の条件（`PanelScope`）を渡されたとき
  - 担当者をその人にする。絞り込みの「担当者（メンバー）」は出さない
  - `taskIds` があれば、出すタスクをその中だけにする（WBS・ガントは `wbsTreeFor` の `only`。11.12）
  - 期間はその月。作業ログの期間の切り替え、ガントの表示期間・「プロジェクトの期間に合わせる」は出さない
  - `taskColumns`（タスク一覧に足す列。並べ替えはしない）、`note`（注意書き）
- 部品を節として置くときは `panelShell`。見出しは h4、中身は `pm-panel-body`（横にだけスクロール）
- メンバーダッシュボードの部品の状態と配置は、個人の設定（`memberDashboard`。6章）
  - 型・既定値・読み取りは `memberDashboardLayout.ts`（テストあり）
  - 知らない部品・重複は捨て、足りない部品は末尾に表示ありで足す（部品を増やしても前の配置を読める）
  - ダッシュボードの中の設定は、単独のビューの設定と別に持つ（自分用の見方を、ふだんのビューに持ち込まないため）
- `ctx.today` などの計算用のデータは置き場所が作って渡す（9.1）

## 11. 計算（`calc/`）

- 計算結果はファイルにも索引にも保存せず、表示のたびに計算する（要件 3.7）
- 日付はすべて `YYYY-MM-DD` の文字列で扱い、計算の中だけ UTC の時刻に直す（タイムゾーンでずれないため）
- 「今日」は呼び出し側が渡す（`localToday()`。テストで日付を固定できるように）
- 計算用のデータ（`CalcContext`：日程・作業ログの集計など）は `ContextCache`（`context.ts`）で使い回す
  - 索引・共有設定・今日が変わるまで。開いているビューがそれぞれ同じ計算をしないため
  - 索引の変化は `VaultIndex.version`（追加・削除のたびに増える番号）で見る
  - 共有設定の変化は `statuses`・`calendar` のオブジェクトが入れ替わったかで見る（`load` で必ず新しくなる）
- `CalcContext` には、何度も引くものを作るときに1回だけ用意する
  - ID からエピック・メンバーを引く表、プロジェクトごとのタスクとエピック（`byProject`）
  - プロジェクトごとに全タスクを見直すと、プロジェクト数×タスク数の手間になるため
- タスクの警告は `warningsOf` で引く。同じ `CalcContext` の中では1回だけ計算する
  - プロジェクト全体・エピックの行・タスクの行で同じタスクの警告を使うため
  - 返す配列は使い回すので `readonly`
- 並べ替えの文字の比較は `compare.ts` を使う
  - `compareJa`（氏名・タイトル）、`compareNumeric`（数字を数として比べる。プロジェクト名・WBS番号）
  - `localeCompare` に言語を渡すと比較のたびに比較器を作り、数千件で遅くなるため
  - 日付・パスの比較は言語に関係ないのでそのまま

### 11.1 作業ログの集計（`worklogSummary.ts`）

- `WorkSummary` は作業ログ全体を一度だけ読み、予定・実績を合計する
  - タスク別、メンバー×日付×プロジェクト別、プロジェクト×月×メンバー別
- 同じ日付・同じタスクの行は合算する（要件 3.5）
- 予定・実績の足し算は `addHours`・`addHoursTo`。ほかの計算（`calc/`）も日別・タスク別の合計に使う
- 記録のプロジェクトは、タスクの所属（`task.project`）で決める
  - タスクが見つからない記録は「所属不明」（`UNKNOWN_PROJECT`）として、メンバーの負荷には入れる
- タスクの所属を引くため、アーカイブ内のタスクも含めて渡す

### 11.2 稼働日と期間（`workdays.ts`, `dates.ts`）

- 稼働日：土日（設定で休日にしているとき）と会社の休日以外。個人休日は入れない（要件 3.6）
  - 日程の計算は稼働日で数える。担当者で日程が変わると分かりにくいため
- 勤務日（`dutyDayOf`）：稼働日のうち、そのメンバーの個人休日でない日。負荷の計算だけに使う（要件 4.5）
  - 個人休日が無い人は稼働日と同じ。ある人は日付の集合を作って引く
  - `countDays`：条件に合う日の数（勤務日の数など）
- 休日の印の判定（`holidayMarks(date, members)`）：その日の休日を種類（会社・個人・土日）の順に返す
  - 個人休日は渡したメンバーの休みをまとめて1つにし、理由は「佐藤（有給）、伊藤」のように名前とメモ
- 期間は日・週（月曜始まり）・月。識別子は、日・週は開始日、月は `YYYY-MM`
- メンバー状況の表示期間の初期値は、前月の初日〜3か月先の末日（要件 4.8）

### 11.3 進捗率と工数の状況（`progress.ts`）

- タスク：完了系なら完了。サブタスクの完了割合は参考として別に返す（要件 4.3）
- エピック・プロジェクト：完了系の件数 ÷ 対象件数。停止系は分母から除く
  - 設定に無いステータスは未完了として分母に入れる（要件 4.8）。対象が0件なら進捗率なし
- ステータスは名前ではなく分類で判定する（旧名も分類に引き当てる。5.4）
- 見積・予定・実績の合計は、停止系のタスクも含めて数える

### 11.4 警告（`warnings.ts`）

- 期限超過：期限日の翌日以降で、完了系でも停止系でもない（要件 4.4, 4.8）
  - 停止系は進捗率の分母から外すのと同じ考え方。設定に無いステータスは対象にする
- 工数超過：実績の合計が見積を超えている（見積が無いタスクは対象外）
- 配分超過：工数配分表の行（プロジェクト×月×メンバー）ごとに、予定の合計が配分を超えている
  - 配分表に無いメンバーの予定は対象外
- 負荷注意・負荷警告：`warnings.ts` では作らない。表示中の値の負荷率の段階（`loadLevel`。11.5）で色と印を出す
- 休日稼働：`warnings.ts` では作らない。勤務日でない日の時間（`MemberLoad.holiday`。11.5）で「休稼」の印を出す
  - 負荷と同じ期間・同じ値で判定しないと、印と表の数字が食い違うため
- 期限超過見込み：見込み終了日が期限日より後（11.9）
- 上位の期限超過見込み（`groupWarnings`）：配下のタスクの見込み終了日が、エピック・プロジェクトの期限日より後
  - まとまりごとに1件。文にはいちばん遅いタスクを出す（件数を増やしすぎないため）
  - 完了系・停止系のタスクは見ない（タスクの期限超過見込みと同じ）
  - 完了系のエピック・クローズ済みのプロジェクトには出さない
  - プロジェクト状況（11.8）で、エピックの行とプロジェクト全体の警告に足す
  - 直す場所はエピック・プロジェクトのフォームなので、印は押せない。指すと文を出す（`warningLink`）
- 警告は対象（タスク、エピック、プロジェクト、プロジェクト×月×メンバー）を持ち、ビューで対象の行やセルに出す

### 11.5 負荷（`load.ts`）

- 基準工数（100%）＝ 期間内の勤務日数（11.2）× 1日の通常稼働時間
  - 個人休日を引くのは、休みのある週が空いて見え、突発の案件を振るときに誤らないため
  - 休日だけの期間（休日の「日」）は基準工数0で、負荷率なし
- 配分負荷率は、期間内の配分（11.22）÷ 基準工数
- 予定負荷率・実績稼働率は、勤務日の予定・実績だけで計算する
  - 休日・個人休日の記録は負荷率に入れず、休日稼働として別に示す（要件 4.5）
- 段階：100%以下（normal）、100%超（caution＝負荷注意）、負荷許容率超（warning＝負荷警告）
- プロジェクト別の内訳は、勤務日とそれ以外の両方を合計する（セルをクリックしたときの内訳。要件 4.8）
  - 配分のプロジェクト別は `allocatedByProject` に別に持つ
- `loadValue`：表示中の元（`LoadMode`：配分・予定・実績）の時間・負荷率・段階・休日の時間
  - 画面の色・印・並べ替えはすべてこれを通す。どの値でも同じ判定にするため（要件 4.5）
- `loadHoursText`：配分・予定・実績・基準の時間を1行にした説明（マウスを乗せたとき）

### 11.6 タスク一覧（`taskList.ts`）

- `taskRows` がタスクごとに所属・現在のステータス名・担当者・工数・進捗・警告をまとめる
  - 絞り込み（`filterTaskRows`）→並べ替え（`sortTaskRows`）→グループ分け（`groupTaskRows`）の順に通す
- 期限日の範囲を指定したときは、期限日の無いタスクは対象外
- 並べ替え
  - 値の無いもの（期限日・見積・エピックなど）は昇順・降順どちらでも最後。同じ値ならタイトル順
  - ステータスは設定の並び順、エピックは「WBS タイトル」を数字として比べる（1.2 → 1.10）
  - 進捗は完了＝1、それ以外はサブタスクの完了割合（無ければ0）
- グループ
  - 名前順で、「（エピックなし）」「（担当者なし）」「（見つからない…）」は最後。ステータスは設定の並び順
  - 担当者が複数のタスクは、それぞれの担当者のグループに出す（抱えている仕事を見るため）
- 見つからない担当者（メンバーノートが無いID）は担当者の列に出さない（健全性チェックで警告済み）
- 当初差（`planDelay`。11.18）の列は遅れの日数で並べる。遅れていれば橙の文字

### 11.7 メンバー状況（`memberStatus.ts`）

- `memberStatusTable` がメンバー×期間ごとに `memberLoad`（11.5）を呼ぶ
  - 期間の端は範囲からはみ出してよい（表示期間の途中から始まる週も1週として数える）
- 表示期間は、指定が無ければ前月〜3か月先（11.2）。逆転していれば入れ替える
- プロジェクトで絞り込んだときの「関わるメンバー」（要件 4.8）。アーカイブ内のタスクも含める
  - そのプロジェクトのタスクの担当者、工数配分表のメンバー、責任者（`manager`）
  - そのプロジェクトのタスクに作業ログを付けた人
- 負荷率は、絞り込んだプロジェクトの分だけでなく、そのメンバーの全プロジェクトの合計で出す（配分も同じ）
  - 負荷はメンバー全体で見るもののため

### 11.8 プロジェクト状況（`projectStatus.ts`）

- 対象はそのプロジェクトのエピック・タスク（アーカイブ内も含む。アーカイブしたプロジェクトも見られるように）
- 全体・エピックごとに、進捗率（11.3）、工数の合計、警告をまとめる。全体の警告はタスクの警告と配分超過
- エピックは WBS 順（数字として比べる。WBS の無いエピックは後ろ、同じならタイトル順）
  - エピックの無いタスク（エピックが見つからないものも）は最後に「エピックなし」としてまとめる
- マイルストーンは日付順。連動エピックについて次を出す
  - 遅れ：期限日がマイルストーンの日付より後
  - 未達：マイルストーンの日付を過ぎたのにエピックが完了系でない
  - 警告（11.4）には数えず、マイルストーン一覧の注意として出すだけ
  - 注意の文（`notes`）もここで作る。連動エピックが見つからないときも注意に出す
    - プロジェクト状況・ダッシュボード・HTMLレポートで同じ文を出すため
    - ガントの ◆ の説明はマウスを乗せたときの文なので、言い回しを変えて別に作る（9.8）
- 配分表：配分表の行と、作業ログにこのプロジェクトの予定・実績がある月×メンバーを合わせて表にする
  - 配分の無い予定も見えるように。同じ月・メンバーの配分行が複数あれば合計する

### 11.9 日程（`schedule.ts`）

- 決まりは要件 4.7「日程計算の細かい決まり」
- `computeSchedules` が全タスクの見込み開始日・終了日を出し、`CalcContext.schedule` に入れる
  - ファイルにも索引にも保存しない
- 1件ずつ、自分の開始日・期限日だけで計算する。先行タスク・所要日数は見ない
  - 先行から自動でずらすと、入れた開始日と出る日程が食い違って分かりにくいため
- 稼働日の数え方は `WorkCalendar.addWorkdays`（n 稼働日進める。0 ならそのまま）と `workdayOnOrAfter`
  - 休日なら次／前の稼働日。休日ばかりのカレンダーで止まらないよう、探すのは10年分まで
- `lag_days`・`duration_days` は読まない（索引の `Task` にも持たない）
  - 期限日があれば作業量は見積工数で足り、日数を二重に入れると食い違うため
- 遅れ
  - 未着手（分類 not_started）で開始日が今日より前なら、開始日を今日（休日なら次の稼働日）にずらす
  - 完了系でないタスクの終了日が今日より前なら、今日まで延ばす
- 遅れの印は開始日・終了日で別々に持つ
  - `startDelayed`：未着手のまま開始日を過ぎたので、今日にずらした
  - `endDelayed`：今日まで延ばした、または開始日のずれが終了日に伝わった（終了日＝開始日のとき）
  - 期限日が終了日のときは、開始日のずれは伝わらない
- 設定に無いステータスのタスクは、開始日をずらさないが、終了日は今日まで延ばす（完了系ではないため）
- 循環（`findCycles`、Tarjan の強連結成分）は日程には影響しない
  - 健全性チェックで、循環に入るタスクごとに経路つきで警告する（自分自身への依存は従来の警告のみ）
- 期限超過見込み（`taskWarnings` の `schedule`）：見込み終了日が期限日より後で、完了系・停止系でない
  - 期限日を過ぎていれば期限超過だけを出す

### 11.10 ダッシュボード（`dashboard.ts`）

- プロジェクトごとに `projectStatus`（11.8）を呼ぶ。対象はビューの絞り込み（既定はクローズ済み・アーカイブ内を除く）
- メンバーの負荷（HTMLレポート用）：負荷を見るメンバー全員の今週・今月・来月の `memberLoad`。名前順
  - 今週は月曜始まりで今日を含む週。日曜に開くと前日までの週になる
- マイルストーン：表示するプロジェクトの、今日〜14日後のもの

### 11.11 カンバン（`kanban.ts`）

- `kanbanColumns` が、タスク一覧と同じ行（11.6）をステータスの列に分ける。旧名は現在の名前の列に入る
- タスクの無い列も出す（ステータスの流れ全体を見せるため）
- 設定に無いステータスのタスクは、最後の「設定に無いステータス」の列にまとめる（あるときだけ）
- カードを動かしたときに書く値（`statusMove`）：動かした先の列のステータス名
  - 今の列は旧名を現在の名前にそろえて比べるので、旧名のタスクを同じ列に落としても書き換えない
  - 「設定に無いステータス」の列から設定のある列へは動かせる（直すため）が、逆はできない

### 11.12 WBS（`wbs.ts`）

- プロジェクトごとに `projectStatus`（11.8）のエピックの行を使う（WBS順、エピックなしは最後）
- タスクは WBS 番号順。番号の無いものは後ろに、見込み開始日の順（日程なしは最後。11.17）
- 担当者・ステータスで絞り込んだときは、合うタスクだけを出し、合うタスクの無いエピックは出さない
  - 進捗・見積・期間・警告は、エピック・プロジェクト全体の値のまま（絞り込みで変わると誤解しやすいため）
- WBS とガントで共通：絞り込みからの階層（`wbsTreeFor`）、開閉の状態
  - `wbsTreeFor` の `only` を渡すと、そのタスクだけを出し、出すタスクの無いプロジェクトも出さない（9.12）
  - 開閉は、初期と逆にした行のキーの集合（`isOpen`・`toggledForAll`・`parseToggled`）
  - ビューはこれを `TreeToggle`（`treeToggle.ts`）で使う。変えたら保存を頼む関数を渡す
  - プロジェクト状況も同じキーで使う（保存しないので関数を渡さない）

### 11.13 ガントチャート（`gantt.ts`）

- 横軸（`ganttScale`）は表示期間を期間の区切りまで広げる（週なら月曜〜日曜、月なら月初〜月末）
  - 1日の幅は日 28px・週 8px・月 3px
- 表示名の欄の幅（`ganttLabelWidthOf`）は 160〜800px。数でなければ初期値 320px、範囲の外は端にそろえる
- 棒（`barBox`）は開始日の左端から終了日の右端まで（両端を含む）
  - 範囲からはみ出した側は切り、重ならなければ出さない。印（`markX`）はその日の中央
- 表示期間はメンバー状況と同じ `displayRange`（初期値は前月〜3か月先。11.7）
- 依存（`dependencyLinks`）：先行は `depends_on`、後続はそのタスクを `depends_on` に持つタスク
  - アーカイブ内のタスクも含めて探す
- 依存の有無（`dependencyFlags`）：全タスクを1回見て、先行があるか・後続があるかを出す
  - 見つからない先行と自分自身への依存は数えない（線を引けないため）

### 11.14 アーカイブの移動の計画（`archive.ts`）

- 対象：プロジェクトのノートと、`project` がそのプロジェクトのエピック・タスク
  - 作業ログは複数のプロジェクトにまたがるので対象にしない
- アーカイブ（`archivePlan`）：移動先は、アーカイブフォルダの下に今のパスをそのまま付けた場所
  - 例：`Tasks/TASK-….md` → `Archive/Tasks/TASK-….md`
  - フォルダ・ファイル名に意味は無い（要件 3.1）が、元の場所が分かるようにそろえる
  - すでにアーカイブフォルダにあるものは数だけ出す（`alreadyDone`）
- 戻す（`restorePlan`）：アーカイブフォルダの中にあるものを、アーカイブフォルダの部分を取った場所へ
  - アーカイブの移動の逆なので、元の場所に戻る。アーカイブの外にあるものは数だけ出す
- 移動先に同じパスのノートがあるものは `clash` にし、動かさない（上書きしないため）
- 注意：エピック・タスクのステータスが完了系・停止系でない（アーカイブのときだけ）、移動先に同じ名前がある
  - 注意があっても一覧には出す（移動するかは人が決める）
- アーカイブできるプロジェクト（`archivableProjects`）
  - ステータスが完了系（クローズ済み）で、アーカイブフォルダの外にファイルが残っているもの
  - 停止系（失注・中止など）は対象にしない（要件 4.9 はクローズ済みのみ）
- 戻せるプロジェクト（`restorableProjects`）：アーカイブフォルダの中にファイルがあるもの。ステータスは問わない
- 並びはプロジェクト → エピック → タスク、同じ種類はパス順

### 11.15 工数の累積（`burnup.ts`）

- 対象はプロジェクトのタスク（アーカイブ内も含む）に付いた作業ログの行
  - 日ごとに予定・実績を足し、期間の毎日の累積を出す
- 期間は次を合わせた範囲（どこから始まりどこで終わるかを全部見せるため）。どれも無ければグラフなし
  - プロジェクトの開始日・期限日、作業ログの最初〜最後の日、タスクの見込みの日程の最初〜最後
- 実績の累積は今日まで（実績の線を今日で止めるため）。予定の累積は期間の終わりまで
- 見積の合計はタスクの見積の合計（11.3 と同じ値）
- 縦軸の目盛り（`niceTicks`）は 1・2・2.5・5 ×10ⁿ の刻みで5本ほど。横軸（`monthTicks`）は各月の1日
- 見込みの進捗（`progressPlan`）：毎日、見込み終了日（11.9）がその日以前のタスクの数を数える
  - 分母と完了の数え方は進捗率（11.3）と同じ（停止系を除く）
  - 見込みの日程は遅れを反映しているので、遅れている未完了のタスクは「今日までに終わるはず」に入る
  - それが実績の点との差になって見える
  - 日程を計算できないタスクは線に入れず、件数を返す

### 11.16 メンバーの負荷率のグラフ（`loadChart.ts`）

- `loadChart` が、選んだ期間について、メンバーごとに `memberLoad`（11.5）を呼ぶ
  - 期間（`loadChartPeriod`）：今週・来週は月曜始まりの週、今月・来月は月
  - 選んだ並び順（`sortLoadRows`）に並べる。段階の判定も 11.5 のまま
- 並べ替え：名前順、負荷率の高い順・低い順。負荷率は選んだ値（配分・予定・実績）のもの
  - 負荷率の無い人（期間に稼働日が無い）はどちらの向きでも最後。同じ負荷率なら名前順
- `chartPoint`：横軸の単位での棒の長さ・その人の 100%・負荷許容率の位置
  - 負荷率では %、工数では時間（100% は基準工数、負荷許容率は基準工数 × 率）
- `chartAxis`：横軸の目盛りと右端
  - 負荷率：`niceTicks`（11.15）で、0 から全員の負荷率・負荷許容率・100% の最大まで
  - 配分・予定・実績の3つの最大で決める。切り替えで軸が伸び縮みし、100% の線がずれないように
  - 工数：右端 ＝ 負荷率の右端 × 基準工数の最も長い人の時間。目盛りは右端までの `niceTicks`
  - 負荷率と工数を切り替えても、その人たちの 100% の線が同じ位置に来るようにするため
  - 期間に稼働日が無いときは、時間の最大だけで決める
- 負荷警告・負荷注意の人数も数える（見出しの下に出す）

### 11.17 WBS 番号（`wbsOrder.ts`）

- タスクはエピック内の連番だけを持ち、表示で「エピックの番号.連番」にする（`taskWbsLabel`）
  - エピックの番号を変えても、タスクのノートを書き換えずに済むため（SVN でぶつかりにくい）
  - エピックの無いタスクは連番だけを出す
- 並び（`sortByWbs`）：番号を数として比べる。番号の無いものは元の順のまま後ろ
- ドラッグ後の順（`moveInOrder`）：動かした行を、落とした行の前か後ろに入れる
- タスクの振り直し（`renumberTasks`）：並べた順に 1, 2, 3…。番号の無いタスクにも付ける
- エピックの振り直し（`renumberEpics`）：今使っている番号の組を数の順に並べ、並べた順に配る
  - `1.1`・`1.2` のような番号の形を崩さないため
  - 番号が無い・重なるエピックの分は、最後の番号の末尾の数を進めて足す（`nextWbs`。1.9 → 1.10）
- どちらも番号が変わるものだけを返す（書き込むノートを最小にするため）
- 新しいタスクの番号（`nextTaskWbsIn`）：同じプロジェクト・エピックのタスクの最大の連番＋1
  - 数でない番号は数えない。ノートの作成とタスクのフォームで同じ関数を使う

### 11.18 当初との差（`planDelay.ts`）

- 呼び名は「当初」「見込み」にする（要件 4.7）。作業ログの「予定(h)」と取り違えないため
- `planDelayDays`：見込み終了日と当初終了日の間の稼働日を数える（要件 4.7「当初との差」）
  - 遅れなら (当初終了日, 終了日] の稼働日の数、前倒しならその負の数
  - 当初終了日が休日でも、次の稼働日に終われば1日遅れ（休日をはさんでも数え方がぶれないため）
- `taskPlanDelay`：当初終了日と見込みの日程がそろったときだけ出す
- `taskPlanPeriod`：当初期間。両方そろい、逆順でないときだけ（ガントの帯・タスク一覧の説明で使う）
- 終了日だけで比べる。開始日のずれは終了日に伝わるので、表示を短く保つため
- 警告にはしない（期限超過見込みと重なり、件数が増えすぎるため）
- 予定は日程の計算（11.9）に使わない。最初の計画を固定値として残し、比べるためだけに持つ

### 11.19 作業ログのビュー（`worklogView.ts`）

- `worklogViewMembers`：記録を探すメンバー。絞り込みがあればその人
  - 無ければ在籍者と、その期間に記録のある退職者
- `worklogViewTasks`：メンバーごとの、期間に記録のあるタスクと担当のタスク
  - 担当のタスクは呼び出し側が渡す。完了・停止を含めるかは表示の設定で決める
  - プロジェクトとステータスで絞る。見つからないタスクは絞り込み中は出さない
- `worklogViewLines`：行の並び。タスクの階層は入力フォームと同じ `gridLines`（4.3）
  - 行ごとに合計する「タスクとメンバーの組」（`pairs`）を持つ
  - 記録した人が1人のタスクは、行の `member` にその人を入れ、人の行を作らない
  - 人の行は名前順。キーは `タスクの ID|m:メンバーの ID`（開閉に使う）
- `worklogAssignedTasks`：メンバーごとの担当タスク。完了・停止を含めるかは表示の設定で決める
- `worklogViewPairs`：タスクごとに、その下に並べるメンバー。担当タスクは在籍者だけに足す
- `worklogViewTable`：日・行・全体の合計、見積、欄の幅。部品（`views/worklogPanel.ts`）は描くだけ
  - 全体の合計はプロジェクトの行の合計。たたんだ行も入れる
  - 合計の欄は最小 64px を列の数で割る。見積の欄は最小 56px
- `worklogColumns`：表示する値（`both`・`planned`・`actual`）を、日の中の列に直す
- `worklogCellWidth`：予定か実績の1列の幅。表示する文字のいちばん長いものに合わせる
  - 数字1字 7px と左右の余白 8px で見積もる。最小 28px（「予」「実」が入る幅）
  - 固定の幅だと、大きな数字が見切れるか、小さな数字で横に広がりすぎるため

### 11.20 ガントの作業ログ（`ganttWorklog.ts`）

- `taskDayHours`：横軸の範囲の作業ログを、タスクごと・日ごとに全メンバーぶん合計する
  - 予定・実績とも 0 の行は除く
- `sumDayHours`：複数タスクの日ごとの合計（プロジェクト・エピックの行）
- `hoursText`：0 は空、小数は2けたまで（0.25 刻みのため。足し算の誤差を消す）
- `worklogCellTexts`：表示する値だけの文字。どちらも空ならマスを出さない

### 11.21 タスクの作業範囲（`taskRange.ts`）

- `taskRanges`：当初期間（`taskPlanPeriod`。11.18）と見込みの日程（11.9）。出せないものは入れない
- `inRange`：日付が範囲の中か（両端を含む）
- `rangeLabel`：日のマスの読み上げに足す文字（例：「当初期間の中、開始日、期限日」）

### 11.22 工数配分の負荷（`allocationLoad.ts`）

- `AllocationSummary` は全プロジェクトの工数配分を、メンバー×月×プロジェクトで合計する
  - アーカイブ内・クローズ済みも含める（要件 4.5。作業ログの予定・実績と同じ扱い）
  - 同じ月・メンバーの行が複数あれば合計する
- `memberRange`：期間の配分。月ごとに「月の配分 × 期間内の勤務日数 ÷ 月の勤務日数」を足す
  - 勤務日はその人の個人休日を除いた日（11.2）。配分は休みも踏まえて決めるので、休みの日に割らない
  - 月の勤務日が0日（まるごと休み）なら、割れないので稼働日で割る
  - 週・日でも配分と予定を同じ単位で比べるため。休日には配分しない
  - 月の稼働日数は月ごとに覚えて使い回す（勤務日が0日の月に使う）
- `CalcContext.allocations` として表示のたびに作る（保存しない。要件 3.7）

### 11.23 メンバーダッシュボード（`memberDashboard.ts`）

- `monthLoad`：その月の負荷。メンバー状況と同じ `memberLoad`（11.5）を月の期間で呼ぶ
- `assignedProjects`：その月にその人の工数配分がある案件（要件 4.14）
  - 全プロジェクト（アーカイブ内も）の配分の行から、月・メンバーが合う行を案件ごとに合計する
  - 予定・実績は作業ログの集計の `allocation`（11.1）。並びは配分の多い順、同じなら名前順
- `memberMonthTasks`：その月にかかる担当タスク（アーカイブ内を除く。完了も含む）
  - 見込みの日程（11.9）の開始〜終了がその月と重なるか、その人のその月の作業ログがあるもの
  - 未完了で遅れたタスクは見込みの終了が今日まで延びるので、過去の月から今月まで出る
  - 日程が無く作業ログも無いものは件数（`undatedTasks`）だけ返す
  - 各タスクに、その人のその月の予定・実績（`monthHours`）を付ける。並びは見込み開始・期限日の順
- `pickMember`：選んだメンバー。見つからなければ在籍者の名前順の先頭
- `parseMemberDashboardOptions`：保存されていたメンバーと月を読む。形の違う値は捨てる

## 12. 開発用の仕組み（`plugin/scripts/`）

- `deploy.mjs`：ビルド結果を開発用Vaultにコピーし、`.hotreload` を置く（Hot Reload が自動で読み直す）
  - `npm run dev` ではビルド成功のたびに呼ぶ
- `generate-dummy.mjs`：ダミーデータ（要件 6.3 の規模）を作る
  - frontmatter の最後に `dummy: true` を入れ、消すときはそれがあるファイルだけを消す
  - 乱数は seed で固定する
  - わざと入れたもの以外の警告が出ないように作る（警告の数を見やすくするため）
  - 日程（開始日〜期限日。要件 4.7）を先に決め、ステータスを日程に合わせる
  - どのタスクにも開始日・期限日を入れる。`lag_days`・`duration_days` は書かない
  - 先行のあるタスクは、それらしく見えるよう先行の終了後に始める（日程の計算には使われない）
  - 見積は予定・実績の合計より少し多め、配分は予定の合計より少し多め
  - わざと入れる警告：クローズ以外のプロジェクトに、期限超過・工数超過・期限超過見込みを1件ずつ
  - 期限超過見込みは、期限日を開始日より前にして作る（要件 4.7 ではこの形でしか出ないため）
  - 並びの2番目と5番目のプロジェクトには配分超過も
  - 基準日（`--today`、既定は実行した日）で作るので、日がたつと期限超過が増える。そのときは作り直す
  - 健全性チェックの確認用に、誤りのあるタスク5件と作業ログの誤りの行2件も作る
- `readme-text.mjs`：使い方の正本（`docs/vault/README.md`）を `src/generated/readmeText.ts` に変換する
  - `npm run dev`・`npm run build` の最初に走る（9章「使い方のノート」）
  - 作ったファイルも Git に入れる（取り出した直後でも、ビルドせずに型チェック・補完が通るように）
  - README を直したときは、このファイルの差分も一緒にコミットする
- `package.mjs`：配布用のパッケージを `plugin/release/` に作る（`npm run package`）
  - `<id>/` に `main.js`・`manifest.json`・`styles.css` を集め、`<id>-<版>.zip` にする
  - zip の中は `<id>/` フォルダごと。`.obsidian/plugins/` に展開すれば動くようにするため
  - `data.json` は入れない。全員共通の設定は配る先の Vault に SVN で置くため（要件 6章）
  - Windows では標準の `tar.exe` で作る。`Compress-Archive` はパスの区切りが `\` になるため
  - `release/` は Git に入れず、lint の対象からも外す
- 版を上げるときは `npm version <版> --no-git-tag-version` を使う
  - `version-bump.mjs` が `manifest.json`・`versions.json` も同じ版に書き換える
  - `--no-git-tag-version` を付けるのは、コミットとタグ付けをユーザーが行うため

## 13. HTMLレポート（`report/htmlReport.ts`, `commands/htmlReport.ts`）

- 中身（要件 4.10）
  - 先頭に作成日時と基準日（今日）
  - 「全プロジェクト」：ダッシュボードと同じ表・メンバーの負荷率・2週間以内のマイルストーン
  - メンバーの負荷率：全員の今週・今月（配分・予定・実績）と来月（配分・予定）。週の会議で使うため
    - 来月の実績はまだ無いので列を出さない。数字にマウスを乗せると時間（`title`）
  - プロジェクトごとの節：概要・マイルストーン・エピック・工数配分
  - 計算はダッシュボード（11.10）とプロジェクト状況（11.8）をそのまま使い、画面と同じ値にする
- 対象は、クローズしていない・アーカイブ内でないプロジェクト
  - ビューの絞り込みには関係しない（誰が書き出しても同じ範囲になるように）
  - メンバーは在籍者。プロジェクトの表示名は書き出した人の個人の設定
- タスクの行は入れない（数千件になり重くなるため。上司が見るのはエピック単位まで）
- 1つの HTML ファイルに CSS も入れ、JavaScript は使わない
  - ほかのファイルが無くても、メールで送っても、ブラウザでそのまま開ける
  - 白地で印刷でき、印刷ではプロジェクトごとに改ページする
  - 全プロジェクトの表から各プロジェクトの節へページ内リンクで飛べる
- 文字はすべてエスケープする（`<` などがあっても崩れない・スクリプトが入らないように）
- 書き出し（`commands/htmlReport.ts`）：個人の設定の出力先フォルダに `project-report.html` を上書きで書く
  - Vault の外に書くので、Obsidian の API ではなく Node の `fs` を使う（デスクトップ専用のため使える）
- 出力先は Windows の絶対パス（`C:\…` か `\\サーバー\共有\…`）だけ受け付ける（`reportFolderProblem`）
  - フォルダが無ければ作らずに知らせる（つなぎ忘れや打ち間違いで、意図しない場所に作らないため）
- 呼び出し：コマンド「HTMLレポートを書き出す」、リボンのメニュー、ダッシュボードの操作の欄のボタン
