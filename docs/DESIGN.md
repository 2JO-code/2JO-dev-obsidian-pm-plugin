## 1. 全体構成

### 1.1 層の分け方

| 層 | 役割 | Obsidian API |
| --- | --- | --- |
| 純粋な処理 | 型、値の変換・検証、表の読み書き、健全性チェック、計算 | 使わない（単体テストする） |
| つなぎ | Vault・MetadataCache との読み書き、イベントの受け取り | 使う |
| 画面 | 設定画面、入力フォーム（モーダル）、ビュー、コマンド・メニュー | 使う |

判定・変換・文字列の組み立ては純粋な処理に置き、つなぎと画面は薄く保つ。

### 1.2 フォルダ（`plugin/src/`）

| フォルダ | 層 | 内容 |
| --- | --- | --- |

| `settings.ts` | 純粋 | プラグイン設定・個人の設定の型と既定値（6章） |

`commands/` の中身：

- ノート作成、フォーム・表の編集画面を開く、作業ログ、再読み込み
- aliases の同期、共有設定の監視、HTMLレポートの書き出し、使い方を開く

### 1.3 データの流れ

1. 起動完了後（`onLayoutReady`）に共有設定を読み、索引を作る（3.2）
2. ノートが変わると索引を差分更新し、`updated` イベントを出す（3.3）
3. ビューは `updated` を受けて描き直す。計算結果は保存せず、表示のたびに計算する（要件 3.7）
4. 書き込みは次のどれかを通す
   - frontmatter の書き方（4.1）
   - 本文の変えた行だけの書き換え：作業ログの行 4.3、表の編集画面 4.7、チェックリスト 4.10

## 2. 型（`model/`）

- 日付は `YYYY-MM-DD` の文字列（`IsoDate`）、月は `YYYY-MM`（`YearMonth`）。`Date` は使わない（4.1）
- `wbs`・`case_id` は文字列。数値にすると `1.10` が `1.1`、`0123` が `123` になる（4.1）
- 任意項目は「キーが無い」で表す（`undefined` を入れない）
- 本文の表の行は、ファイル先頭からの行番号（0始まり）を `line` に持つ
  - 警告一覧で「何行目」を示すため
- ステータスは名前の文字列のまま持ち、分類はその都度 `findStatus` で引く
  - 設定を変えても索引を作り直さずに済む

## 3. 読み込みと索引（`store/`）

### 3.1 対象のファイル

- ファイル名がノートIDの形式（`TASK-…` など。10章）のものだけを対象にする。フォルダは問わない
- アーカイブフォルダの中のノートも読み、`archived` で区別する
  - 一覧の既定では除くが、IDの重複確認や参照先の確認には含める

### 3.2 起動時の読み込み

- `onLayoutReady` の後に全ノートを読む。`onload` には含めない（起動を遅くしないため）
  - 4,000件で `onload` は約3ミリ秒、索引の作成は約0.1秒
- 200件ずつ処理し、区切りごとに処理を譲る（画面を固まらせないため）
- 本文を読むのはプロジェクト・メンバー・作業ログだけ（表があるため）
  - タスクのチェックリストは MetadataCache の `listItems` から数え、ファイルを読まない
- 作り直し中に再度呼ばれたら、同じ処理の完了を待つ
- 作り直しの間に変わった・消えた・名前が変わったファイルは覚えておき、最後に読み直す
  - 無くなっていれば索引から消す
  - 作り直しは途中で読んだ内容でまとめて置き換えるので、古い内容での上書きを防ぐため

### 3.3 差分更新

- frontmatter・本文の変更は MetadataCache の `changed`（解析後のキャッシュと本文を受け取れる）で受ける
- `changed` はリネームで呼ばれないので、vault の `rename` を別に受ける。削除は vault の `delete`
- ビューへの通知（`updated`）は300ミリ秒まとめて出す（入力中に何度も描き直さないため）
- タイトルが変わったら `title-changed` を出す（4.2）。最初の読み込み中は出さない
- 多くのノートをまとめて書くとき（WBS 番号の振り直し。9.7）は `writeMany` を使う
  - 書いたファイルがすべて `changed` で読み直されるまで、`updated` を止める。最後に1回だけ出す
  - 300ミリ秒のまとめは最初の変更から数えるので、書き込みが続くと何度も描き直して重くなるため
  - 知らせが届かないときのために上限を置く（書いている間10秒、書き終えてから2秒）
  - 書き込みは並行に行う。書く前に対象のファイルがすべてあるか確かめる

### 3.4 値の読み取り（`buildNote`, `Coercer`）

- 空の値（`null`・空文字・空配列）は未入力として扱い、問題にしない
- 型が違う値は無視し、理由を `problems` に記録する（健全性チェックで出す。8章）
- `wbs`・`case_id` が数値で読まれていたら、文字列に戻して警告する
  - 元の表記が失われている可能性があるため。直し方はフォームでの入れ直しを案内する（4.9）
- `.obsidian/types.json` でこの2つを「テキスト」型に固定することはしない
  - 値はフォームから文字列で書くので、数値になる経路はノートの直接編集だけ
  - types.json が効くのはプロパティ欄の入力だけで、ソースモードの手入力は防げない
  - Vault ごとに設定ファイルを配る手間に見合わない。警告で気づければ足りる
- プロジェクト・エピック・タスクは、必須の参照（`project`, `status`）が無いとモデルを作らない
  - ただし他の項目も最後まで調べ、誤りをまとめて報告する（直すときに一度で分かるように）
- メンバーの数値が無ければ既定値（8h・120%・在籍）を使う
- 作業ログのメンバーと月はファイル名を正とし、プロパティと違えば警告する
- frontmatter の `title` は、モデルを作れなかったノートでも `NoteRecord.title` に持つ
  - 警告一覧で人が見分けられるように

## 4. 書き込み

### 4.1 frontmatter（`write/frontmatter.ts`）

Obsidian 1.14.5 の `processFrontMatter` の実装を調べた結果に基づく（HISTORY.md の T0-3）。

- `processFrontMatter` は `yaml` ライブラリ v2（YAML 1.2）で読み書きし、frontmatter 部分だけを置き換える
  - 書き出しの設定：`{nullStr: "", lineWidth: 0, aliasDuplicateObjects: false}`。本文は変わらない
- キーはオブジェクトの順に書き出される
  - コールバックの中で全キーを消し、`FRONTMATTER_KEYS` の順に入れ直す
  - 決めていないキーは元の順で後ろに付ける
- 日付は文字列で渡す。`Date` を渡すと `2026-11-30T00:00:00.000Z` になるので、渡したらエラーにする
- リンクは `"[[ID]]"`（ダブルクォート付き）、配列はブロック形式で書かれる
- 手で編集したノートは、最初の書き込みで frontmatter 全体の書式が整う（2回目以降は差分が出ない）
  - frontmatter 内のコメントは消える
- YAML が壊れている（SVN のコンフリクトなど）と例外になるので、呼び出し側で通知する

### 4.2 aliases の同期（`write/aliases.ts`, `commands/aliasSync.ts`）

- aliases はタイトルと同じ値1つだけにする（要件 3.2）。手で足した値や以前のタイトルは残さない
- タイトルが変わったら1.5秒待ってから書く（ソースモードで入力中に何度も書かないため）
  - 待っている間にさらに変わったら数え直す
- 起動時・再読み込みでは書かない（SVN 更新などで多数のノートが一斉に書き換わるのを防ぐ）
  - ずれているノートは健全性チェックで知らせる
- すでに合っていれば書かないので、書き込み→変更検知→書き込み…の繰り返しにならない

### 4.3 作業ログの行（`forms/worklogForm.ts`）

- 1回の入力で1行（日付×タスク）を書く
  - 同じ日付・同じタスクの行があればその行を書き換える（行が増えて合算されるのを防ぐ）
- 同じ日付・タスクの行が複数あるときは、最初の行の値を読み、最初の行だけを書き換える
  - 他の行は残り、集計では合算される（要件 3.5）
- 追加するときは日付順の位置に入れる
- 書き換える行以外は1文字も変えない。改行コード（CRLF）も保つ（SVN の差分を最小にするため）
- メモの `|` は `\|` に、改行は空白にする（表を壊さないため）
- 表が無ければ本文の末尾に作る（`appendTable`。4.7 と共通。本文が frontmatter だけなら空行をはさまない）
- ログファイル（メンバー×月）が無ければ作業ログのフォルダに作る
- ログファイルは、まず索引から探し、無ければ作業ログのフォルダのパスで探す
  - アーカイブなど作業ログのフォルダの外にあっても、索引にあればそれを使う
  - 作ったばかりのファイルは Obsidian が読み終えるまで索引に載らない
  - 索引だけで探すと、同じファイルをもう一度作ろうとして失敗するため
- Obsidian で表を編集すると表全体の列幅がそろえ直され、差分が広がる。対策は 4.8

入力フォーム（`ui/worklogModal.ts`）：

- 開く場所：コマンド「作業ログを入力」と、プロジェクト状況のタスクの行の「＋工数」（9.4）
- タスクの行から開くときは、そのタスク（とプロジェクト）を選んだ状態で開き、タイトルにタスク名を出す
  - 「続けて入力」のあともタスクを残す（別の日付を続けて入れるため）
- 最初に選ぶメンバー（`defaultWorklogMember`）
  - 前回選んだ人がそのタスクの担当者ならその人
  - そうでなく、在籍の担当者が1人ならその人。ほかは前回選んだ人
- タスクの行の中に入力欄を開く形にはしない
  - 表が横に長くなり、その日の記録の一覧や書き換えの案内を作り直すことになるため
- コマンドは、タスクを探さずに入れたいとき用に残す

### 4.4 ノートの作成（`commands/newNote.ts`）

- 入力を確かめ、作るノートのパス・frontmatter・本文を決める処理は純粋関数にする
- ステータスは一覧の先頭（新規作成時の初期値。要件 3.6）
- 本文に空の表を入れる（そのまま読み取れる形）
  - プロジェクトは「マイルストーン」「工数配分」、メンバーは「個人休日」
- ファイルを作ってから `processFrontMatter` で frontmatter を書く（4.1 のキー順を通すため）
  - フォルダが無ければ作る。作業ログのファイルと共通（`write/frontmatterFile.ts` の `createNoteFile`）
- 2回目の書き込み（frontmatter）が失敗しても、作成は終わりとする
  - 画面を閉じ、作りかけであることとパスを通知する
  - 画面を開いたままだと、もう一度押されて別のIDのノートができるため
  - 作業ログのファイルも同じ（行は書けているので保存は成功として通知する）
- 作ったノートは開かず、「「タイトル」を作成しました」と通知するだけ
  - 値はすべて画面から入れる方針（4.9）で、ノートを開いても使わないため。作ったものはビューにすぐ出る
- ID は索引で重複を確かめて採番する（アーカイブ内も含む）
- タスクの WBS 番号は、同じエピックのタスク（アーカイブ内も含む）の続きの連番にする（11.17）
- まだ入力していないプロパティも、`FRONTMATTER_KEYS` のキーをすべて空の枠として入れる
  - プロパティ欄にはじめから項目が並び、どこに何を書けばよいか分かるようにするため
  - 空の値（`model/frontmatter.ts` の `emptyValue`）：リストのキー（`LIST_KEYS`）は `[]`、ほかは `null`
  - `null` は 4.1 の設定で `start:` のように値なしで書かれる
  - 読み取り（3.4）は `null`・`[]` を「無い」と同じに扱うので、警告や計算は変わらない

### 4.5 入力補助フォーム（`forms/taskForm.ts`, `epicForm.ts`, `projectForm.ts`, `memberForm.ts`）

共通：

- frontmatter から読める値だけをフォームに入れる（必須項目が欠けたノートもフォームで直せるように）
- リンクの項目で読めない値（打ち間違い、種類の違うIDなど）は、消さずに元の文字列のまま持つ
  - フォームでは「（読めません）」と出し、外さなければ保存時に元のまま書き戻して通知する
  - 捨てると、開いて保存しただけで値が消えるため
  - 文字列・数値でない値（リストの中の `null` など）は読み飛ばす
- 選択肢に無い値（見つからないID、読めない値）も選択肢に足して選んだままにする（`missingLabel`）
- 入力の誤り（必須・刻み・日付・自分自身への依存）は保存しない
  - 期限日が開始日より前などは、保存したうえで知らせる
- 空欄の任意項目は、キーを消さずに空の値（4.4 の `emptyValue`）にする（`keepFrames`）
  - 作成時に用意した枠が、フォームで保存したときに消えないようにするため
- ステータスは旧名で書かれていても現在の名前で保存する（5.4）

タスクのフォームの WBS 番号：

- 1以上の整数だけを受け付け、文字列で書く（4.1）
- プロジェクトかエピックを変えると、移った先の続きの番号に入れ替える（11.17。同じ番号が重ならないように）

エピックのフォーム：

- 項目：タイトル・プロジェクト・ステータス・担当者（`owner`、1人）・WBS番号
  - ほかに開始日・完了予定日・インプット・アウトプット
- 担当者のプルダウンは在籍者と「なし」。在籍していない人が入っていれば選択肢に残す
  - 開いて保存しただけで消えないように
- インプット・アウトプットは文字列のリスト。入力欄は複数行で1行に1つ。空の行は除く
- プロジェクトは、使われていれば変えられない（`epicFormToUpdate` の `fixedProject`）
  - 使われている：そのエピックのタスク（アーカイブ内も含む）か、マイルストーンの連動エピック
  - エピックだけ移すと、タスクの `project` と食い違って警告が出るため
  - タスクもまとめて書き換える案は、多くのファイルが変わり SVN でぶつかりやすいので採らない
  - 連動が無いエピックだけ、作り間違えの直しとして変えられる
  - プルダウンは押せなくして理由を添え、保存時にも確かめる

メンバーのフォーム：

- 項目：氏名・1日の通常稼働時間・負荷許容率・在籍
- 通常稼働時間は 0 より大きく 24 以下の 0.25 刻み。負荷許容率は 1 以上の整数
  - 100 未満は保存したうえで知らせる
- 空の項目は既定値（8・120・在籍）で開く。3.4 と同じ値なので、開いて保存しても計算は変わらない
- 数値は数値、在籍は true/false で書く。個人休日は 4.7 の編集画面で変える
- 開く場所：メンバー状況のメンバー名の横の「フォーム」、メンバーのノートの右クリック、コマンド

プロジェクトのフォーム：

- 項目：簡易プロジェクト名・正式案件名・案件ID・ステータス（プロジェクト用）・開始日・期限日・責任者
- 簡易名・正式名・案件IDは必須（作成時と同じ）。案件IDは数字に見えても文字列で書く（4.1）
- 本文の表（マイルストーン・工数配分）は扱わず、表ごとの編集画面（4.7）で変える

部品：

- 値の読み取り・日付の確かめは `forms/formValues.ts`
- 入力欄の部品は `ui/formParts.ts`
  - 日付、時間（`hoursInput`。0.25刻み）、メンバー1人（`memberSetting`）、ステータス（`statusSetting`）
  - プロジェクト・エピックのプルダウン（`projectOptions`・`epicOptions`）、誤りの表示
- 保存して閉じる流れは `ui/formModal.ts` の `FormModal` にまとめる
  - 誤りの表示、二重送信の防止（4.6）、失敗・知らせることの通知、「キャンセル」「保存」のボタン
  - 継承するもの：4つのフォーム、表の編集画面（4.7）、チェックリストの編集画面（4.10）
  - 作業ログ入力（4.3）は「保存して続けて入力」があり流れが違うので継承しない
- 開く処理は `commands/editTask.ts` の `openTaskForm`・`openEpicForm`・`openProjectForm`・`openMemberForm`
  - ファイルかパスを受け取る。読み込み中・frontmatter が読めないときは通知して開かない
  - ノートの種類からフォームを選ぶ表（`FORMS`・`formOpenerOf`）は、コマンド・右クリック・警告一覧で共通

### 4.6 二重送信の防止

- 書き込む画面は、保存が終わるまで次の保存を受け付けない（`saving` の印）
  - 対象：作成・作業ログ・4つのフォーム・表の編集画面・チェックリストの編集画面
  - Enter の連打などで保存が2回走ると、ノートが2つできたり、ファイルの作成が失敗したりするため
- 入力の誤りで止まったとき・保存に失敗したときは印を戻し、直してもう一度押せるようにする

### 4.7 表の編集画面（`forms/projectTables.ts`, `holidayTable.ts`, `worklogTable.ts` ほか）

マイルストーン・工数配分・個人休日・作業ログの表を、画面で直す。

- 画面は `ui/tableEditModal.ts`、工数配分だけ `ui/allocationMatrixModal.ts`
- 書き出しは `write/markdownTable.ts`

開く場所：

- マイルストーン・工数配分：プロジェクト状況の見出しの横の「編集」（`commands/editProjectTables.ts`）
- 個人休日（`commands/editHolidays.ts`）
  - メンバー状況の「個人休日を編集」（メンバーを選ぶ）、メンバーのノートの右クリック
  - コマンド「個人休日を編集」（開いているのがメンバーのノートならその人、ほかは選ぶ）
- 作業ログ（`commands/editWorklog.ts`）：警告一覧の作業ログの表の警告、「作業ログを入力」の「（月）の記録を一覧で編集」

共通：

- 表の行を入力欄の一覧にし、変更・追加（「＋行を追加」）・削除してまとめて保存する
  - 1行ずつのフォームにしないのは、工数配分などは行が多く手間がかかるため
- 行はノートの本文から直接読む（索引ではなく）
  - 読めない行（日付の誤りなど）も一覧に出し、画面で直せるようにする
  - 中身の無い行は出さず、ノートにはそのまま残す
- 書き換えは 4.3 と同じく**変えた行だけ**。変えていない行は1文字も変えない
  - リンクにタイトルが無くても直さない
  - 消した行は除き、新しい行は日付（工数配分は月）の順の位置に入れる。CRLF を保つ
- 変えた行・新しい行のリンクは `[[ID\|タイトル]]`（要件 3.5）
  - 読めないリンクは消さずに元のまま書き戻して知らせる（4.5 と同じ）
- 列の順は表の見出し行に合わせ、決めていない列（自分で足した「メモ」など）の値は残す
- 開いたあとにノートの表が変わっていたら保存しない
  - ほかの人の SVN 更新などで行番号がずれ、別の行を書き換えるおそれがあるため
  - 開いたときの行（`tableSnapshot`）と保存時の行を比べ、違えば「画面を開き直してください」と通知する
- 表が無ければ本文の末尾に作る。必要な列が足りない表は、開かずに知らせる
- 共通の処理：行を列名で読む（`readRows`）、リンクのセル（`linkCell`）、変えたか（`isChanged`）
  - `forms/tableRows.ts`。開く前の確かめ（`tableSource`・`usable`）は `commands/ready.ts`
  - セルの入力欄（`textCell`・`hoursCell`）とメンバーのプルダウン（`memberOptions`）は `ui/formParts.ts`
  - 書き出しの部品（`tableCell`・`tableLink`・`tableRow`・`emptyTable`）は 4.3・4.4 と共通

確かめ：

- マイルストーン：名前・日付が必須。連動エピックはこのプロジェクトのエピック（WBS順）から選ぶ
- 個人休日：日付が必須。同じ日付の行は最初の行だけが使われる（7章）ので、保存したうえで知らせる
- 中身の無い新しい行は捨てる

作業ログの表：

- 1ファイル（メンバー×月）の表を直す
  - 「作業ログを入力」は1行を足す・書き換えるだけで、行を消す・誤りを直すことができないため
- タスクの欄は、押すとタスク名（とプロジェクト名）で探して選ぶ画面を開く（`ui/chooseModal.ts`）
  - `FuzzySuggestModal` を使う。個人休日のメンバーの選択と共通
  - 行ごとのプルダウンは、タスク数千件・行数十行で重く、画面も横に長くなるため
  - 選べるのはアーカイブ外のタスク。アーカイブ内のタスクの行はタイトルを出し、変えなければ残る
- 日付は対象月の中だけ（ファイルが月ごとのため。ほかの月は消して「作業ログを入力」で入れ直す）
- 予定・実績は空か0.25刻み。変えた行・新しい行は、予定か実績のどちらかが必須
  - 変えていない行は、両方空でも残す
- 同じ日付・タスクの行は集計で合算されるので、保存したうえで知らせる
- 時間は数値の形（`2.50` → `2.5`）で書く

工数配分のマス目（`allocationMatrix`・`allocationMatrixEdits`）：

- 縦にメンバー・横に月。プロジェクト状況の配分表（11.8）と同じ向き
  - ノートの表の形は変えず、画面だけマス目にし、保存時に行の書き換えに直す
- 並べる月：表の行の月、プロジェクトの開始日〜期限日の月、作業ログに予定・実績のある月
- 並べるメンバー：表の行のメンバー、責任者、作業ログのある人（名前順）
- 「＋メンバー」（在籍者）・「＋月」で足す。メンバーの行のごみ箱で、その人の配分をすべて消す
- 書き換え
  - 変えていないマスの行は1文字も変えない。変えたマスは、その月・メンバーの1行目を書き換える
  - 新しいマスは行を足す（月の順の位置）。空にしたマスは行を消す。0 は「配分0」として残す
- 同じ月・メンバーの行が複数あれば、マスには合計を出す（`groupAllocationRows`。集計でも合計するため）
  - そのマスを変えたら1行にまとめ、保存したうえで知らせる
- 月かメンバーが読めない行はマス目の下に一覧で出し、消すことだけできる。消さなければ残る
- マスの下に、参考としてその月・メンバーの予定・実績を出す（配分を決めるときに見たいため）
  - このプロジェクトのタスクに付けた作業ログの合計。11.8 と同じ値。画面を開いた時点
  - どちらも0なら出さない。予定が配分を超えたら赤（入力のたびに描き直す）

### 4.8 表の自動整形と SVN の差分

- Obsidian のライブプレビューで表のセルを編集すると、表全体の列幅が空白でそろえ直される
  - 1行直すたびに表全体が差分になり、SVN のコンフリクトが起きやすい
- Obsidian にこの整形を止める設定は無い
  - 止めるには外部のプラグイン（Table Formatter など）を全員に入れる必要があり、使わない
- プラグインが同じ「列幅をそろえた形」で書く案も採らない
  - 長い値が1つ入るだけで、プラグインの書き込みでも表全体が変わるため
  - プラグインは詰めた形（`| a | b |`）で、変えた行だけを書き換える（4.3、4.7）
- **運用で避ける**：本文の表はプラグインの画面から変える（4.9）
- すでに整形された表も、編集画面は変えていない行を変えないので、そろえた空白はそのまま残る

### 4.9 ノートを直接編集させない

要件 4.2 の方針。

- 利用者が変える値（プロパティ・本文の表）は、すべてプラグインの画面で変えられるようにする
  - 画面なら値の確かめ（日付・0.25刻み・リンクの形）が効く
  - 書き込みは 4.1 のキー順・4.3 の「変えた行だけ」が守られ、書き方の誤りと SVN の差分を防げる
- ノートを開くことは止めない
  - Obsidian にノートを書き込み禁止にする仕組みが無く、中身を見る・警告を直す最後の手段として要るため
  - 使い方の README では直接編集を案内しない
- 画面
  - 入力補助フォーム（4.5）、表の編集画面（4.7）、作業ログ入力フォーム（4.3）
  - チェックリストの編集画面（4.10）、カンバンのカード移動
- 警告一覧の行は、直す画面があればそれを開く（8章）
- まだ画面が無いもの
  - 作業ログのプロパティ（member・month。ファイル名が正なので計算には使わない）
  - タスク本文の説明の文

### 4.10 チェックリストの編集画面（`forms/checklist.ts`, `ui/checklistModal.ts`, `commands/editChecklist.ts`）

- 専用の画面にする（タスクのフォームの中に入れない）
  - フォームはプロパティ、この画面は本文と書き込む先が分かれ、どちらかだけ失敗することが無いため
  - フォームの「チェックリストを編集」は、フォームの入力を残したまま上に重ねて開く
- 開く場所：タスクのフォーム、タスクのノートの右クリック、コマンド「タスクのチェックリストを編集」
  - タスク一覧・WBS・プロジェクト状況の進捗の値からも開く（9.1）
- 出す項目は完了の割合で数えるものと同じ：`[ ]`・`[x]`・`[X]`
  - frontmatter とコードブロックの中、ほかの記号（`[-]` など）は出さず、そのまま残す
  - 入れ子の項目も出す（字下げは保つ）
- 書き換えは 4.7 と同じく**変えた行だけ**
  - チェックと内容だけを置き換え、行頭（字下げ・`-` や `1.`）は元のまま
  - `[X]` はチェックしたままなら `X` を保つ
  - 消した項目は行ごと除く（その下の入れ子の項目は残る）。CRLF を保つ
- 新しい項目は `- [ ] 内容` の形で、今の最後の項目の下（その下の字下げした行の後ろ）に足す
  - 最後の項目を消しても、その位置に足す
  - 項目が無ければ本文の末尾に、空行をはさんで足す（本文が frontmatter だけならはさまない）
  - 今ある項目の間には入れられないので、画面でも新しい項目は後ろにだけ並ぶ。並べ替えはできない
- 1項目は、チェックボックスと内容の入力欄を横に並べる（ノートのチェックリストと同じ形）
  - チェックボックスはノートと同じ見た目（`task-list-item-checkbox`）
  - 完了の項目は内容を薄く・取り消し線にする
- 入力欄で Enter を押すと、次の新しい項目を足してそこへ移る（続けて入れやすいように）
- 内容の無い新しい項目と、今ある項目の内容を空にしたものは誤りにして保存しない
  - 黙って捨てると、足したつもりの項目が消えて気づけないため。要らなければごみ箱で消す
- 開いたあとにチェックリストの行が変わっていたら保存しない（4.7 と同じ。行番号がずれるため）

## 5. 共有設定（`config/`）

### 5.1 ファイル

- `_pm/statuses.json`, `_pm/calendar.json`（フォルダはプラグイン設定で変えられる）。Vault API で読み書きする
- 書き出しはキー順・2スペースのインデント・末尾改行で固定する（SVN で余計な差分を出さないため）
- 休日は日付順に並べる

### 5.2 ファイルが無いとき

- 初期値（要件 3.6 のステータス、土日休み・休日なし）で動く
- ファイルは設定画面で保存したときに初めて作る
  - 起動時に作ると、SVN を更新していない人のファイルと、他の人のファイルがぶつかるため

### 5.3 ファイルが壊れているとき

- 使える部分だけ使い、壊れた部分は初期値で補う。ファイルは書き換えない
- 問題は `SharedConfig.problems` に入れ、警告一覧と設定画面の先頭に出す（保存すると上書きされるため）
- ファイルの作成・変更・削除・リネームを検知して読み直す（SVN 更新や他の人の保存に追従するため）
- 読み直したとき、ファイルの場所と中身が前回と同じなら何もしない（ビューも描き直さない）
  - 設定画面で保存すると、保存後の読み直しとファイルの監視で2回読み直すため
  - 自分の書き込みを印で見分ける方法は、印を消すタイミングが難しいので採らない
  - 保存後の読み直しは残す（保存の直後に設定画面を新しい値で描き直せるように）

### 5.4 ステータスの名前変更

- 旧名を `aliases` に残し、既存のノートは書き換えない（要件 3.6。SVN で大量のファイルが変わるのを避ける）
- 旧名のノートも新しい名前のステータスとして集計・表示する
  - ノートの値は、次にプラグインがそのノートを書くときに新しい名前になる
- 名前・旧名が他のステータスと重なる変更、空の名前、最後の1つの削除は受け付けない

### 5.5 設定変更の影響（`config/impact.ts`）

- 変更ごとに影響を「なし／通知／確認」に分ける（対応表は要件 4.12）
  - 確認は保存前に確認画面、通知は保存後に出す
- 影響するノートの件数は `UsageCounter` から得る
  - 索引ができる前は `NO_USAGE`（件数なし）を使い、説明だけを出す

## 6. プラグイン設定と個人の設定

設定の保存先は要件 4.12 の表のとおり。

全員共通の設定（`data.json`）：

- フォルダのパスと、種類（プロジェクト・エピック・タスク）ごとの色（`colors`）
  - `data.json` はプラグインフォルダごと SVN で配られるので、個人の好みは入れない
  - 色は全員で同じにしたい（HTMLレポートの色もそろう）ので共通にした
- 色は `#rrggbb`（小文字）だけを受け付け（`cleanColor`）、それ以外は初期の色にする
- 色を選んでいる間は何度も変わるので、`data.json` への保存は0.5秒待ってまとめる（`debounce`）
- 画面には CSS 変数（`--pm-color-project` など。`ui/kindColors.ts`）として `body` に入れる
  - 別ウィンドウを開いたときにも入れ、プラグインを止めたら消す

ステータスの色（`statusColors`）：

- 全員共通の設定に、セット（タスク・エピック用／プロジェクト用）ごとに「名前 → 色」で持つ
  - `_pm/statuses.json` に持たせる案もあったが、種類の色と同じ `data.json` にした
- 選んでいないステータスは分類の色（`config/statusColor.ts` の `CATEGORY_COLORS`）
  - 未着手系＝灰、進行中系＝青、完了系＝緑、停止系＝橙
  - 何も選ばなくても見分けられ、分類を変えれば色もついてくる
- 名前で覚えるので、名前を変えたら色も付け替え（`renameStatusColor`）、削除したら消す
  - 旧名のノートは `findStatus` で今の名前にしてから色を探す
- 設定画面のステータスの行に、色を選ぶ欄と「分類の色に戻す」ボタン
- ステータス名は自由なので CSS 変数の名前にできない。描くときに要素へ `--pm-mark-color` を入れる
  - そのため色を変えたら開いているビューを描き直す（`redrawViews`。保存と一緒に0.5秒まとめる）

個人の設定：

- 項目：プロジェクトの表示名、ノートを開く場所、左枠の幅、作業ログで前回選んだメンバー、HTMLレポートの出力先
- `app.saveLocalStorage` に保存する。この PC・この Vault だけに残り、SVN で共有されない
- 以前 `data.json` に入れていた表示名・開く場所は、個人の設定がまだ無いときに引き継ぐ
  - `data.json` は起動時には書き換えない（SVN 管理のファイルを全員の PC で書き換えないため）
  - 古い値は、誰かがフォルダや色の設定を保存したときに消える

その他：

- `minAppVersion` は 1.8.7
  - `getFileByPath`（1.5.7）、ビューの遅延読み込み（1.7.2）、`saveLocalStorage`（1.8.7）に合わせた
- フォルダのパスは `\` を `/` にそろえ、前後の `/` や空白を除く。空や `..` を含むパスは受け付けない

## 7. 本文の表の読み取り（`parse/`）

- 見出し（`##` など）の名前で表を探し、その見出しの直後の最初の表を読む
  - 次の同じか上位レベルの見出しまでに表が無ければ「表なし」
- 見出し名・列名は、全角括弧と空白の違いを無視して比べる。列は列名で見分け、並び順は問わない
- `\|` はセル区切りではなく文字の `|` として扱う（リンクの別名 `[[ID\|タイトル]]` のため）
- コードブロックの中の見出し・表は無視する
- 全セルが空の行は無視する。読めない行は読み飛ばし、行番号つきで problems に返す
- 必須の列が無い表は行を読まない
- リンクは `[[ID]]`・`[[ID|タイトル]]`・`[[フォルダ/ID]]`・ID そのものを受け付け、ID部分だけを使う
  - タイトルが古くても集計は変わらない
- 個人休日（`parsePersonalHolidays`）：列は日付・メモ。日付だけ必須
  - 同じ日付の2行目以降は読み飛ばす（印を出すだけなので、警告するほどではない）
  - 日付の形式違いは problems に入れ、健全性チェックに出す

## 8. 健全性チェック（`health/`）

警告一覧には次をまとめて出す。

| 出どころ | 内容 |
| --- | --- |
| 共有設定（5.3） | JSON として読めない、値の形式違い |
| ノートの読み取り（3.4） | frontmatter が読めない、type とファイル名の種類の違い、必須項目の欠落、値の形式違い、本文の表の問題 |
| 索引 | 同じIDのファイルが複数ある |
| `check.ts` | 存在しないノートへの参照、自分自身への依存、別プロジェクトのエピック、設定に無いステータス（旧名は問題にしない）、aliases がタイトル1つでない |
| `strayFiles.ts` | 管理フォルダの中の、ファイル名が ID の形でない Markdown ファイル |

- 参照先は、読めないノートでもファイルがあれば「ある」とみなす（そちらで別の警告が出るため）
- 警告一覧では、ノートを種類とタイトルで出す（`labels.ts`）
  - 作業ログは「メンバー名の作業ログ（月）」
  - 読めないノートは frontmatter の `title`、それも無ければファイル名

ID の形でないファイル（`strayFiles.ts`）：

- 対象は設定の「フォルダ」のうち共有設定（`_pm`）以外の6つと、その下のフォルダ
  - Vault の直下（`README.md` など）やほかのフォルダは見ない（利用者が自由にノートを置く場所のため）
- Markdown だけを見る（添付ファイルはノートと同じフォルダに置く設定のこともあるため）
- 索引には入れず、警告一覧を描くたびに Vault のファイルの一覧から探す（ファイル名を見るだけで速い）
- `VaultStore` は、管理フォルダでこの形のファイルが作られた・消えた・名前が変わったときも `updated` を出す

直す画面：

- 問題を作るところで、直せる画面を `NoteProblem.fix` に入れる
  - 値：`form`・`milestones`・`allocations`・`holidays`・`worklog`
  - メッセージの文字から後で推し量ると、文言を変えたときに壊れるため
- プロパティの問題は入力補助フォーム
  - 形式違い・必須項目の欠落・type の違い・存在しない参照・設定に無いステータス・aliases・循環
  - フォームは読めない値も消さずに持ち、保存で type・aliases も書き直すので、どれも直せる
- 本文の表の問題は、その表の編集画面（読めない行も元の文字のまま出すので、そこで直せる）
- 画面が無いもの
  - frontmatter が読めない（フォームも開けない）、同じ ID のファイル、ID の形でないファイル
  - 作業ログのプロパティ（member・month の食い違い）、作業ログの表が無い
  - 共有設定（設定画面で直す）
- 行は、`fix` があればその画面を開き、無ければノートを開く
  - 行の右の「ノート」ボタンでノートも開ける（最後の手段として残す。4.9）

## 9. 画面

- **設定画面**：入力欄は `change` イベント（フォーカスが外れたとき・Enter）で確定する（1文字ごとに保存しない）
  - 保存後は描き直すが、スクロール位置を保存・復元する（`display()` は中身を作り直し先頭に戻るため）
- **確認画面**（`ui/confirmModal.ts`）：Promise で「実行／キャンセル」を返す。閉じたらキャンセル
- **入力フォーム**：入力の誤りはフォームの上に出し、フォームを閉じない
  - 選択肢が変わる操作（プロジェクトの選択など）の後は中身を描き直す
- **作業ログのフォーム**：追加か書き換えかを、タスクを選んだ時点で目立つ枠とボタンの文言で示す
  - 保存後は索引の更新を受けて「その日の記録」だけを描き直す（入力欄は触らない）
- **ビュー**：表示中に例外が起きたら、画面に内容を出す
  - メソッド名の注意は [OBSIDIAN_BEST_PRACTICES.md](OBSIDIAN_BEST_PRACTICES.md) 5章
- **リボン**：ボタンは2つ。↻ は再読み込み（要件 4.11）
  - かばんのボタンはメニューで主な操作を開く（ボタンを並べるとリボンが混むため）
  - メニューの並び（「／」は区切り線）
    - ノートの作成4種／作業ログの入力・開いているタスクの編集
    - ／ビュー（ダッシュボード・タスク一覧・カンバン・WBS・ガントチャート・メンバー状況・プロジェクト状況）・警告一覧
    - ／HTMLレポートの書き出し・アーカイブ対象の一覧／使い方（README）・データの再読み込み

使い方のノート（`commands/readme.ts`）：

- 利用者向けの使い方は Vault の直下の `README.md` に置く
  - メニュー「使い方（README）」とコマンド「使い方を開く」で開く
- 正本はリポジトリの `docs/vault/README.md`（Vault はリポジトリと別管理のため）
- ファイル名が ID の形でないので、プラグインはノートとして読まない
- プラグインが作る（手でコピーすると Vault の README が古いまま残りやすいため）
  - ビルドの前に `scripts/readme-text.mjs` が正本を `src/generated/readmeText.ts`（文字列1つ）に変換する
  - main.js に入れる（esbuild の設定を変えずに済むため）
  - `npm run dev` の監視中は README を直しても変換し直さないので、dev を起動し直す
- 「使い方を開く」で、`README.md` が無ければ作り、中身がプラグインの版と違えば上書きしてから開く
  - 判定は `commands/readmeContent.ts`。改行コードの違いは見ない（SVN の取り出しで CRLF になっても書き直さない）
- 見出しの次に「プラグインが作るので直接書き換えない」注意書きを入れる（次に開くと元に戻るため）
- 古いプラグインの人が開くと古い中身に戻り、SVN の差分になる。全員のプラグインをそろえる運用が前提

設定画面：

- 並び：保存先で大きく2つに分け、その中を内容で分ける（誰に影響するかが一目で分かるように）
  - このパソコンだけの設定：表示（プロジェクトの表示名・ノートを開く場所・左枠の幅）／HTMLレポート
  - 全員共通の設定：ステータス → 会社カレンダー → 種類ごとの色 → フォルダ
- グループ（`ui/settingGroups.ts`）：見出しを押すと開閉する枠（`<details>`）。中は左の線で入れ子を示す
  - 公式の `SettingGroup`（1.11〜）は入れ子と開閉ができず、対応バージョンも上げる必要があるため自作した
  - 初めは外側の2つだけ開く。描き直しても開閉は変わらない
  - 開閉は WBS と同じく「初期と逆にしたキー」で、ローカルストレージ（`project-manager:setting-groups`）に覚える
- ファイル：共有設定を変える欄（ステータス・会社カレンダー）は `ui/sharedConfigSettings.ts`
  - それ以外（個人の設定・色・フォルダ）は `ui/settingsTab.ts`（規約 2章の300行を超えたため分けた）

### 9.1 ビューの土台（`views/baseView.ts` ほか）

描き直し：

- すべてのビューは `PmView` を継承し、`draw(el, ctx)` だけを書く
  - 索引・共有設定が変わったら描き直す。読み込み中・例外の表示・スクロール位置の保持は `PmView` が行う
- `ctx`（`calc/context.ts`）は作業ログの集計（11.1）・稼働日・プロジェクトの一覧・計算上の日程（11.9）
  - 開いているビューの数だけ作り直さないよう、変わるまで使い回す（11章の `ContextCache`）
- 見えていないビュー（裏のタブ・たたんだ横の欄）は、索引が変わっても描き直さず、見えたときに描く
  - 判定は `contentEl.isShown()`。`active-leaf-change`・`layout-change`・`onResize` で確かめる
  - 最初の1回は見えていなくても描く

絞り込み：

- 絞り込み（`calc/filter.ts`）はビューの状態（`getState`/`setState`）として Obsidian に保存する
  - タブを閉じるまで、再起動しても残る。保存先は `.obsidian/workspace.json`（svn:ignore の対象）
- 判定は純粋関数（`filterTasks`, `filterProjects`）
  - クローズ済み＝ステータスが完了系のプロジェクト
  - 期間はタスクの開始日〜期限日と重なるもの（日付の無いタスクは、期間を指定したときは対象外）
  - ステータスは旧名を現在の名前にそろえて比べる
- 部品（`views/filterBar.ts`）は、ビューごとに出す項目を選ぶ。複数選択は「×で外す・プルダウンで追加」

作成・編集の呼び出し（要件 4.2）：

- 各ビューのシェルの操作の欄に作成のボタン（`views/actions.ts`）を置く
- 1つに絞り込んでいるプロジェクト・エピックは、作成画面で最初から選んでおく（`NewNoteModal` の `initial`）
  - 選択肢に無いアーカイブ内のものは選ばない
- 編集は入力補助フォームなどの画面（ノートを開くのは最後の手段。4.9）
- 警告一覧は直すための画面なので、作成のボタンは置かない

| ビュー | 作成・入力 | 編集 |
| --- | --- | --- |
| タスク一覧 | 新しいタスク、作業ログを入力 | 行のクリック（ノート／フォームの切り替え） |
| メンバー状況 | 作業ログを入力、新しいメンバー | メンバー名の横の「フォーム」 |
| プロジェクト状況 | 新しいエピック・タスク（このプロジェクトを選んでおく）、新しいプロジェクト、エピックの行の「＋タスク」 | エピックの行と開いたタスクの行の「フォーム」 |
| ダッシュボード | 作業ログを入力、新しいプロジェクト | — |
| カンバン | 新しいタスク（1つに決まっていれば選んでおく）、作業ログを入力 | カードの「フォーム」 |
| WBS | 新しいプロジェクト、プロジェクトの行の「＋エピック」、エピックの行の「＋タスク」 | タスクの行の「フォーム」 |
| ガントチャート | プロジェクトの行の「＋エピック」、エピックの行の「＋タスク」（9.8） | エピック・タスクの行の「フォーム」 |

シェル（`PmView.shell`）：

- どのビューも同じ並びの枠で描く。ビューは返された欄に中身を入れるだけで、置く場所を決めない
  - ビューごとにボタンの位置がばらつかないように。新しい機能も同じ場所に置ける
- 上に固定する欄（上から）
  1. 見出し：ビューの名前、一行の説明（`getDescription`）、右端に件数など（`summary`）
  2. 絞り込み（`filters`）：`renderFilterBar`、プロジェクト状況・アーカイブ対象のプロジェクトの選択
  3. 左に表示の設定（`settings`）、右に操作のボタン（`actions`）
     - 表示の設定：単位・グループ・すべて開く／閉じる・表示の切り替え
     - 操作のボタン：作成・入力・書き出し・ほかの画面へ
  4. 凡例・注意（`notes`）
- 中身の無い欄は出さない（CSS の `:empty`）。上の欄と本体の間に区切りの線を引く
- 「罫線を表示」は、表示の設定の後ろにある専用の欄に置く（並び順を CSS で入れ替えない）
  - `shell(el, { grid: true })` を渡したビューだけ。カンバン・警告一覧は表が無いので出さない
- 操作のボタン（`actionButtons`）は操作の欄にそのまま並べ、入れ物を重ねない
- 共通のクラス：節の見出しの行 `pm-section-head`、凡例 `pm-legend`、注意書き `pm-note`
- 入力欄の部品（プルダウン・期間・チェック・つまみ `rangeSlider`）は `views/filterBar.ts`
- 表のビューは「上に固定する欄（シェル）」と「スクロールする欄（表）」に分ける
  - スクロールしても絞り込みと表の見出しが見えるように
  - 表の見出しはスクロールする欄の上端に、メンバー状況のメンバー名の列は左端に固定する
  - 描き直しでは、スクロールする欄の縦横の位置も保つ

数字と印（`views/format.ts`：文字の組み立て。テストあり。`views/badges.ts`：画面の部品）：

- 時間は 3けた区切り、小数は2けたまで（`hoursText`。例：8,123.5）。表・説明・グラフ・HTMLレポートで使う
- 割合は `rateText`、タスク1件の進捗（完了／チェックリストの割合）は `subtaskText`
- タスク一覧・WBS・プロジェクト状況の進捗の値は、押すとチェックリストの編集画面（4.10）を開く
  - `subtaskCell`。動かすリンクで、行のクリックとは別に動く
- 進捗率は横棒と文字（`progressBar`。60px の棒の長さを `--pm-ratio` で渡す）
  - ダッシュボード・プロジェクト状況・WBS のプロジェクトとエピック・HTMLレポート
  - 表の中では、棒をセルの左端、文字を右端に置く。棒は縮めない（`flex: none`）
  - 文字の長さで棒の位置がずれ、狭い列で棒が縮んだため
  - 文字は％（`pm-progress-pct`。同じ幅の欄に右寄せ）と件数（`pm-progress-count`。左寄せ）に分ける
  - 行どうしで％と「（」の位置がそろう。HTMLレポートも同じ
- ステータスの枠（`statusBadge`。ビューからは `PmView.statusCell`）
  - 枠線と薄い背景はステータスの色（6章）、文字は通常の色
  - 付ける：タスク一覧・プロジェクト状況・WBS・ダッシュボード・HTMLレポート
  - 付けない：カンバンの列の見出し、文の中のステータス（マイルストーンの「エピックの状況」など）
  - 設定に無いステータスは枠を付けず、注意の色の文字
- 警告は種類ごとの小さな印（`warningBadges`）。名前と件数を必ず書く（色だけに頼らない）
  - 重いものから：期限超過＝赤、期限超過見込み＝橙、工数超過＝黄、そのほか＝紫
  - タスクの行は件数なしの印（`taskWarningCell`）で、マウスを乗せると警告の文
- 種類の色の印（`kindMark`）：プロジェクト・エピック・タスクのタイトルの前に、設定の色の小さな丸
  - ダッシュボード・タスク一覧・カンバン・プロジェクト状況・WBS・ガント・アーカイブ対象・HTMLレポート
  - タイトルではない列（タスク一覧の「プロジェクト」列など）には付けない

休みの印（`holidayMark`・`dateCell`・`periodText`・`periodCells`）：

- 一覧の日付が休日なら、後ろに種類ごとの印を付け、マウスを乗せると理由を出す
  - 例：「会社休日：文化の日」「個人休日：佐藤（有給）」「土日休日：土曜」
  - 休日に置いた開始日は計算で次の稼働日にずれる（要件 4.7）ので、一覧で気づけるようにする
- 種類は社休＝橙・個休＝紫・土日＝灰。色だけに頼らず文字も変える。判定は `WorkCalendar.holidayMarks`（11.2）
- 個人休日はその行の人で見る（ID からメンバーを引くのは `views/format.ts` の `membersOf`）
  - タスクは担当者（だれか1人でも休みなら付ける）、エピックは `owner`、プロジェクトは `manager`
  - マイルストーンの日付は人がいないので見ない
- 付ける場所：タスク一覧・プロジェクト状況・WBS・ダッシュボード・カンバンのカードの期限
  - 入力フォームの日付欄には付けない。メンバー状況にも付けない（9.3）
- 表の中の期間（ダッシュボード）は、開始日と「〜 期限日」を別のセルに分ける（`periodCells`）
  - 1つのセルだと、開始日の印の数で「〜」と期限日の位置が行ごとにずれるため
  - 見出しは2列ぶんの「期間」。間の罫線と余白は消して1つに見せる
  - 表でない場所（プロジェクト状況の概要）は `periodText` で1つの文字列にする

警告から直す場所への導線（`views/warningLink.ts`）：

- 警告の印をクリックすると、タスク一覧をそのプロジェクト（エピック）・警告ありのみで開く
  - 場所：ダッシュボードのプロジェクトの行、プロジェクト状況の概要とエピックの行、WBS のプロジェクト・エピックの行
  - クローズ済み・アーカイブ内のタスクも出す（警告の件数に入っているため）
  - タスク一覧のグループ・並べ替え・行のクリックの動きは残す
- 配分超過はタスクの警告ではないので、配分超過だけのときはプロジェクト状況へ動かす
  - プロジェクト状況の中では工数配分の表へ
- リンクは警告の印だけ（セルの余白を押しても動かない）。行のクリック（画面の移動）とは別に動く
- タスク一覧の件数はタスクの数なので、1つのタスクに警告が2つあると警告の件数より少なくなる

表の見た目：

- 見出しはすべて中央にそろえる（`.pm-table th` と `th.is-numeric`）。HTMLレポートとガントの月の見出しも
  - はじめは一部の表だけ頼まれたが、同じ種類の表すべてに広がったので表全体の決まりにした
- 罫線：表の画面のマスの縦横に、うっすらした罫線を出す
  - 対象：タスク一覧・メンバー状況・プロジェクト状況・ダッシュボード・WBS・ガント・アーカイブ対象
  - 色は `--pm-grid-color`＝`rgba(var(--mono-rgb-100), 0.08)`（テーマの明暗に合わせて薄く見える）
  - 「罫線を表示」で消せる。ビューの状態（`gridLines`、初期は表示）で、「条件をクリア」でも変わらない
  - 消したときは行の区切りの線も出さない
  - ガントは行の横線と、期間の区切りの縦線。縦線は期間の数だけ行の後ろに置き、行ごとには作らない（数千行でも軽く）
  - プロジェクトの行の背景は、縦線が透けるよう半透明にする
- 開閉：WBS・ガント・プロジェクト状況の階層は、▶／▼ の印（`toggleMark`。`views/actions.ts`）を押したときだけ開閉する
  - 行のほかの場所では開閉しない（タイトルや警告のリンクと押し間違えないように）
  - カンバンの列のたたみ（見出しのクリック）は階層ではないので別
- 色・余白・印・リンクの書き方は [UI_STYLE_GUIDE.md](UI_STYLE_GUIDE.md)。決めた理由：
  - 機能を足すたびに個別に決めてきたため、印が7通り、薄い背景の濃さが5通り、押せるものが5通り、赤が2種類に分かれていた
  - 押せるものは名前以外ふだん通常の色にした（表の数字やガントの表示名を青にすると画面が青くなりすぎる）
  - 点線の下線は見づらいので使わない
  - 赤は `--color-red` に1つ（`--text-error` はテーマで色味が違い、ガントの棒の赤と並ぶとずれて見える）

ノートを開く（`views/openNote.ts`、`views/paneLeaf.ts`）：

- ノートは個人の設定の場所（右枠／新しいタブ／別ウィンドウ）で開く。警告一覧も同じ（作成は開かない。4.4）
- ビューを見ながら隣でノートを編集できるよう、中央の編集領域を左右の枠に分けて使う
- 枠：中央のタブ（`iterateRootLeaves`）を並び順に見て、親（タブのまとまり）ごとにまとめたもの（`groupsInOrder`）
  - 最初の枠を左枠、最後の枠を右枠とする。サイドバーと別ウィンドウは対象外
- ビュー（`openView`）：すでに開いていればその場所のまま表示する（動かした位置を尊重）。無ければ左枠に開く
- ノート（`openNote`、設定が「右枠」）：枠が2つ以上なら右枠に開く。1つなら、その右に縦に分割して開く
- クリックの種類（`noteClick`。ノートを開くだけなら `noteLink`）
  - 左クリックは右枠で表示中のノートを差し替える（タブが増え続けないように）
  - 中クリックと Ctrl＋クリックは右枠に新しいタブを作る（Obsidian の普段の操作に合わせる）
  - 表示中のタブがノート・空のタブ以外か、固定（ピン留め）されているときは新しいタブにする
  - 設定が「新しいタブ」なら左クリックも新しいタブ、「別ウィンドウ」なら中クリックだけ新しいタブ
  - 「ノートを開く」などのボタンは左クリックだけ。中ボタンを押したときの自動スクロールは止める
- 枠の中に空のタブがあればそれを使う
  - 無ければその枠で表示中のタブを（フォーカスを移さずに）アクティブにしてから `getLeaf('tab')` で作る
  - 特定のタブのまとまりにタブを足す公開 API が無いため
- 左枠の幅（個人の設定 `paneRatio`、30〜80% の5%刻み、初期値60%）
  - ノートを開くときに分割したときと、設定のつまみを動かしたときだけ当てはめる（`applyPaneRatio`）
  - そのあとマウスで動かした幅は尊重し、ノートを開くたびには戻さない
  - 中央の枠がちょうど2つで同じ親の中にあるときだけ当てはめる
  - 幅を変える公開 API が無いので、非公開の `setDimension` を使う
  - 無ければ何もしない（将来の Obsidian で変わっても、幅が変わらなくなるだけ）
  - 左右の値は合計100にし、`requestSaveLayout` で画面の配置の保存を頼む

### 9.2 タスク一覧（`views/taskListView.ts`）

- 計算は 11.6。ビューは表を描くだけ
- 計算上の日程のセル（`views/scheduleCells.ts`。プロジェクト状況・WBS でも使う）
  - 遅れでずれた開始日・終了日はそれぞれ橙（`startDelayed`・`endDelayed`。11.9）
  - 期限日より後の終了日は赤。両方に当たるときは赤にし、説明には両方の理由を出す
  - 完了系・停止系は期限日より後でも赤にしない（期限超過見込みと同じ）
  - 期限日のセル（`dueCell`）は期限超過なら赤にし、警告の文を説明に出す
- 絞り込みは共通の部品に、タスク一覧だけの項目（エピック・期限日の範囲・警告ありのみ）を足す
  - 共通：プロジェクト・担当者・ステータス・クローズ済み・アーカイブ
  - 「条件をクリア」は両方を消すが、グループ・並べ替え・行のクリックの動きは残す
- タスク一覧だけの条件（`TaskListOptions`）も、ビューの状態として保存する
- 100行ずつ出し、「さらに表示」で100行ずつ増やす（要件 4.8）
  - 条件を変えたら100行に戻す。データの更新で描き直したときは、出している行数を保つ

### 9.6 カンバン（`views/kanbanView.ts`）

- 計算は 11.11。列はタスク用ステータス（設定の並び順）。列の中は期限日の早い順
- 絞り込みはタスク一覧と同じ（`views/taskFilters.ts` の部品を共通で使う）
- 完了系・停止系の列は初めからたたむ。見出しのクリックで開閉する
  - 初期と逆にした列の名前（`toggled`）をビューの状態として保存する。「条件をクリア」でも残す
- 列の見出し（ステータス名・件数）は、スクロールしても上に残す（`position: sticky`）
  - 列の余白の分まで背景を塗り、下を流れるカードを隠す
  - 列はいちばん長い列と同じ高さにそろえる（sticky は親の列の中でしか残らないため）
  - 背景（枠）はカードのあるところまで：列は透明にし、見出しとカードの欄（`.pm-kanban-cards`）だけ塗る
- 列の幅：表示の設定の「列の幅」のつまみで、すべての列をそろえて変える
  - 160〜520px、20px 刻み、初期値 260px。「元に戻す」で初期値。「条件をクリア」でも変わらない
  - 動かしている間は CSS 変数（`--pm-kanban-col`）だけ変え、離したときに保存する（`columnWidth`）
  - 数百枚のカードを描き直すと重いため
  - たたんだ列も同じ幅（開け閉めで横の並びがずれないように）
- 「画面の幅に合わせる」：押したときの画面の幅にすべての列が収まる幅を計算して保存する
  - （幅 − 列の間 ×（列の数 − 1））÷ 列の数。範囲の外なら端の値（収まらなければ横にスクロール）
  - 画面の大きさを変えても自動では追いかけない
- 列ごとに50枚ずつ出し、「さらに表示」で増やす（保存しない。絞り込みを変えたら戻す）
  - 進行中だけで数百枚になり得るため
- カードのクリックでノートを開く。「フォーム」で入力補助フォーム

カードのドラッグ＆ドロップ（要件 4.8c）：

- ほかの列に落とすと、そのタスクの `status` だけを列のステータス名に書き換える（`writeFrontmatter`。4.1）
- たたんだ列にも落とせる（完了の列はたたんであることが多いため）。落とせる列は点線の枠で示す
- 同じ列なら何もしない。「設定に無いステータス」の列には落とせない
- 書き込んだらお知らせを出し、描き直しは索引の更新に任せる
- 取り消す操作は作らない（もう一度動かせば戻せる）。確認の画面も出さない（よく使う操作のため）
- ドラッグのデータは独自の種類（`application/x-pm-task`）で渡す（ノートに落としても文字が貼られないように）
- 落とされたデータは `parseDraggedCard`（`calc/kanban.ts`）で形を確かめてから使う（規約 4章）

### 9.7 WBS（`views/wbsView.ts`）

- 計算は 11.12。1つの表に、プロジェクト・エピック・タスクの行を字下げして並べる
- ▶／▼ で開閉（初期はプロジェクトだけ開く）。初期と逆にした行のキーをビューの状態として保存する
  - エピックの開閉は、表全体を描き直さず、そのエピックのタスクの行だけを足す・消す（`toggleEpic`）
  - 開いているエピックが多いと、全体の描き直しが重いため（約3,500タスクのデータで目立った）
  - プロジェクトの開閉・「すべて開く」「すべて閉じる」・ファイルの変更では全体を描き直す
  - 「すべて開く」「すべて閉じる」もある
- タイトルはリンク：プロジェクトはプロジェクト状況を、エピックはノートを開く
- タスクの行のクリックはノート、「フォーム」で入力補助フォーム
- プロジェクトの行に「＋エピック」、エピックの行に「フォーム」と「＋タスク」
- 担当者の列：プロジェクトは責任者（`manager`）、エピックは担当者（`owner`）
- コマンド名「WBSを開く」は lint の sentence-case の警告が出るが、要件の画面名どおり「WBS」のままにする
- タスクの WBS の列は「エピックの番号.連番」（`taskWbsLabel`）。ガントの表示名の先頭にも付ける
- エピック・タスクの行のドラッグで番号を入れ替える（`views/wbsDrag.ts` の `WbsDrag`。計算は 11.17）
  - ガント（9.8）・プロジェクト状況（9.4）でも同じ `WbsDrag` を使う
  - ガントでつかめるのは左の表示名の欄だけ（棒の欄は日程を見る場所のため）。落とす先は行全体
  - 行全体をドラッグできる。落とす先の行の上半分なら前、下半分なら後ろに置き、行の上か下に線を出す
  - 落とせるのは同じまとまり（エピックは同じプロジェクト、タスクは同じエピック）の行だけ
  - dragover ではドラッグの中身を読めないので、ドラッグ中の行はビューの側で持つ
  - 書き込むのは番号が変わるノートだけ（SVN の差分を小さくするため）。描き直しは索引の更新に任せる
  - 絞り込みで隠れた行も含めた全体の並びで振り直す（隠れた行の番号が重ならないように）
  - 取り消す操作・確認の画面は作らない（カンバンと同じく、もう一度動かせば戻せるため）

### 9.8 ガントチャート（`views/ganttView.ts`, `views/ganttParts.ts`）

作り：

- ビュー（行の階層・開閉・状態）は `ganttView.ts`、見出し・棒・印・依存の線は `ganttParts.ts`（300行の決まり）
- 計算は 11.13。行の階層・開閉・絞り込みは WBS（9.7）と同じ（`wbsTree`）。開閉の状態は WBS と別に保存する
- 表ではなく `div` の行で描く
  - 左に表示名の欄（幅 320px、横にスクロールしても左に固定）、右に横軸の欄
  - 見出し（上の段に月、下の段に日・週・月）は上に固定する
  - 日の単位の見出しは日付の数字だけにし、曜日はマウスを乗せると出す（1日 28px に収めるため）
- エピックの開閉は全体を描き直さず、タスクの行だけを足す・消す（9.7 と同じ理由）
  - 足した棒には `dependencyLines` の戻り値で依存の線の仕掛けを付け、消した棒は線の対象から外す
- タスクの番号は名前と別の欄（`pm-gantt-wbs`）に入れ、表示中でいちばん長い番号の幅にそろえる
  - 番号のけたが違っても、名前の頭がそろうようにするため
- 棒・印の位置と幅は、計算した px を CSS 変数（`--pm-x`・`--pm-w`）で渡す（`el.style` に書かない）

棒と印：

- 棒の色は種類ごとの設定の色（6章）。状態の色が優先する（問題に気づきやすくするため）
  - 遅れを反映＝橙、期限日より後＝赤、完了・停止＝薄いグレー（9.2 の日程のセルと同じ決まり）
  - CSS では行のクラスで `--pm-bar-color` を決め、状態のクラスが後から上書きする
- エピック・プロジェクトの棒は細く、配下のタスクの最初〜最後
- 期限日は赤い縦線、マイルストーンは ◆（遅れは橙、未達は赤）、今日は緑の縦線
- 範囲からはみ出した棒は、はみ出した側の角を丸めない
- 休日（単位が日のとき）は、見出しのマスと同じ色（`--background-secondary`）の縦の帯を下端まで引く
  - 罫線の縦線と同じく、期間の数だけ行の後ろに置く。罫線の切り替えに関係なく出す

依存：

- 線は SVG を重ねて描く。棒を指している間だけ、そのタスクの先行・後続との間に線を引く
  - 線の位置は描いた後の棒の位置（`getBoundingClientRect`）から求める
  - 矢印の印の ID はガントごとに変える（2つ開いても重ならないように）
  - 相手が閉じた行・絞り込みで見えないときは線を引かず、上の注意欄に件数を出す
- 注意欄は初めから1行の高さに固定し、案内の文を出しておく（高さが変わると棒の位置がずれるため）
- 依存のあるタスク（`dependencyFlags`。11.13）の印
  - 棒の左端に丸（先行あり）・右端に丸（後続あり）、表示名の後ろに「⇆」
  - 表示名の前に置くと、表示名の頭がそろわないため後ろにした
  - 棒が表示期間の外でも分かるよう表示名にも出す。表示名が長いときは表示名を「…」で省略する
  - マウスを乗せたときの説明にも「先行タスクあり・後続タスクあり」を出す
  - 「依存の印を表示」で出し入れし、初期は出さない（目立ちすぎるため）
  - 切り替えはビューの状態で、「条件をクリア」でも残す。指したときの線は切り替えに関係なく出す

操作：

- 棒は見るだけ（要件 4.2）。タイトルのクリックでノート（プロジェクトはプロジェクト状況）を開く
- 表示名の欄の右端のボタン（`rowButton`。WBS・プロジェクト状況とそろえる）
  - エピック・タスクの行：「フォーム」で入力補助フォーム
  - エピックの行：「フォーム」の右に「＋タスク」（プロジェクトとエピックを選んだ作成画面）
  - 「（エピックなし）」の行にも「＋タスク」を置き、エピックは選ばない
  - プロジェクトの行：「＋エピック」。「フォーム」は置かない（プロジェクト状況にあるため）
  - 長い表示名は「…」で省略し、ボタンは必ず見えるようにする
- 表示期間・単位も状態として保存する
  - 「プロジェクトの期間に合わせる」：プロジェクトの開始日・期限日とタスクの日程の最初〜最後にする
  - 「条件をクリア」は表示期間を初期値に戻す（単位と開閉は残す）

### 9.9 アーカイブ対象（`views/archiveView.ts`）

- 計算は 11.14。プラグインはファイルを動かさず、移動するファイルと移動先を出すだけ（要件 4.9）
  - SVN の「移動」でないと履歴が途切れるため、移動は各自が TortoiseSVN で行う
- 上のプルダウンでクローズ済みのプロジェクトを選ぶ（ビューの状態として保存）
- 移動元のフォルダごとに表を分け、「移動元 → 移動先（件数）」の見出しと「ファイル名をコピー」を付ける
  - TortoiseSVN ではフォルダを開いてファイルを選び、右ボタンのドラッグで「ここに移動」するため
- 画面の上に TortoiseSVN での移動の手順を出す（エンジニア以外も使うため）
- svn のコマンドを使える人向けに「移動のコマンドをコピー（svn move）」も置く
  - `svn move --parents` を1ファイル1行。実行はしない
- 行のクリックでノートを開く。注意（完了系・停止系でない、移動先に同じ名前がある）は橙で出す
- 移動してコミットすると、索引の更新でアーカイブ内と判定され、一覧から消える
  - 全部消えたプロジェクトは選択肢からも消える
- 呼び出し：リボンのメニュー、コマンド、クローズ済みのプロジェクトのプロジェクト状況の「アーカイブ対象を見る」

## 10. ID（`id/`）

- ファイル名 = `接頭辞-UUID v7`（作業ログは `USER-UUID_YYYY-MM`）
  - v7 は先頭48ビットが作成時刻なので、並べると作成順になる
- 依存ライブラリを増やさないため UUID v7 は自前で書く。乱数は `crypto.getRandomValues`
- 重複していたら作り直す（10回重複したらエラー）

## 11. 計算（`calc/`）

- 計算結果はファイルにも索引にも保存せず、表示のたびに計算する（要件 3.7）
- 日付はすべて `YYYY-MM-DD` の文字列で扱い、計算の中だけ UTC の時刻に直す（タイムゾーンでずれないため）
- 「今日」は呼び出し側が渡す（`localToday()`。テストで日付を固定できるように）
- 計算用のデータ（`CalcContext`：日程・作業ログの集計など）は `ContextCache`（`context.ts`）で使い回す
  - 索引・共有設定・今日が変わるまで。開いているビューがそれぞれ同じ計算をしないため
  - 索引の変化は `VaultIndex.version`（追加・削除のたびに増える番号）で見る
  - 共有設定の変化は `statuses`・`calendar` のオブジェクトが入れ替わったかで見る（`load` で必ず新しくなる）
- 並べ替えの文字の比較は `compare.ts` を使う
  - `compareJa`（氏名・タイトル）、`compareNumeric`（数字を数として比べる。プロジェクト名・WBS番号）
  - `localeCompare` に言語を渡すと比較のたびに比較器を作り、数千件で遅くなるため
  - 日付・パスの比較は言語に関係ないのでそのまま

### 11.1 作業ログの集計（`worklogSummary.ts`）

- `WorkSummary` は作業ログ全体を一度だけ読み、予定・実績を合計する
  - タスク別、メンバー×日付×プロジェクト別、プロジェクト×月×メンバー別
- 同じ日付・同じタスクの行は合算する（要件 3.5）
- 記録のプロジェクトは、タスクの所属（`task.project`）で決める
  - タスクが見つからない記録は「所属不明」（`UNKNOWN_PROJECT`）として、メンバーの負荷には入れる
- タスクの所属を引くため、アーカイブ内のタスクも含めて渡す

### 11.2 稼働日と期間（`workdays.ts`, `dates.ts`）

- 稼働日：土日（設定で休日にしているとき）と会社の休日以外。個人休日は入れない（要件 3.6。印だけ）
- 休日の印の判定（`holidayMarks(date, members)`）：その日の休日を種類（会社・個人・土日）の順に返す
  - 個人休日は渡したメンバーの休みをまとめて1つにし、理由は「佐藤（有給）、伊藤」のように名前とメモ
- 期間は日・週（月曜始まり）・月。識別子は、日・週は開始日、月は `YYYY-MM`
- メンバー状況の表示期間の初期値は、前月の初日〜3か月先の末日（要件 4.8）

### 11.3 進捗率と工数の状況（`progress.ts`）

- タスク：完了系なら完了。サブタスクの完了割合は参考として別に返す（要件 4.3）
- エピック・プロジェクト：完了系の件数 ÷ 対象件数。停止系は分母から除く
  - 設定に無いステータスは未完了として分母に入れる（要件 4.8）。対象が0件なら進捗率なし
- ステータスは名前ではなく分類で判定する（旧名も分類に引き当てる。5.4）
- 見積・予定・実績の合計は、停止系のタスクも含めて数える

### 11.4 警告（`warnings.ts`）

- 期限超過：期限日の翌日以降で、完了系でも停止系でもない（要件 4.4, 4.8）
  - 停止系は進捗率の分母から外すのと同じ考え方。設定に無いステータスは対象にする
- 工数超過：実績の合計が見積を超えている（見積が無いタスクは対象外）
- 配分超過：工数配分表の行（プロジェクト×月×メンバー）ごとに、予定の合計が配分を超えている
  - 配分表に無いメンバーの予定は対象外
- 負荷注意・負荷警告：予定負荷率で判定する（11.5）
- 休日稼働：休日に予定か実績が入っている日（0h だけの日は出さない）
- 期限超過見込み：計算上の終了日が期限日より後（11.9）
- 警告は対象（タスク、プロジェクト×月×メンバー、メンバー×期間、メンバー×日付）を持ち、ビューで対象の行やセルに出す

### 11.5 負荷（`load.ts`）

- 基準工数（100%）＝ 期間内の稼働日数 × 1日の通常稼働時間
  - 休日だけの期間（休日の「日」）は基準工数0で、負荷率なし
- 予定負荷率・実績稼働率は、稼働日の予定・実績だけで計算する
  - 休日の記録は負荷率に入れず、休日稼働として別に示す（要件 4.5）
- 段階：100%以下（normal）、100%超（caution＝負荷注意）、負荷許容率超（warning＝負荷警告）
- プロジェクト別の内訳は、稼働日と休日の両方を合計する（セルをクリックしたときの内訳。要件 4.8）

### 11.6 タスク一覧（`taskList.ts`）

- `taskRows` がタスクごとに所属・現在のステータス名・担当者・工数・進捗・警告をまとめる
  - 絞り込み（`filterTaskRows`）→並べ替え（`sortTaskRows`）→グループ分け（`groupTaskRows`）の順に通す
- 期限日の範囲を指定したときは、期限日の無いタスクは対象外
  - 共通の「期間」（開始日〜期限日との重なり）はタスク一覧では使わない（要件 4.8 の絞り込みは期限日）
- 並べ替え
  - 値の無いもの（期限日・見積・エピックなど）は昇順・降順どちらでも最後。同じ値ならタイトル順
  - ステータスは設定の並び順、エピックは「WBS タイトル」を数字として比べる（1.2 → 1.10）
  - 進捗は完了＝1、それ以外はサブタスクの完了割合（無ければ0）
- グループ
  - 名前順で、「（エピックなし）」「（担当者なし）」「（見つからない…）」は最後。ステータスは設定の並び順
  - 担当者が複数のタスクは、それぞれの担当者のグループに出す（抱えている仕事を見るため）
- 見つからない担当者（メンバーノートが無いID）は担当者の列に出さない（健全性チェックで警告済み）

### 11.7 メンバー状況（`memberStatus.ts`）

- `memberStatusTable` がメンバー×期間ごとに `memberLoad`（11.5）を呼ぶ
  - 期間の端は範囲からはみ出してよい（表示期間の途中から始まる週も1週として数える）
- 表示期間は、指定が無ければ前月〜3か月先（11.2）。逆転していれば入れ替える
- プロジェクトで絞り込んだときの「関わるメンバー」（要件 4.8）。アーカイブ内のタスクも含める
  - そのプロジェクトのタスクの担当者、工数配分表のメンバー、責任者（`manager`）
  - そのプロジェクトのタスクに作業ログを付けた人
- 負荷率は、絞り込んだプロジェクトの分だけでなく、そのメンバーの全プロジェクトの合計で出す
  - 負荷はメンバー全体で見るもののため

### 11.8 プロジェクト状況（`projectStatus.ts`）

- 対象はそのプロジェクトのエピック・タスク（アーカイブ内も含む。アーカイブしたプロジェクトも見られるように）
- 全体・エピックごとに、進捗率（11.3）、工数の合計、警告をまとめる。全体の警告はタスクの警告と配分超過
- エピックは WBS 順（数字として比べる。WBS の無いエピックは後ろ、同じならタイトル順）
  - エピックの無いタスク（エピックが見つからないものも）は最後に「エピックなし」としてまとめる
- マイルストーンは日付順。連動エピックについて次を出す
  - 遅れ：完了予定日がマイルストーンの日付より後
  - 未達：マイルストーンの日付を過ぎたのにエピックが完了系でない
  - 警告（11.4）には数えず、マイルストーン一覧の注意として出すだけ
- 配分表：配分表の行と、作業ログにこのプロジェクトの予定・実績がある月×メンバーを合わせて表にする
  - 配分の無い予定も見えるように。同じ月・メンバーの配分行が複数あれば合計する

### 11.9 日程（`schedule.ts`）

- 決まりは要件 4.7「日程計算の細かい決まり」
- `computeSchedules` が全タスクの計算上の開始日・終了日を出し、`CalcContext.schedule` に入れる
  - アーカイブ内も含む（先行を引くため）。ファイルにも索引にも保存しない
- 先行の日程を先に計算する（メモ化した再帰）。先行の終了日は遅れを反映した後の値を使う
  - 遅れは後続へ順に伝わる
- 稼働日の数え方は `WorkCalendar.addWorkdays`（n 稼働日進める。0 ならそのまま）と `workdayOnOrAfter`
  - 休日なら次／前の稼働日。休日ばかりのカレンダーで止まらないよう、探すのは10年分まで
- `lag_days` は先行の終了日から数える（0 なら同じ日。休日なら次の稼働日）。所要日数0は1日として扱う
- 遅れ
  - 未着手（分類 not_started）で開始日が今日より前なら、開始日を今日（休日なら次の稼働日）にずらす
  - 完了系でないタスクの終了日が今日より前なら、今日まで延ばす
- 遅れの印は開始日・終了日で別々に持つ
  - `startDelayed`：自分が未着手でずらした、または最も遅い先行の終了日が遅れでずれていた
  - `endDelayed`：今日まで延ばした、または開始日のずれが終了日に伝わった（所要日数で決まるとき）
  - 期限日が終了日のときは、開始日のずれは伝わらない
- 設定に無いステータスのタスクは、開始日をずらさないが、終了日は今日まで延ばす（完了系ではないため）
- 先行が見つからないID（健全性チェックで警告済み）は無いものとして扱う
  - 先行の日程が出せなければ、後続も日程なし
- 循環（`findCycles`、Tarjan の強連結成分）に入るタスクは日程なし
  - 健全性チェックで、循環に入るタスクごとに経路つきで警告する（自分自身への依存は従来の警告のみ）
- 期限超過見込み（`taskWarnings` の `schedule`）：計算上の終了日が期限日より後で、完了系・停止系でない
  - 期限日を過ぎていれば期限超過だけを出す

### 11.10 ダッシュボード（`dashboard.ts`）

- プロジェクトごとに `projectStatus`（11.8）を呼ぶ。対象はビューの絞り込み（既定はクローズ済み・アーカイブ内を除く）
- 負荷の高いメンバー（HTMLレポート用）：在籍者のうち、今週か今月の**予定負荷率**が注意・警告の人
  - 今週は月曜始まりで今日を含む週。日曜に開くと前日までの週になる
- マイルストーン：表示するプロジェクトの、今日〜14日後のもの

### 11.11 カンバン（`kanban.ts`）

- `kanbanColumns` が、タスク一覧と同じ行（11.6）をステータスの列に分ける。旧名は現在の名前の列に入る
- タスクの無い列も出す（ステータスの流れ全体を見せるため）
- 設定に無いステータスのタスクは、最後の「設定に無いステータス」の列にまとめる（あるときだけ）
- カードを動かしたときに書く値（`statusMove`）：動かした先の列のステータス名
  - 今の列は旧名を現在の名前にそろえて比べるので、旧名のタスクを同じ列に落としても書き換えない
  - 「設定に無いステータス」の列から設定のある列へは動かせる（直すため）が、逆はできない

### 11.12 WBS（`wbs.ts`）

- プロジェクトごとに `projectStatus`（11.8）のエピックの行を使う（WBS順、エピックなしは最後）
- タスクは WBS 番号順。番号の無いものは後ろに、計算上の開始日の順（日程なしは最後。11.17）
- 担当者・ステータスで絞り込んだときは、合うタスクだけを出し、合うタスクの無いエピックは出さない
  - 進捗・見積・期間・警告は、エピック・プロジェクト全体の値のまま（絞り込みで変わると誤解しやすいため）
- WBS とガントで共通：絞り込みからの階層（`wbsTreeFor`）、開閉の状態
  - 開閉は、初期と逆にした行のキーの集合（`isOpen`・`toggledForAll`・`parseToggled`）

### 11.13 ガントチャート（`gantt.ts`）

- 横軸（`ganttScale`）は表示期間を期間の区切りまで広げる（週なら月曜〜日曜、月なら月初〜月末）
  - 1日の幅は日 28px・週 8px・月 3px
- 棒（`barBox`）は開始日の左端から終了日の右端まで（両端を含む）
  - 範囲からはみ出した側は切り、重ならなければ出さない。印（`markX`）はその日の中央
- 表示期間はメンバー状況と同じ `displayRange`（初期値は前月〜3か月先。11.7）
- 依存（`dependencyLinks`）：先行は `depends_on`、後続はそのタスクを `depends_on` に持つタスク
  - アーカイブ内のタスクも含めて探す
- 依存の有無（`dependencyFlags`）：全タスクを1回見て、先行があるか・後続があるかを出す
  - 見つからない先行と自分自身への依存は数えない（線を引けないため）

### 11.14 アーカイブ対象（`archive.ts`）

- 対象（`archivePlan`）：プロジェクトのノートと、`project` がそのプロジェクトのエピック・タスク
  - すでにアーカイブフォルダにあるものは数だけ出す
  - 作業ログは複数のプロジェクトにまたがるので対象にしない
- 移動先は、アーカイブフォルダの下に今のパスをそのまま付けた場所
  - 例：`Tasks/TASK-….md` → `Archive/Tasks/TASK-….md`
  - フォルダ・ファイル名に意味は無い（要件 3.1）が、元の場所が分かるようにそろえる
- 注意：エピック・タスクのステータスが完了系・停止系でない、移動先に同じパスのノートがある
  - 注意があっても一覧には出す（移動するかは人が決める）
- アーカイブできるプロジェクト（`archivableProjects`）
  - ステータスが完了系（クローズ済み）で、アーカイブフォルダの外にファイルが残っているもの
  - 停止系（失注・中止など）は対象にしない（要件 4.9 はクローズ済みのみ）
- 並びはプロジェクト → エピック → タスク、同じ種類はパス順。移動元のフォルダごとにまとめる

### 11.15 工数の累積（`burnup.ts`）

- 対象はプロジェクトのタスク（アーカイブ内も含む）に付いた作業ログの行
  - 日ごとに予定・実績を足し、期間の毎日の累積を出す
- 期間は次を合わせた範囲（どこから始まりどこで終わるかを全部見せるため）。どれも無ければグラフなし
  - プロジェクトの開始日・期限日、作業ログの最初〜最後の日、タスクの計算上の日程の最初〜最後
- 実績の累積は今日まで（実績の線を今日で止めるため）。予定の累積は期間の終わりまで
- 見積の合計はタスクの見積の合計（11.3 と同じ値）
- 縦軸の目盛り（`niceTicks`）は 1・2・2.5・5 ×10ⁿ の刻みで5本ほど。横軸（`monthTicks`）は各月の1日
- 予定の進捗（`progressPlan`）：毎日、計算上の終了日（11.9）がその日以前のタスクの数を数える
  - 分母と完了の数え方は進捗率（11.3）と同じ（停止系を除く）
  - 計算上の日程は遅れを反映しているので、遅れている未完了のタスクは「今日までに終わるはず」に入る
  - それが実績の点との差になって見える
  - 日程を計算できないタスクは線に入れず、件数を返す

### 11.16 メンバーの負荷率のグラフ（`loadChart.ts`）

- `loadChart` が、選んだ期間について、メンバーごとに `memberLoad`（11.5）を呼ぶ
  - 期間（`loadChartPeriod`）：今週・来週は月曜始まりの週、今月・来月は月
  - 選んだ並び順（`sortLoadRows`）に並べる。段階の判定も 11.5 のまま
- 並べ替え：名前順、予定負荷率の高い順・低い順
  - 負荷率の無い人（期間に稼働日が無い）はどちらの向きでも最後。同じ負荷率なら名前順
- 横軸の目盛りは `niceTicks`（11.15）で、0 から全員の予定負荷率・負荷許容率・100% の最大まで
- 負荷警告・負荷注意の人数も数える（見出しの下に出す）

### 11.17 WBS 番号（`wbsOrder.ts`）

- タスクはエピック内の連番だけを持ち、表示で「エピックの番号.連番」にする（`taskWbsLabel`）
  - エピックの番号を変えても、タスクのノートを書き換えずに済むため（SVN でぶつかりにくい）
  - エピックの無いタスクは連番だけを出す
- 並び（`sortByWbs`）：番号を数として比べる。番号の無いものは元の順のまま後ろ
- ドラッグ後の順（`moveInOrder`）：動かした行を、落とした行の前か後ろに入れる
- タスクの振り直し（`renumberTasks`）：並べた順に 1, 2, 3…。番号の無いタスクにも付ける
- エピックの振り直し（`renumberEpics`）：今使っている番号の組を数の順に並べ、並べた順に配る
  - `1.1`・`1.2` のような番号の形を崩さないため
  - 番号が無い・重なるエピックの分は、最後の番号の末尾の数を進めて足す（`nextWbs`。1.9 → 1.10）
- どちらも番号が変わるものだけを返す（書き込むノートを最小にするため）
- 新しいタスクの番号（`nextTaskWbsIn`）：同じプロジェクト・エピックのタスクの最大の連番＋1
  - 数でない番号は数えない。ノートの作成とタスクのフォームで同じ関数を使う

## 12. 開発用の仕組み（`plugin/scripts/`）

- `deploy.mjs`：ビルド結果を開発用Vaultにコピーし、`.hotreload` を置く（Hot Reload が自動で読み直す）
  - `npm run dev` ではビルド成功のたびに呼ぶ
- `generate-dummy.mjs`：ダミーデータ（要件 6.3 の規模）を作る
  - frontmatter の最後に `dummy: true` を入れ、消すときはそれがあるファイルだけを消す
  - 乱数は seed で固定する
  - わざと入れたもの以外の警告が出ないように作る（警告の数を見やすくするため）
  - 日程はプラグインと同じ決まり（要件 4.7）で先に計算し、ステータスを日程に合わせる
  - 期限日は計算上の終了日以降、見積は予定・実績の合計より少し多め、配分は予定の合計より少し多め
  - わざと入れる警告：クローズ以外のプロジェクトに、期限超過・工数超過・期限超過見込みを1件ずつ
  - 並びの2番目と5番目のプロジェクトには配分超過も。遅らせるのは後続の無いタスク（広がらないように）
  - 基準日（`--today`、既定は実行した日）で作るので、日がたつと期限超過が増える。そのときは作り直す
  - 健全性チェックの確認用に、誤りのあるタスク5件と作業ログの誤りの行2件も作る
- `readme-text.mjs`：使い方の正本（`docs/vault/README.md`）を `src/generated/readmeText.ts` に変換する
  - `npm run dev`・`npm run build` の最初に走る（9章「使い方のノート」）
  - 作ったファイルも Git に入れる（取り出した直後でも、ビルドせずに型チェック・補完が通るように）
  - README を直したときは、このファイルの差分も一緒にコミットする

## 13. HTMLレポート（`report/htmlReport.ts`, `commands/htmlReport.ts`）

- 中身（要件 4.10）
  - 先頭に作成日時と基準日（今日）
  - 「全プロジェクト」：ダッシュボードと同じ表・負荷の高いメンバー・2週間以内のマイルストーン
  - プロジェクトごとの節：概要・マイルストーン・エピック・工数配分
  - 計算はダッシュボード（11.10）とプロジェクト状況（11.8）をそのまま使い、画面と同じ値にする
- 対象は、クローズしていない・アーカイブ内でないプロジェクト
  - ビューの絞り込みには関係しない（誰が書き出しても同じ範囲になるように）
  - メンバーは在籍者。プロジェクトの表示名は書き出した人の個人の設定
- タスクの行は入れない（数千件になり重くなるため。上司が見るのはエピック単位まで）
- 1つの HTML ファイルに CSS も入れ、JavaScript は使わない
  - ほかのファイルが無くても、メールで送っても、ブラウザでそのまま開ける
  - 白地で印刷でき、印刷ではプロジェクトごとに改ページする
  - 全プロジェクトの表から各プロジェクトの節へページ内リンクで飛べる
- 文字はすべてエスケープする（`<` などがあっても崩れない・スクリプトが入らないように）
- 書き出し（`commands/htmlReport.ts`）：個人の設定の出力先フォルダに `project-report.html` を上書きで書く
  - Vault の外に書くので、Obsidian の API ではなく Node の `fs` を使う（デスクトップ専用のため使える）
- 出力先は Windows の絶対パス（`C:\…` か `\\サーバー\共有\…`）だけ受け付ける（`reportFolderProblem`）
  - フォルダが無ければ作らずに知らせる（つなぎ忘れや打ち間違いで、意図しない場所に作らないため）
- 呼び出し：コマンド「HTMLレポートを書き出す」、リボンのメニュー、ダッシュボードの操作の欄のボタン
